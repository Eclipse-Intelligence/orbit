# Architecture

PostgreSQL is the source of truth. The web UI, REST API, and MCP server call the same company service in `lib/crm/companies.ts`. Matching, partial updates, idempotency, and audit writes are not reimplemented in each client.

```
Browser  -> server actions -> domain services -> PostgreSQL
Agent    -> /api/v1        -> domain services -> PostgreSQL
Agent    -> /api/mcp       -> domain services -> PostgreSQL
Person   -> /api/mcp       -> domain services and lib/mail -> PostgreSQL
```

The MCP server lives in `server/mcp/`. Agent tokens and personal tokens both reach it (see Personal tokens and MCP mail).

The references for agents are `docs/api.md` (REST endpoints, scopes and webhooks), `docs/mcp.md` (every MCP tool and which tokens see it) and `docs/assistant.md` (how the in-app assistant runs and every one of its tools).

Zustand (`stores/companies-store.ts`) holds which panel is open and the Mail unread count. Lists are rendered from the database. A reload reads PostgreSQL again.

## Tenancy

Every business row has `workspace_id`. Human sessions resolve a user id, then `withActor` sets the JWT claims and `SET LOCAL ROLE authenticated` for the transaction. Agent sessions set `app.workspace_id` and `SET LOCAL ROLE crm_agent`. Policies use those settings. The table owner is not the role the request runs as, and row-level security is forced.

Business tables are in the `crm` schema so the Supabase Data API does not expose them. Privileged functions live in `private` and are executable by the `crm_app` login, not by `authenticated` or `crm_agent`. Policies may call `private` helpers such as `private.user_workspace_ids()`, `private.session_user_id()` and `private.is_workspace_admin()`, but queries run inside `withActor` cannot: `authenticated` has no usage on the schema.

Most business rows are visible to every workspace member. The exceptions are enforced by policy, not by the UI: mailboxes, email messages, call records, calendars, calendar accounts and their events (except events from a Use for CRM calendar that list a contact or company, which every member can read), unfiled Teams transcripts, assistant conversations, AI accounts, Orbit Agent pairings, LinkedIn capture browsers and pairings, personal tokens, Granola keys, email signatures, unsent email attachments, the Mail mirror and everything built on it (`mail_sources`, `mail_folders`, `mail_messages`, `mail_drafts`, `mail_reminders`, `mail_summaries`, `mail_prepared`, `mail_attachment_texts`, `mail_tracking`, `mail_opens`, `mail_viewer_addresses`, `mail_sender_rules`, `mail_preferences`, `mail_subscriptions`, `mail_unsubscribes`, `mail_pitch_failures`), sending addresses (`send_identities`), push subscriptions and the push log, booking pages, workflow runs and their steps, and notifications are owner-only. Tasks are visible to their owner, their creator, and the workspace owner and admins (`private.is_workspace_admin`); the update policy uses the same rule, and its check allows handing a task to someone else only when the editor still sees it afterwards. The agent mailbox's messages and sender list are visible to the workspace owner and admins and to the member each one belongs to; its thread map is owner-only (see Agent mailbox).

### Workspaces

A person can belong to several workspaces. `getUserActor` reads every membership (oldest first) and uses the one named by the `crm_workspace` cookie, or the oldest when the cookie is missing or names a workspace they are not in. The oldest membership is their home workspace (`private.home_workspace_id`, `getHomeActor`). The sidebar switcher sets the cookie through `switchWorkspaceAction`, then reloads the current section's index page (`sectionIndex` in `lib/workspace-paths.ts`: a company page lands on `/`, a board on `/opportunities`, Mail, Calendar, Capture and Settings keep their path). Only someone who owns at least one workspace can create one: `createWorkspace` takes only a name and calls `private.create_workspace(user, name, null)`, which checks that, makes them owner, adds the default pipeline and its stages, sets their Capture marker and writes a `workspace.created` audit event. A new workspace starts blank: nothing is copied from the workspace it was made in, so `crm.workspaces.brand_source_id` stays null.

Mail, calendar and the other personal things follow the person, not the workspace. Reads of mailboxes, the Mail mirror, calendars, calendar accounts, own calendar events, sending addresses, signatures, AI accounts, Orbit Agent pairings, push devices and daily notes filter by user only; row-level security still limits them to the person's rows in workspaces they belong to. Writes keep each row in one place through `before insert` triggers: `private.mail_row_workspace()` puts Mail mirror rows, sending addresses, calendars and events in the workspace of the mailbox, calendar account, source, message or calendar they belong to, and `private.personal_row_workspace()` puts per-person rows (Mail preferences, sender rules, subscriptions, read tracking, signatures, unsent attachments, hidden attendees, AI accounts, Orbit Agent pairings, push devices and the push log, daily notes) in the home workspace, so an upsert from any workspace hits the same row. A mailbox is created in the workspace it is connected from; connecting Microsoft again from another workspace updates the existing connection. Background work runs once per person: `private.background_members()` marks each person's home membership (`is_home`) and only that one carries their mail and calendar sync, alerts and due mail, while every workspace still gets its own target for workspace jobs. Page-load syncs run as the home actor too. Matching calendar meetings to contacts and companies still uses the workspace the sync runs in; mail, Granola notes, Teams calls and Teams transcripts are matched across workspaces (below, and Calls across workspaces). Mail notifications (`source = 'mail'`) show in every workspace; other notifications stay in their own. Removing someone from a workspace moves their personal rows to their next workspace (`private.move_personal_rows`) when they have one, and disconnects them only when they have none.

### Mail across workspaces

`lib/mail/routing.ts` decides where a person's mail belongs, and `lib/mail/timeline.ts` (`fileMailOnTimeline`) files it. The filer runs as the person (row-level security lets one session read contacts and companies in all their workspaces), matches each email's sender, and for email they sent each To and Cc address, against contacts in every workspace they belong to, and the sender's domain against companies (never free-mail domains), then writes the activity in each matching workspace as that workspace's actor (`workspaceActors`). An email gets one activity per contact in a workspace, or one on the company when no contact matches (`mailMessageId` or `internetMessageId`); when the sender of an email filed on a company later becomes a contact, or their contact was archived and they are added again, the existing activity moves onto the contact (an `activity.updated` audit event) instead of a second one being logged. A fresh inbound email on a company with no open task also suggests a follow-up task there. Three owner-only tables (forced row-level security, `user_id` is the session user and every workspace named must be one of theirs) change that:

- `crm.mail_address_homes`: the person's choice of home workspace for one of their receiving addresses (a mailbox in `mail_sources` or a sending address in `send_identities`), set with Workspace next to each address in Settings › Email (shown only to people in more than one workspace). The same choice decides the default From in that workspace (see Default From). Without a row the home is the workspace the account lives in. The receiving address of an email is the first of the person's addresses in To or Cc, otherwise its mailbox.
- `crm.mail_domain_rules`: everyone at a domain files in the chosen workspaces only (`workspace_ids`). Free-mail domains and the person's own or a colleague's domain (in any of their workspaces) are refused. When an inbound sender at the domain is not a contact in a chosen workspace and isn't automated or a newsletter, the filer adds them there (copying name, title and company from another workspace when known) for email received after the rule was saved.
- `crm.mail_thread_routes`: per conversation (`source_id`, `thread_key`), the workspaces chosen in Filed in (`filed_in`), the workspace a Capture item was moved to (`capture_workspace_id`), the contact chosen with File to (`contact_id`) and Dismiss (`ignored_at`).

A thread choice beats a domain rule, which beats automatic matching, and a File to contact only counts in a workspace the thread is filed in (choosing workspaces without that contact's drops it). Add to in a thread's Contacts adds the conversation's current workspace to the thread choice when the effective filing left it out. Changing the choice files the conversation in the new workspaces (adding the main counterpart as a contact where nobody on it is known) and stops filing new email elsewhere, but activities already logged stay: they are append-only and shared with that workspace. Email from people no workspace knows waits in Capture (`unknownMail` in `lib/mail/filing.ts`) in the moved-to workspace, else the domain rule's first workspace, else the home of the receiving address. Capture lists the newest email per thread from the last 30 days (`CAPTURE_LOOKBACK_DAYS`, the same window as Replies) that is in the Important split, has no unsubscribe footer, no newsletter, blocked or cold pitch record in `mail_subscriptions`, no ready `pitch` in `mail_prepared`, isn't from an automated or calendar sender, the person's own or a colleague's domain, and has no reply from the person after it. These count towards Capture's badge, and `captureStatuses` works out every workspace's counts from one `captureContext` so the switcher can show a dot next to another workspace with something new since that Capture was last opened. "Email received" workflow events are queued in each workspace the email is filed in, or in its Capture workspace when nobody knows the sender. Deferral checks treat a sender known in any workspace as known, and the deferral task goes in a workspace the email is filed in (the current one when it is). The older Capture filing in `syncMailbox` skips a workspace that a thread choice or domain rule leaves out (`routedAway`, matched on the mailbox's own source when there is one). The layout and the Capture page share one `captureContext` per request (one `unknownMail` scan and one `waitingOnce`), and the other-workspace dots are skipped for someone in one workspace. Prepared replies and nudges use the brand of the one workspace the thread is filed in (`threadBrand`), and leave the brand out when it is filed in several. Leaving a workspace drops it from these rows (`private.move_personal_rows`).

### Moving records between workspaces

Someone in more than one workspace can move companies and people to another of their workspaces: More › Move to workspace… on a company or person, Move to workspace… in the bulk bar on the Companies and People lists, the assistant's `move_records_to_workspace` and the MCP tool of the same name. Pages get the other workspaces from `getMoveTargets` (the cached memberships, minus the current one), and an empty list renders nothing, so a person in one workspace sees no sign of it. `lib/crm/move-workspace.ts` checks again on the server: the actor must be a person in two or more workspaces, the target must be one of theirs (by id, or by name for the assistant and MCP) and they need `companies:write`, `contacts:write`, `opportunities:write`, `activities:write` and `tasks:write` in both. Moving records out needs owner or admin in the source workspace (checked in `moveActors` and again in SQL); any member of both can copy, and the dialog ticks and locks "Also keep in" for them. Up to 100 records a call.

The dialog (`components/crm/move-workspace-dialog.tsx`) picks the workspace, "Also keep in <current>" (copy instead of move), "Copy opportunities too" with a copy, "Also move <company>" ("and its N other contacts"; "their N companies" in bulk) for people who have a company, and "Move its N contacts too" ("its contact" for one, "their" in bulk) for companies with people, both ticked by default and worded Copy with a copy. Unticking the second says "They'll stay in <current> without a company." and, when there are deals, Put opportunities on (the target's pipeline or a board) and Stage, defaulting to the stage with the same name, else the first stage ("Same as now" when the deals are in different stages). `previewMoveToWorkspace` fills the summary: the people, deals, activities, tasks and files that go along (every task, including other members' private ones, since they all move), companies that come with their people, records that merge into ones already there, the boards the company comes off and the AI fields that stay behind. A failed preview shows Retry.

The work is one transaction: `withActorAfterAppStep` raises `statement_timeout` to 60 seconds for that transaction (the pool's default is 10), takes the companies and contacts advisory locks of both workspaces, then calls `private.move_records_to_workspace(user, source, target, input, dry_run)` with `query` on the transaction's `crm_app` connection, and then, as the person, fills gaps on merged records with `fillCompanyGaps` and `fillContactGaps` from `lib/crm/merge.ts` and writes the audit events. A timeout or deadlock becomes "Timed out. Move fewer records.", and a unique violation says the target already has a matching record. The function is security definer, executable only by `crm_app`, and refuses anyone who isn't a member of both workspaces. It plans in a temporary `orbit_move_map` table (old id, new id, merged), which the preview reads with `dry_run`:

- Companies match an active company in the target by domain, then LinkedIn, then the same normalised name when neither has a domain (`private.move_company_match`); people by email, then LinkedIn, then Sales Navigator (`private.move_contact_match`). A match is merged into: the moved record goes to the target archived, everything that pointed at it points at the match, and the match's empty fields are filled (never overwritten) and tags combined, as a merge does.
- `includeCompany` (true from the app, assistant and MCP) moves each person's company as a company move, taking all its people, and merges it into a match in the target as usual. `includeContacts` false moves a company without its people: they stay in the source with `company_id` cleared (`contact_stay` in the plan), and their activities and tasks stay with them, losing the company and any moved deal or removed card. Deals go with the company and lose a primary contact who stays. A proposal needs a company and a contact, so anyone named on a moving company's proposals goes with it whatever their company, on every move (`proposalContacts`); their own company, when it isn't moving, is linked to a match in the target or copied there. The moved company's `health_activity_id` is cleared when that activity stays. Each person left behind gets a `contact.updated` audit event (`companyMovedTo`), which undo refuses. A copy applies the same choices without changing the source: people who aren't copied are listed in `notCopied` (not `leftBehind`), and the company's activities that name one of them are copied without the person. The checkbox counts include archived people on a move, since they move or stay too; a copy skips archived people. When a company comes along with a person, the result message names it, for example "Moved Tia Tandem, with Tandem and its 2 other contacts, to Mark Ridgeon." Calendar events in the source drop the ids of every company and person that moved. The SQL defaults are `includeCompany` false and `includeContacts` true, the behaviour before these options, so a caller that leaves them out still gets it.
- A person on their own (`includeCompany` false) brings their company, unless the target already has it (they are linked to that company, which also takes the source company's empty details) or the company has other active people who aren't moving (the company stays, and a copy of its details is made in the target for them, archived if the original is). Moving a company takes all its people, archived ones too.
- With a company go its deals, tasks, activities (with their tones, call summaries, follow-up suggestions, call records, Granola and Teams imports and filed emails, unless the target already holds that call, import or email), proposals and their versions, links, files, signatures and steps (the template is dropped unless the target has it), Knowledge items and chunks, memories, market notes and watchlist items (unless the target already has that URL or label), and enrichment lookups. A proposal belongs to its company: it moves when its company moves, and keeps that company (or the company it merges into). A person who moves alone takes a proposal of a company that stays only when that company is linked or copied into the target for them, filed under that link. If a moving person is named on the proposal of a company that neither moves nor is linked, the move is refused naming the proposal ("Kay Lane is named on the Tandem proposal 'Q1 plan'. Move Tandem too, or change the proposal's contact first.", with "the archived Tandem proposal" when it is archived), and the preview returns the same text as `proposalConflict` so the dialog can block the move. Deals go on the chosen pipeline or board (`private.move_deal_stage`): an open deal takes the chosen stage, else the same name, else the first stage; a won or lost deal takes the same name, else the target's won or lost stage, else the chosen stage, so choosing a stage never reopens a closed deal. The status follows the stage. A board refuses more than one card per company, and a pipeline with no stages is refused before anything changes. Cards on the source's boards are deleted; activities and tasks that pointed at them keep the company. Tasks, activities and other rows that pointed at a person who moved go with them. Rows that stay in the source lose their links to moved records, and owners who aren't members of the target become the mover.
- AI field answers, web check signals and the company's web state are deleted in the source on a move, so the target's AI fields and checks fill in on their normal schedule. Workflow runs stay with the source's workflows, and so do `workflow_record_marks`, so a record moved back later isn't run again by a workflow that already handled it. Docs aren't per record, so they and their `page_links` stay; a mention of a moved record in a source doc no longer opens it there. Knowledge and proposal files keep their storage paths, which may start with the source workspace's id; files are read by the stored path, so they still open.
- A copy leaves the source as it is. It creates the companies and people in the target (or fills gaps on a match), copies their activity and call summaries, and copies open deals (not board cards) only with Copy opportunities too. Tasks, proposals and Knowledge aren't copied. A copied company skips health (and its activity), relationship overrides, web state, AI answers and signals; a copied person skips relationship overrides.

A move writes `company.moved_out` and `contact.moved_out` in the source and `company.moved_in` and `contact.moved_in` in the target, with the deals that moved and how many board cards came off. `eventTriggerTypes` maps none of them, so a moved record starts no workflow and fires no `*.created` webhook. A company copied for people who moved without it writes `company.copied` in the source and `company.created` in the target. A copy writes `company.copied` and `contact.copied` in the source and, in the target, `*.created` with `copiedFrom` (or `*.updated` for a record that took the copy's details) and `opportunity.created` with `copiedFrom` for copied deals, which can start Record created workflows there. Undo can't reverse a move. Migration `20270105100000_move_records_workspace.sql` adds the function and its helpers (`private.move_owner`, `move_company_match`, `move_contact_match`, `move_deal_stage`); `20270110100000_move_together.sql` replaces the function with the same signature to add `includeCompany` and `includeContacts`. There is no new table.

### Settings

Every setting lives in one place: either the person (the same in every workspace) or the workspace (only there). `lib/settings-nav.ts` lists the pages (`SETTINGS_PATHS`, `SETTINGS_LABELS`) and builds the menu with `settingsNav({ name, multi })`. For someone in more than one workspace it returns two groups: You (General, Email, Calendars, Connections, Memory, API tokens), and the current workspace with its tile (About you, Brand, Knowledge, Team, Pipeline, Tags and lifecycles, AI fields, Email templates, Booking page, Learning, Tools, Activity log). Someone in one workspace gets one list with no headings, without About you and Memory, and no page shows them workspace wording: General shows one About you card (role, about, LinkedIn, how you write, what you care about) that saves through both `saveYouAction` and `saveAboutYouAction`, Learning adds a You tab with their personal notes, and `/settings/about-you` and `/settings/memory` redirect to `/settings/general#you` and `/settings/learning#notes`. `app/(crm)/settings/layout.tsx` passes `multi` (more than one membership) to `components/crm/settings-shell.tsx`, which shows the menu down the left on wide screens. On phones `/settings` is the menu (`components/crm/settings-index.tsx` sends wide screens on to General) and every page has a Settings link back to it; the desktop sidebar links straight to General.

Old addresses still work. `legacySettingsHref` in `proxy.ts` sends `/settings/integrations` to `/settings/connections` and `/settings/api` to `/settings/api-tokens` (keeping the query), and `/settings` with a query through `settingsRedirect` (calendar connection results to Calendars, the rest to General). `settingsHashTarget` maps old and current card anchors (`#microsoft`, `#signatures`, `#clickup`, `#webhooks`, `#web-checks`, `#memory` and the rest) to the page that holds them; `SettingsHashRedirect`, in the shell, runs on every Settings page and moves to that page keeping the anchor. Sync now and Connect actions return to Settings › Email (mailbox) or Settings › Connections (Teams calls and transcripts, Granola) with `error` or `info`.

## People and agents

Humans sign in with Supabase Auth when `NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_ANON_KEY` are set. `proxy.ts` and `getUserActor` (`lib/auth/user.ts`) check the session with `auth.getClaims()`, which refreshes an expired session and then verifies the ES256 token locally against the project's cached public keys, so a page makes no Auth request; `getUserActor` is wrapped in React `cache()`, so a request looks up its memberships once. Membership is still read from the database on every request, so removing someone takes effect at once even though their token lasts until it expires. Without those, a local password session is used. `supabase/bootstrap/local-auth.sql` creates a small `auth.users` table and `auth.uid()`. Do not run that file on a hosted Supabase project.

Agents are rows in `crm.agents`, not user accounts. A credential is a random token stored as a SHA-256 hash. The plaintext is shown once. Revoke it by setting `revoked_at`. Scopes are `crm:read`, `companies:write`, `contacts:write`, `leads:write`, `activities:write`, `opportunities:write`, `tasks:write`, `market:write`, `docs:read`, `docs:write`, and `admin`. `admin` implies the others. `market:write` only allows reading the watchlist and adding market notes. A lead ingestion checks `leads:write` and the write scope of each record it actually creates or updates.

The service role key is never given to an agent. Agents use their own bearer token against this application's API.

### Personal tokens and MCP mail

`crm.personal_tokens` holds each person's MCP tokens (owner-only, forced row-level security): name, prefix, the SHA-256 of the token, and last used and revoked times. `lib/auth/personal.ts` creates (`orbit_…`, shown once, at most 10 active per person), lists and revokes them; the card is Settings › API tokens › Personal tokens, which shows each token's workspace to people in more than one workspace. `/api/mcp` treats a bearer token starting with `orbit_` as a personal token: `private.authenticate_personal_token` (security definer, executable only by `crm_app`) returns the person only when the token isn't revoked and they are still a member of its workspace, and updates `last_used_at` at most once a minute. The request then runs as that person, with their role's scopes, through `withActor`, limited to 120 requests a minute per token. `server/mcp/server.ts` registers the mail tools in `server/mcp/mail.ts` only for a person, so workspace agent tokens and stdio (`npm run mcp`) never get them. The mail tools read the Mail mirror and its attachments, ask questions with `askMail`, and save or discard Outlook drafts through `lib/mail/compose.ts`. There is no tool that sends email.

## Companies

Active companies in a workspace are unique by canonical domain. When neither has a domain, a company also matches another company with the same normalised name. Create and update follow exactly that rule, so creating "Mercury" with `mercury.com` succeeds even when a "Mercury" without a domain exists. Upsert is the one exception: an upsert with a domain that matches no company falls back to a company with the same normalised name and no domain, and attaches the domain to it. The same display name with two different domains stays two companies. Writes take a workspace advisory lock, then unique indexes stop a race.

Name normalisation lowercases, strips accents, keeps letters and digits in any script plus `+` and `#`, and drops a trailing legal suffix such as Inc or GmbH. When an upsert or create gives a website but no domain, the domain comes from the website host, unless that host is a shared one such as LinkedIn, Facebook, Instagram, X, GitHub, Medium, Google Sites, Notion, Wix, Squarespace, or YouTube.

`PATCH` and upsert leave omitted fields alone. An explicit `null` clears an optional field. A domain-only upsert does not replace an existing name. A company or contact write whose values all equal the stored ones changes nothing: no audit event, no webhook, and `updated_at` stays put.

`Idempotency-Key` is stored per workspace and actor. The same key and body replays the stored response. The same key and a different body returns 409.

Deletes archive. `archived_at` is set and the row stays. There is no hard delete on the API.

## Audit

`crm.audit_events` is append-only. A trigger rejects updates and deletes, and those grants are not given out. Mutations write an event with the actor type (`user` or `agent`), agent id, credential id, source, and source URL when the caller provides them. Each event also queues a delivery for every enabled webhook subscribed to that event type, and, when the event can start a workflow, a row in `crm.workflow_events` (see Workflows). Delivery signs the body with HMAC SHA-256 and retries a failed attempt for about three hours.

## People, opportunities, activity, and tasks

Contacts match an active email, then an active LinkedIn profile, then the same normalised name at the same company. Opportunities use the workspace default pipeline unless `pipelineId` names a board (see Boards). A primary contact must work at the opportunity's company (`assertContactCompany`, on create and whenever the company or contact changes); otherwise the write fails with `invalid_input` on `primaryContactId`. Won-deal board cards copy the contact only if it still works there. Omitting the stage picks the first stage. A won or lost stage sets the status, and setting the status to won or lost moves the opportunity to that stage. `opportunity.stage_changed` is written when the stage or status changes.

Activities are append-only: `authenticated` and `crm_agent` can insert them but not update them. A company timeline reads activities stored against that company. `listActivities` also filters by `actorUserId` (who logged it, `a.actor_user_id`), `actorAgentId` (`a.actor_agent_id`; the log's Person menu lists agents from `listActivityAgents`), `from` and `to` (`occurred_at`, `to` exclusive; a date-only `to` in the API or URL means the end of that London day). Settings › Activity log (`app/(crm)/settings/activity/page.tsx`, `components/crm/activity-log.tsx`) uses it with the viewer's id by default, any member's, or none for Everyone; `activities_actor_user_idx` covers `(workspace_id, actor_user_id, occurred_at desc)` for live rows. Row-level security is unchanged: activities are shared with the workspace. `/activities` redirects there. Tasks live in `crm.tasks`; the Tasks page (`/tasks`, which `/actions` redirects to) opens on All, every open task with overdue first and undated last. Completing a task sets `completed_at` and leaves that timestamp in place if it is completed again.

`POST /api/v1/leads` and the `add_lead` tool run company, contact, activity, opportunity, and task writes in one transaction, through the same functions the individual endpoints use. A second lead with the same domain and email updates those rows instead of creating new ones.

Company, contact, opportunity, and task references must belong to the same workspace. That check is a trigger, so a foreign id cannot be attached even when the caller's row-level policy would otherwise hide it. It checks a reference only when that reference, the row's company, or its workspace changes, so moving a contact to another company leaves its existing tasks and opportunities editable.

## Conversations

`record_email` and `record_meeting` file an interaction on a contact matched by email, or on a company matched by the email's domain. When that company has no open task, the CRM adds a follow-up due in two days.

The inbox connects one Microsoft mailbox per user. `MICROSOFT_CLIENT_ID` and `MICROSOFT_CLIENT_SECRET` come from an Entra app with delegated `Mail.ReadWrite`, `Mail.Send`, `User.Read`, `Calendars.ReadWrite`, and `offline_access`. Signatures: `crm.email_signatures` (owner-only RLS) holds one plain-text signature per user and sending address (lowercased, up to 2,000 characters); `saveSignature` only accepts the user's own senders and deletes on empty. `sendContactEmail` appends the sender's signature after a blank line unless `signature: false`, and logs the message without it. Senders: `listSenders` returns the main mailbox (`primary`) and every connected Microsoft extra account with `can_send`; `sendContactEmail` takes `from` (an account id, default the mailbox), refreshes and stores that account's token, and records `metadata.from` on the email activity. Attachments: `prepareAttachment` (`lib/crm/email-attachments.ts`) records a row in `crm.email_attachments` (owner-only RLS: name, content type, size up to 25 MB) and returns a signed upload URL from `lib/storage.ts`, which talks to the Supabase Storage REST API with the service key (bucket `email-attachments`, private, created on first use); the browser PUTs the file there. `sendContactEmail` takes the attachment ids, reads each object back (its size must match), and `sendGraphMail` sends up to 3 MB in total inline through `sendMail`, otherwise creates a draft (`POST /me/messages`, which needs `Mail.ReadWrite`; a 403 asks to reconnect), adds small files directly and large ones through `createUploadSession` in 3,200 KiB chunks, then sends it, deleting the draft on failure. After sending, the rows and objects are deleted unless the caller keeps them (bulk email discards them once all messages are out), and the email activity records `metadata.attachments` (`{name, size}`). `private.claim_stale_email_attachments` lets the cron remove rows older than a day, whose objects are then deleted. The refresh token is encrypted with `APP_SECRET`. Filing for Capture (`lib/crm/inbox.ts`) is separate from the Mail mirror below: opening Capture, or choosing Sync now in Settings › Email, reads messages received since the last sync (the first sync looks back 14 days, up to 100 messages). From a contact, Send email delivers through that mailbox and files the message on the contact. A mailbox connected before Mail.Send was granted has to be disconnected and connected again. A message attaches to a contact by email address, otherwise to a company by domain. The mailbox's own address is not the contact. A match from the last 48 hours files an email activity and, when the company has no open task, suggests a follow-up. Mail that matches neither stays unattached. Gmail is not connected. The Outlook calendar is described below.

Teams phone calls come from Graph `getPstnCalls`, which only accepts an app-only token, so Orbit uses the client-credentials flow with the same Entra app and the `CallRecords.Read.All` application permission. The tenant is `MICROSOFT_TENANT` when it names one, otherwise the `tid` claim of the connected mailbox's access token, cached on the sync state. Only rows whose user principal name is the mailbox address (or whose user id is the mailbox user) and whose type is `user_in` or `user_out` count. `crm.call_records` stores one row per call log id per workspace: direction, the other party's number in E.164, start time, duration, and the contact, company, and activity it was filed on. A row with no matching contact phone keeps those empty and is filed on a later sync. `crm.call_sync_state` keeps one row per mailbox connection with the tenant id, the last synced and attempted times, and the last error. Both tables are readable and writable only by the mailbox owner. The CRM layout runs a sync after the response through `after()`, claiming the attempt so Graph is called at most once every five minutes; Sync calls in Settings › Connections forces one. Each sync re-reads from 24 hours before the last sync, and syncs for a connection run one at a time under an advisory lock.

`crm.call_insights` holds at most one summary per call or meeting activity, since activities are append-only and never updated. It stores the workspace, the activity, the contact and company copied from it, the source (`manual` for a pasted transcript, `teams` for a Teams transcript, `granola` for a Granola meeting), the transcript as compact `Speaker: line` text (up to 200,000 characters), the summary, key points, suggested action items, the model, a status (`pending`, `ready`, or `failed`), and the last error. Each action item is `{id, title, owner, dueDate, status, taskId}`: owner is `me`, `them`, or null, the due date is a London calendar day, and accepting one creates a task through the normal task path and records its id. Workspace members and agents can read and insert rows in their workspace, and can update only the summary, key points, action items, model, status, and error; the transcript, links, and source never change. Summarising needs `activities:write` and accepting an action needs `tasks:write`. The model call (`lib/llm.ts`) runs outside the database transaction against `LLM_API_BASE_URL` with `LLM_API_KEY`, times out after 25 seconds, and retries once on a gateway 5xx, a network failure, or a reply that is not the expected JSON. The summary prompt also asks for `health` (`healthy`, `watch`, `at_risk` or null) and `healthReason`, stored as `sentiment` and `sentiment_reason` with `sentiment_checked_at`. In the same transaction, `applyCallHealth` copies a non-null sentiment to `crm.companies.health`, `health_reason`, `health_at` (the call's `occurred_at`) and `health_activity_id`, for the call's company or else its contact's company, skipped when the company's `health_at` is later than the call (a newer call, or a hand-set health, which stamps `now()` and clears the activity). A change records `company.updated` with fields `health` and/or `healthReason` (operation `call_health`), which feeds webhooks and field-changed workflows; the actor needs `companies:write`. `private.claim_unjudged_calls` (for `crm_app`) claims ready summaries with no sentiment that were never checked, marking them checked; `backfillCallHealth` (`lib/crm/call-health.ts`) runs one per cron request through `judgeCallSentiment`, a smaller sentiment-only prompt, as the call's creator or else the workspace owner. Company context and the contacts page load the summaries for every call they show in one query, without the transcript, which is fetched only when Transcript is opened.

### Automatic transcripts

Transcripts arrive from Granola (`lib/granola.ts`, `lib/crm/granola.ts`) and Teams (`lib/microsoft/transcripts.ts`, `lib/crm/teams-transcripts.ts`). Both go through `lib/crm/conversations.ts`, which records the import, matches people, creates the activity through `createActivityInDb`, and summarises through `summariseCall` outside the import transaction.

| --- | --- |
| `crm.conversation_imports` | One row per imported transcript. Granola rows are unique per workspace and note id and visible to every member. Teams rows are unique per mailbox owner and transcript id, fileable and updatable only by that owner (`user_id = private.session_user_id()`), and readable by that owner until filed, then by every member. `source` is `granola` or `teams`, `kind` is `meeting` or `call`. Matching: a Granola note matches attendees and calendar invitees against contacts by email, then companies by domain, skipping free-mail domains, the note owner, every workspace member, and the owner's and members' own domains, in every workspace the person belongs to (see Calls across workspaces). A match files a `meeting` activity and the import as `filed` in that workspace, otherwise one `unfiled` import waits in To file. A Teams transcript is stored as `pending` and attaches to the activity of the call record with the same `teams_call_id`; this is retried on every transcript sync and every Teams call sync, and a transcript still pending after 48 hours becomes `unfiled`. Filing a Teams transcript from Capture creates the call activity on the chosen contact and links the call record to it; a call record that arrives later for that call reuses the filed activity instead of logging a second call. A note or transcript that fails to import is stored as `pending` with its error and attempt count and retried on later syncs; after three attempts it becomes `unfiled`. Item failures do not hold back `last_synced_at`; only a failed listing or running out of time does. Summaries are retried at most three times for errors that leave no summary row, and a summary left `pending` for more than three minutes (a run that was cut off) is picked up again and shows Try again on the timeline.

#### Calls across workspaces

Calls follow the person like mail. `lib/crm/call-routing.ts` (`routeCallInDb`) runs as the person, whose session reads contacts and companies in all their workspaces, and checks each workspace in turn: the participants' emails (never the person's own addresses, a member's or a member's domain) against contacts, then their domains against companies (never free-mail domains, `FREE_MAIL_DOMAINS`). A domain rule (`crm.mail_domain_rules`) limits everyone at its domain to the rule's workspaces, and for a call after the rule was saved adds an unknown participant at that domain as a contact in each of them (copying name, title and company from another workspace when known, never for automated addresses). Teams transcripts carry speaker names, not emails; a name of two or more words that matches exactly one live contact in a workspace (and no member's name) is used only to choose which workspace's To file gets a transcript that never matched a call, never to log a call on its own.

- Granola (`fileGranolaNote`): one import, activity and summary per workspace that knows someone on the note, all in one transaction as that workspace's actor. `knownImportsFor` returns the workspaces that already have the note (any member's import counts, as Granola imports are shared and unique per workspace) and whether the person has imported it themselves: a note the person already imported, or one every workspace has, is skipped; otherwise it is routed only to the workspaces that don't have it, so a colleague's import in one workspace never keeps it out of the person's others, and nothing is filed twice in a workspace. When only workspaces without it are left and none of them knows anyone on it, it is skipped rather than put in To file. A failed first import's `pending` placeholder is deleted once the retry lands elsewhere.
- Teams calls (`syncCalls`): the other party's number is matched against contacts' phones in every workspace (a contact whose email domain has a rule only counts in the rule's workspaces), and each matching workspace gets its own call record and call activity. An unmatched call is kept once, in the mailbox's home workspace, and a later rematch moves it to (and copies it into) the workspaces that now know the number. `crm.call_records.workspace_id` is updatable by its owner for that.
- Teams transcripts (`settleTeamsTranscripts`, after every transcript and call sync): a transcript goes to every workspace holding a call record with its `callId` and an activity; one waiting elsewhere is moved there with `private.move_conversation_import` and copied to the rest, then attached. A transcript already filed (for example by hand from Capture, before its call record arrived) is never moved, only copied into workspaces that log the call later. A transcript just moved or copied, or whose call already has a call record with an activity, is never sent elsewhere by a speaker name match. Teams imports are unique per workspace, person and transcript (`conversation_imports_teams_workspace_key`), and `knownImportsFor` counts the person's own imports plus a colleague's filed one, each only in its own workspace: a transcript the person already has, or one every workspace has, is skipped, and otherwise it goes only to the workspaces that don't have it.
- Summaries, action items and follow-ups: each workspace's import is summarised as that workspace's actor (`summarisePendingAcross`), so the call insight, account health, accepted action items (tasks in that workspace, sent to that workspace's ClickUp list) and Knowledge entry belong to it. A summary that is already ready in another of the person's workspaces is copied (`summariseCall` with `reuse`) instead of calling the model again. Claiming a summary takes a transaction-scoped advisory lock on source, external id and user, and stamps `summary_claimed_at`; a sibling claimed in the last three minutes without a finished summary makes the others wait for it and reuse its result, so two workspaces summarising at once pay for one model call. `followUpCallsAcross` drafts call follow-ups in each workspace, so a call filed in two workspaces gets one follow-up draft per workspace.
- A call already filed in one workspace isn't filed again into another that later adds the number or the person, as with mail; only Teams transcripts follow call records that arrive later.

A call nobody knows waits in To file in one workspace: the first workspace of a domain rule for a participant's domain, else the home of the account's address (`crm.mail_address_homes` for the Granola account's or mailbox's address), else the workspace that address is connected in, else the workspace the sync runs in. To file shows Move to on it, like unknown email: `moveImport` (`lib/crm/call-routing.ts`, the `import-move` Capture action) checks the import is the person's own and waiting, then calls `private.move_conversation_import(user, import, workspace)` (security definer, `crm_app` only), which refuses a workspace they aren't in. When the target already has that conversation, the moving import is dropped only if the target's copy is the person's own and `filed`; an `ignored` or `pending` copy (such as a failed first import's placeholder) is deleted and the import moved; a colleague's `filed` or `unfiled` Granola copy refuses the move ("A colleague already has this conversation in that workspace."). A moved `unfiled` import gets a fresh `unfiled_at`.

Background work runs without a session. `private.background_members()` lists workspace members; each workspace acts as every member who owns a connected mailbox (or as its owner when none does), through the same `UserActor` and row-level security as a signed-in page. Public routes do the cheap check first: `private.granola_webhook_targets()` returns the stored Granola signing secrets in one query, the Standard Webhooks signature (HMAC SHA-256 over `id.timestamp.body`, timestamps within five minutes) is checked against them, and only then is the delivery id recorded and the note fetched in `after()`; a delivery with no note id runs the normal rate-limited sync. The Graph routes (`/api/microsoft/notifications` for transcripts and `/api/microsoft/lifecycle` for subscription lifecycle events) echo `validationToken` as `text/plain`, reject more than 50 notifications per request, resolve all subscription ids with one call to `private.transcript_subscriptions(ids)`, accept a notification only when its `clientState` matches, answer 202, and fetch the transcript in `after()`. Lifecycle events renew (`reauthorizationRequired`), recreate (`subscriptionRemoved`), or poll (`missed`). These security-definer functions are executable only by `crm_app`. `/api/cron/sync` checks `Authorization: Bearer <CRON_SECRET>` in constant time. Every background path carries a deadline about 50 seconds from the start of the request: the model call timeout shrinks to fit and skips its retry when time is short, Graph paging and Granola rate-limit backoff stop early, and no step starts without enough time left.

### Outlook calendar

A user's calendars come from two kinds of Microsoft connection. The main mailbox connected in Settings › Email (`crm.mailbox_connections`, unchanged) supplies the main account's calendars. Extra accounts (`crm.calendar_accounts`) are connected from Settings › Calendars or Settings › Email (Add Microsoft account), through the same `/api/microsoft/connect` and `/api/microsoft/callback` routes: the signed state cookie carries `purpose: "calendar_account"` (or `"send_account"` for Add mail, which adds `Mail.Send Mail.ReadWrite` and sets `can_send` from the granted scopes; a later calendar-only reconnect keeps it), the scopes are `openid offline_access User.Read Calendars.Read`, the authority is `MICROSOFT_TENANT` (default `common`), and `prompt=select_account` (plus `login_hint` on Reconnect) lets the user pick a different account. The callback reads `/me` (`mail`, else `userPrincipalName`, and `displayName`), refuses the main mailbox's own address, upserts the account with encrypted tokens and the tenant id from the ID token's `tid` claim, and syncs it in `after()`. Authorization or token errors naming AADSTS50020, 700016, 65001, 90094, 50194, 90008, 500011, `consent_required`, admin approval or consumer accounts become the "organisation hasn't approved Orbit" message, because they mean the app registration's supported account types or the other tenant's consent policy block it. Reconnecting never swaps or deletes an account: the state also carries the address being reconnected (`hint`, always the main mailbox for the main flow, whatever the URL says) and the page to return to (`back`). The callback compares the Graph user id (stored on connect, with the tenant), falling back to `mail` or `userPrincipalName` for older rows, and refuses a different account ("You signed in as X. Sign in as Y to reconnect it.", with Add as another account when X is new), refuses the main address in the extra-account flows, and refuses making an existing extra account the main one. Removing an extra account (`disconnectCalendarAccount`) needs the account's address as confirmation when it has a Mail mirror or sending addresses, because the delete cascades to both (the dialog also counts drafts and scheduled emails). Only a 401, an expired or revoked sign-in, or a 403 with an auth or consent code (or a stored scope without `Mail.ReadWrite`) counts as needing a reconnect; `invalid_client`, AADSTS7000222 and AADSTS7000215 mean Orbit's own Microsoft app needs attention and flag no account.

`lib/microsoft/calendar.ts` lists `GET /me/calendars` (`$select=id,name,color,hexColor,isDefaultCalendar,canEdit,owner`, at most five pages) and reads `GET /me/calendars/{id}/calendarView` per calendar for 30 days back to 60 days ahead with `$select` limited to the fields below plus `body`, `$top=100`, and `Prefer: outlook.timezone="UTC", outlook.body-content-type="text"` (so Graph sends the body as plain text), following `@odata.nextLink` (only on graph.microsoft.com) for at most ten pages and stopping early when the deadline is close. It does not use `calendarView/delta`, because a delta link keeps the window of its first request, does not accept `$select`, and only covers the default calendar. A calendar's colour is Graph's `hexColor`, else its named `color`, else a palette colour (kept once chosen).

### Calendar links (iCal)

Settings, Calendars, Add calendar by link (`addCalendarFeedAction` → `lib/crm/calendar-feeds.ts`) accepts `https://` and `webcal://` (rewritten to `https://`) links without credentials, checks the host, inserts an `ics` row in `crm.calendar_accounts`, and runs a forced sync of just that account; if that first sync fails the row is deleted and the error shown. A duplicate link (same HMAC) is refused. Settings and the Calendar page only ever see `feed_host` plus `…`.

`lib/ical/fetch.ts` reads the link server-side. Before every request, and again for each of at most three redirects, it resolves the host and refuses it when any address is loopback, private (RFC 1918, CGNAT, unique-local), link-local (including 169.254.169.254), multicast, reserved, documentation, IPv4-mapped/compatible, NAT64, 6to4 or Teredo; redirects must stay on `https`. The production transport (`node:https`) also checks the addresses inside its connection `lookup`, so DNS rebinding between check and connect is refused too. Requests time out after 20 seconds (less near the deadline), bodies over 10 MB are refused, `If-None-Match`/`If-Modified-Since` are sent when the last full read is under six hours old, and a body without `BEGIN:VCALENDAR` is an error. Error messages name the host only, never the path. Tests inject the request function and the DNS lookup; there is no environment override.

`lib/ical/parse.ts` and `lib/ical/recurrence.ts` are a small RFC 5545 reader (no dependency): line unfolding, quoted parameters, text unescaping, `VEVENT` with `DTSTART`/`DTEND`/`DURATION` as `VALUE=DATE` (all-day, stored at UTC midnight like Graph's), UTC (`Z`), `TZID` or floating (the calendar's `X-WR-TIMEZONE`, else London). A `TZID` is used when it is an IANA name (Google and iCloud use those), else a common Windows name is mapped, else a path ending in an IANA name is used; anything else is read as UTC. `VTIMEZONE` definitions are not interpreted. `RRULE` supports `FREQ` `DAILY`/`WEEKLY`/`MONTHLY`/`YEARLY` with `INTERVAL`, `COUNT`, `UNTIL`, `BYDAY` (with ordinals such as `2MO` and `-1FR`), `BYMONTHDAY` (negative too), `BYMONTH`, `BYSETPOS` and `WKST`; instances are generated in the event's wall-clock time and converted in its zone, so they keep their local time across DST. Rules with other parts (`BYHOUR`, `BYWEEKNO`, hourly and so on) keep only the first instance. `RDATE` adds instances, `EXDATE` removes them, and a `RECURRENCE-ID` override replaces its instance (a cancelled override is kept cancelled). At most 1,000 instances per event and 5,000 events per calendar inside the window; hitting a cap marks the read incomplete, so only events before the window are deleted.

`lib/ical/events.ts` maps an event: id is the `UID` for a single event and `UID/<instance start>` (`20261019T080000Z`, or `20261019` for all-day) for each instance and its override, hashed when longer than 400 characters, and the same value is the iCal uid of an instance so Meetings cards don't merge a series; `SUMMARY`, `LOCATION`, `URL` (the Open event link, only when present), `STATUS:CANCELLED`, `TRANSP:TRANSPARENT` → `free`, `STATUS:TENTATIVE` → `tentative`, else `busy`; `ORGANIZER` and `ATTENDEE` (`CN`, `mailto:` or `EMAIL`, `PARTSTAT`, `CUTYPE=RESOURCE`/`ROOM` skipped); `DESCRIPTION` as the event's notes (converted to text when it is HTML); the Join link from `X-GOOGLE-CONFERENCE`, `X-MICROSOFT-SKYPETEAMSMEETINGURL`, or the first recognised meeting link in `LOCATION` then `DESCRIPTION` (see Join links below). The calendar's name is the user's name, else `X-WR-CALNAME`, else the host; its colour is `X-APPLE-CALENDAR-COLOR` (or `COLOR`) when it is hex, else a palette colour.

`lib/crm/calendar.ts` runs the sync from the CRM layout through `after()`, the `calendar` cron step (which now also runs for users with only extra accounts), Sync now in Settings › Calendars (forced), and after connecting. Each account is claimed at most once every five minutes (`integration_state` for the mailbox, `calendar_accounts.last_attempt_at` for extra accounts). Sources are routed by provider (`PROVIDERS` in `lib/crm/calendar.ts`): `microsoft` sources are skipped when the Microsoft app isn't configured, and `ics` sources read their link as above, keep a single `feed` calendar row (Use for CRM off at first), skip the request entirely when that calendar is hidden and not used for CRM, treat 304 as synced with nothing changed, and record fetch and parse errors on the account and the calendar. The etag is stored only after events were saved. For each Microsoft account it refreshes the token, saves the calendar list (removing calendars Graph no longer lists after a complete listing), then reads every calendar that is shown or used for CRM, least recently attempted first, each in its own transaction under an advisory lock. Running short of time (45 seconds by default, or the cron deadline) stops between calendars; the next run starts with the ones it skipped. A calendar Graph refuses with 403 (for example a shared calendar that needs `Calendars.Read.Shared`) keeps its own error and does not fail the account.

Notes are capped at 8,000 characters because every event's notes travel with the Calendar page; the Join link is found in the whole body first. Both are written on every sync, which re-reads the whole window, so existing events gain them on their next sync (within five minutes for Microsoft, six hours for calendar links). The assistant's calendar tools leave notes out.

The event panel shows the notes under Description as plain text (never HTML), with links and email addresses linked (`components/_ui/linked-text.tsx`, built on `textParts` in `lib/text-links.ts`, which Mail's plain-text linkify also uses). Web links open in a new tab with `rel="noopener noreferrer"`. The location is linked the same way. Long notes are clamped to eight lines with Show more.

Migration `20261022100000_multi_calendar.sql` creates a `__default__` calendar for each existing mailbox connection and moves its events onto it, so nothing is lost and no one reconnects. The first sync renames that row to the real default calendar's Graph id, keeping its settings and event rows.

Every sync upserts the events it read. After a complete read of a calendar it deletes that calendar's events that Graph no longer returned (removed, moved out of the window, or older than it), except events Orbit created (`created_by_orbit`) that start after the window, which the sync can't see yet; a partial read only drops events that ended before the window. Cancelled meetings are kept with `is_cancelled` and hidden everywhere. Missing permission: a connection made before `Calendars.Read` was added keeps working for mail. A token refresh never sends `scope`, so old connections keep refreshing. When the token response's `scope` lacks `Calendars.Read` (or `Calendars.ReadWrite`), or listing calendars answers 403 `ErrorAccessDenied`, the sync sets `scope_missing` and stops without an error; Capture (one line), Settings › Email and the Meetings card then ask to reconnect. Reconnecting clears the flag and runs a forced sync after the redirect. Write access is tracked the same way: the callback and every token refresh store the token response's `scope` in `integration_state.granted_scopes`, and `grantsCalendarWrite` reads it. No `Calendars.ReadWrite` there means `canWriteCalendar = false` and the invite dialog asks to reconnect; reads and mail are untouched. When nothing is stored yet (a connection from before this change whose access token is still valid), sending an invite first refreshes the token to learn the scopes. Orbit does not decode Graph access tokens, since Microsoft documents them as opaque to clients; it only reads `tid` from the ID token issued to Orbit itself.

Meetings card: up to five meetings that have not ended (the first shown as Next) and five that have, for the contact (`contact_ids`) or company (`company_ids`), from calendars used for CRM, with the same meeting in two calendars (same iCal uid) shown once. A Granola `meeting` activity within two hours of the start, on the same contact (or, on a company page, on the company or one of the meeting's contacts), is linked as Notes. People you've met: outside organisers and attendees of non-cancelled events in calendars used for CRM, without an active contact or a hidden entry, grouped by address with their last and next meeting, people met most recently first, then upcoming-only people, at most 25. Create contact checks the address is in the user's calendar and goes through `createContactFromAttendee`, the same path Unfiled conversations uses.

Calendar page (`app/(crm)/calendar`): `?date=YYYY-MM-DD&view=day|week`. Without `view` it shows the week on large screens and the day as an agenda list below that. The server loads the visible calendars' non-cancelled events overlapping the range (padded a day for all-day events) with contact ids for every attendee and the overlapping Granola note. Ranges and positions are London wall-clock days (`lib/calendar-view.ts`), so DST days are 23 or 25 hours; all-day events, which Graph returns at UTC midnight, sit on their calendar date. Overlapping events are packed into side-by-side columns per cluster. Toggling a calendar updates `is_visible` optimistically.

### Meeting invites

`lib/crm/invites.ts` sends, moves, cancels and answers invites for the signed-in user from any of their invite senders (see Invite senders below). Pure rules shared with the browser (durations, limits, the https-only link check, the default slot and 15-minute snapping) live in `lib/invite-rules.ts`; the Graph calls live in `lib/microsoft/calendar.ts`.

- `crm.profiles.meeting_link`: the user's https meeting link (at most 500 characters, checked in `checkMeetingLink` and by the `profiles_meeting_link_https` constraint), edited in Settings, Meeting link.
- `createInvite(actor, input)` validates before any network call: a title (at most 200 characters), `startLocal` `YYYY-MM-DDTHH:mm` in London time that must exist (times skipped when the clocks go forward are refused), be in the future and within two years, a whole-minute duration from 5 to 480, up to 50 guests (none adds a personal event, below; each a valid address; duplicates merged case-insensitively; the user's own addresses, i.e. sign-in, profile, other emails, mailbox and calendar-account addresses, dropped), notes up to 4000 characters, and `includeMeetingLink` (default: on when a link is saved; asking for it without a link is an error). It then needs a connected mailbox, refuses with "Reconnect Microsoft to send invites" when the stored scopes lack `Calendars.ReadWrite`, and posts to `POST /me/calendars/{default calendar id}/events` (or `POST /me/events` before the calendar list has synced) with `Prefer: outlook.timezone="UTC"` and: `subject`; `body` `{contentType: "HTML"}` holding the notes HTML-escaped with line breaks as `<br>` and `Join: <a href=link>link</a>`; `start` and `end` as London wall-clock times with `timeZone: "GMT Standard Time"` (the Windows name for London; times in the repeated autumn hour, and other app time zones without a mapping, are sent in UTC instead); `location.displayName` set to the link; attendees as `required`; `isOnlineMeeting: false`; `responseRequested: true`; `allowNewTimeProposals: true`; and a `transactionId`. The dialog makes one random UUID per submission and keeps it across retries of that submission; the server retries once, with the same id, after a network error or a 502, 503 or 504, and makes its own id when none is given. Graph sends the invitations itself; that can't be turned off.
- On success the returned event (UTC) is upserted into `crm.calendar_events` with `created_by_orbit = true` on the mailbox's default calendar row (creating the `__default__` row if the list hasn't synced), linked with the usual rules (`linkEvents` limited to that event), and every guest who is an active contact (the contact chosen in the dialog wins over a duplicate with the same email) gets a `meeting` activity "Invited <name> to <subject>" with the London date and time, the link and the notes, `occurred_at` now, and `metadata {source: "orbit", kind: "invite", eventId, providerEventId, startsAt}`. A failure after Graph accepted the event returns a warning instead of an error, so the user isn't tempted to send it twice.
- `cancelInvite(actor, eventId, comment?)` needs the event to be in a calendar of a connected Microsoft account (the main mailbox or a calendar account), not cancelled, not started, and organised by the user (`created_by_orbit`, or the organiser is one of their addresses). It posts `POST /me/events/{id}/cancel` with `{comment}` when there is one (the organiser-only action that notifies attendees; Delete would not), sets `is_cancelled`, and logs "Cancelled <subject>" on each guest contact. A 404 from Graph is treated as already gone; a 400 saying only the organiser can cancel is explained.
- Personal events: `createInvite` with no `attendees` (missing or an empty list; a list holding only the user's own addresses is still refused, and so are `contactIds` without attendees: "Add each guest's email address, or leave contactIds empty for a personal event.") adds an event just for the user. The calendar comes from `pickPersonalCalendar` over `personalCalendars(readInviteSenders(...))`, the Microsoft senders only (the main mailbox and calendar accounts with `can_send`); an SMTP address as `from` is refused with "<address> has no calendar…" and an unknown one is a 404, both with `field: "from"`. The default (`defaultCalendarAddress`) is `defaultInviteAddress` over those calendars with the last used one taken from the user's newest Orbit event with no attendees and no invite identity (events are stored in the calendar's workspace, so this is per user, not per workspace), then `crm.invite_sender_choices`, then the main mailbox. A calendar with a problem throws it, so it never falls back. It posts `personalDraft` (the same body as `holdDraft` without the "Invite sent from" line: no attendees, `showAs: busy`, `responseRequested: false`, the notes, and the link only when `includeMeetingLink` is true) to that calendar, and saves the row with `created_by_orbit` and no invite fields. No iTIP email, no contacts, no `linkEvents`, no activity, and `crm.invite_sender_choices` isn't written. An event is personal (`isPersonalEvent` in `lib/crm/calendar.ts`, used by move, cancel, `listCalendarItems` and the assistant's cards) when Orbit created it, it has no invite identity or uid, no linked contacts and no attendee who isn't the user. Moving one patches it without the message; cancelling one sends `DELETE /me/events/{id}` instead of `/cancel`, and neither logs anything. Guestless events made in Outlook aren't personal in this sense, so they keep the meeting rules. Sync treats them like any other event: they update from Outlook and are deleted when Outlook no longer has them, never kept as missing holds.
- `respondToInvite(actor, {eventId, response, note?, sendResponse?, proposedStartLocal?, proposedDurationMinutes?})` answers a meeting someone else organised: `accept`, `tentative` or `decline`. It needs the event in a calendar of a connected Microsoft account, answered with that account's token, not cancelled, not started, and not organised by the user (refused with "You're the organiser."). It posts `POST /me/events/{id}/accept`, `/tentativelyAccept` or `/decline` with `sendResponse` (default true), `comment` when there is a note, and, for tentative or decline, `proposedNewTime` (London wall-clock, keeping the meeting's length unless a duration is given). A note or a new time without telling the organiser is refused, as Graph would. A 400 about proposals says the organiser doesn't take them. It stores `response_status`, sets `show_as` to tentative for Maybe (busy when accepting a tentative hold), updates the user's own attendee entry, and logs "Accepted", "Tentatively accepted" or "Declined <subject>" on the organiser's contact when the organiser was told. A 404 marks the event cancelled, like move. Sync fills `response_status` from Graph's `responseStatus.response`.
- Errors: 401 asks to connect again, 403 `ErrorAccessDenied` (and similar) asks to reconnect for `Calendars.ReadWrite`, other 403s say the mailbox can't change that calendar, 429 reports Graph's `Retry-After`, a 400 on a new meeting gives Graph's reason and says to change the meeting rather than retry, and anything else is a fixed sentence per action ("Couldn't create the meeting. Try again." and so on), with Graph's text in the server log.
- `listCalendarItems` adds `createdByOrbit`, `personal` (`isPersonalEvent`) and `canCancel` (same rules as above, and at least one guest who isn't the user, or a personal event), plus `organisedByMe`, `myResponse` and `canRespond`, for the event popover. Meeting details shows Accept, Maybe and Decline, an optional note and "Let the organiser know" when `canRespond` is true (`respondToInviteAction`).

UI: `components/crm/invite-dialog.tsx` is shared by the Calendar page (New event in the header, a click on an empty grid slot, New event on an empty agenda day), the contact header (calendar button next to Call in Teams, disabled without an email) and the calendar button above an email in Mail. Its title is New event. With more than one invite sender it shows a From `NativeSelect` (the addresses), starting on `defaultFrom`; a sender with a problem shows the problem as a link to fix it and disables Send. Guests are optional: with none the select is labelled Calendar and lists `calendars` (starting on `defaultCalendar`), Add meeting link starts off, and the button reads Add to calendar instead of Send invites; adding a guest switches back to the senders, and each mode keeps its own choice. Meeting details show Move and Delete event for personal events, without the message to guests. Guests are searched with `searchContactsToFileAction`. Sending shows a notice ("Invite sent to Jane Doe") and refreshes the page. Server actions: `sendInviteAction` and `cancelInviteAction` in `app/(crm)/calendar/actions.ts`, `saveMeetingLinkAction` in `app/(crm)/settings/actions.ts`.

#### Invite senders

`lib/crm/invite-senders.ts` lists every address that can send an invite (`readInviteSenders`), in this order, one entry per address:

- The main mailbox connection (`primary`). Problems: not connected ("Connect Microsoft in Settings › Email to send invites.") or stored scopes without `Calendars.ReadWrite` ("Reconnect Microsoft to send invites.").
- Each Microsoft calendar account with `can_send`. The event goes into that account's default calendar with that account's token. Add mail (`send_account`) now asks for `Calendars.ReadWrite`; `calendar_accounts.calendar_write` records whether the token has it. `storeAccountToken` sets it from the token's scopes whenever an account token is stored (connect, calendar sync, mail sync and invite refreshes; `coalesce`, so a downgraded scope sets false and a response without scopes keeps it). Null means not known yet. Problems: disconnected ("Reconnect <address> in Settings › Calendars to send invites from it."), `calendar_write` not true ("Allow invites for <address> in Settings › Calendars first.", where Allow invites reruns Add mail, shown in Settings › Calendars whenever `calendar_write` isn't true), or no writable default calendar. The account's stored write flag stands in for its scopes, so a cached token isn't refreshed just to learn them. Allow invites keeps the `send_account` scopes: these accounts already granted `Mail.Send` and `Mail.ReadWrite`, so Microsoft only asks for the calendar permission, and asking for less could leave the stored token without the mail scopes.
- Each SMTP sending address (`crm.send_identities`, `kind: "smtp"`). It needs a hold calendar: `send_identities.hold_calendar_id` when it is still a writable calendar of the main mailbox or a usable calendar account, else the default calendar (main mailbox or calendar account) whose domain best matches (the same domain, or a shared run of at least four letters such as ridgeon in markridgeon.com). With no match the address shows "Choose a hold calendar for <address> in Settings › Email." rather than holding in the main calendar, and a hold calendar whose account hasn't allowed invites shows that account's Allow invites problem. Settings › Email, Sending addresses, has an "Invites hold time in" select per address (Best match or a calendar; `PATCH /api/mail/identities`).

Default From (`defaultInviteAddress`, per active workspace): the first sender whose home (`addressHomesInDb` in `lib/mail/routing.ts`: an explicit `crm.mail_address_homes` row, else the workspace the mail source, sending address or calendar account with mail was added in) is this workspace, explicit homes first, else the last address used for an invite in this workspace (`crm.invite_sender_choices`, written after every successful `createInvite`), else the main mailbox, else the first sender without a problem. `pickInviteSender` takes the requested `from` (an address, case-insensitive) or that default. It never falls back: an unknown address is a 404 "<address> can't send invites. Choose another From address.", and a sender with a problem throws that problem with `field: "from"`, so the dialog and the assistant say exactly what to reconnect.

`getInviteSetup` adds `senders` (`{address, kind, primary, problem, fixHref}`), `defaultFrom`, and `calendars` and `defaultCalendar` for personal events; `ownEmails` includes the SMTP addresses, so they are dropped from guest lists.

Microsoft senders work as above with the sender's token and default calendar; the saved event keeps `account_id` (or `connection_id`), so move, cancel and respond later use the same account. Orbit-created events on a calendar account are linked to contacts even when that calendar isn't used for CRM.

SMTP senders (`lib/ical/itip.ts`): Orbit first creates the hold in the hold calendar (`holdDraft`: same subject, times, location and notes, a line "Invite sent from <address> by Orbit.", no attendees so Outlook sends nothing, `showAs: busy`, `responseRequested: false`, the same `transactionId`). It then builds an iTIP email with nodemailer's `MailComposer`: `multipart/mixed` holding `multipart/alternative` (plain text and HTML in Orbit's email style: "<name> invited you to <title>." then When, Join, Organiser and Guests, then the notes) with a `text/calendar; method=REQUEST` part, plus `invite.ics`. The calendar has `METHOD:REQUEST`, one `VEVENT` with `UID:orbit-<transactionId>@<sender domain>` (stable across retries of one submission), `SEQUENCE:0`, `DTSTAMP`, UTC `DTSTART`/`DTEND`, `SUMMARY`, `DESCRIPTION` (notes and Join link), `LOCATION` and `URL` (the link), `ORGANIZER;CN=<name>:mailto:<address>`, an `ATTENDEE;CN=…;CUTYPE=INDIVIDUAL;ROLE=REQ-PARTICIPANT;PARTSTAT=NEEDS-ACTION;RSVP=TRUE` per guest, `STATUS:CONFIRMED` and `TRANSP:OPAQUE`; text is escaped and lines are folded at 75 octets. It goes out through the address's SMTP server (`defaultSmtpSender`, injectable as `smtp`) and is appended to its IMAP Sent folder when it has one. If sending fails, the hold is deleted, `send_identities.last_error` is set and the error names the address. The Orbit row is the hold (`calendar_id` and `account_id` or `connection_id` of the hold calendar) with `organizer` set to the SMTP address, the guests as attendees, `invite_identity_id`, `invite_uid`, `invite_sequence` and `invite_notes`. Calendar sync keeps `organizer`, `attendees` and `response_status` on rows with `invite_identity_id`, so the hold syncs without losing the guests. Free/busy, booking pages (`private.booking_busy`) and other people's Outlook see the hold.

Moving an SMTP invite patches the hold (without the message), or makes a new hold with `holdDraft` when it is marked missing or the patch gets a 404 (the row keeps its id and gets the new `provider_event_id`; it is never marked cancelled), then sends a `REQUEST` with `SEQUENCE + 1`, the new times, the original notes and an "Updated invitation" email naming the old time and the message; if the email fails the hold is moved back. Cancelling sends a `CANCEL` (`STATUS:CANCELLED`, attendees `PARTSTAT=DECLINED`, `SEQUENCE + 1`) and then deletes the hold (`DELETE /me/events/{id}`; if that fails the guests were still told and a warning says to delete the hold in Outlook). `invite_sequence` is bumped in the database before each `REQUEST` or `CANCEL` is sent and put back if the send fails. Calendar sync never deletes a row with `invite_identity_id` or `invite_uid` whose hold has gone from Outlook: it sets `invite_hold_missing` instead (cleared when the hold syncs again), cancel skips deleting a missing hold, and move recreates it. A row whose sending address was removed (`invite_uid` set, `invite_identity_id` null) can't be moved or cancelled, and `removeIdentity` refuses while the address has upcoming invites that aren't cancelled ("Cancel the 2 upcoming meetings sent from <address> first…"). Removing an address or disconnecting a calendar account also clears it from `booking_pages.invite_sender` and `crm.invite_sender_choices`.

Replies (`lib/mail/invite-replies.ts`): the mail cron reads, for each SMTP address with an invite that hasn't ended, the address's IMAP inbox (Neo has one) with IMAP timeouts set from the deadline. It resumes after `send_identities.reply_last_uid` while `reply_uid_validity` matches the mailbox's UIDVALIDITY (300 messages a run); the first run, or a run after UIDVALIDITY changes, reads from the day before the first open invite (at most 14 days back, the last 300 messages). It downloads `text/calendar` and `application/ics` parts (at most 256 KB each, `maxBytes`) with the message's From and Sender, and applies `METHOD:REPLY` ones (`readItipReply`) whose `UID` matches `invite_uid` and whose `ORGANIZER` is the sending address, taking only the `ATTENDEE` entries whose address is the message's From or Sender, so a forged reply can't answer for someone else. Replies to an older `SEQUENCE` are ignored and a reply without one counts as current: `ACCEPTED`, `TENTATIVE` and `DECLINED` become the guest's `accepted`, `tentativelyAccepted` and `declined`. Without an IMAP server, responses aren't read.

Booking pages send from `booking_pages.invite_sender`. Null means the booking default (`bookingDefaultSender`): the address homed in the booking page's workspace, else the main mailbox, else the same fallback as the dialog. Choosing the default stores null. Invites from in Settings › Booking page shows when there is more than one sender and starts on the default; a saved address that can no longer send is dropped from the form with a warning. A booking whose saved address isn't a sender any more fails with "<address> can't send invites any more. Choose who booking invites come from in Settings › Booking page." as the page's last error.

Migration `20270104100000_invite_senders.sql` adds `calendar_events.invite_identity_id`, `invite_uid`, `invite_sequence` and `invite_notes`, `send_identities.hold_calendar_id`, `calendar_events.invite_hold_missing` (and update grants on it and `provider_event_id`), `send_identities.reply_uid_validity` and `reply_last_uid`, `booking_pages.invite_sender`, `calendar_accounts.calendar_write`, and the owner-only `crm.invite_sender_choices` (one row per user and workspace, RLS forced). It can be run more than once.

Migration `20261210110000_invite_response.sql` adds `calendar_events.response_status`. Migration `20261024100000_meeting_invites.sql` adds `profiles.meeting_link`, `calendar_events.created_by_orbit` and `integration_state.granted_scopes`. It doesn't touch `crm.mailbox_connections`, `crm.email_messages` or `private.schema_migrations`, so it runs in the hosted SQL editor as `postgres`, and it can be run more than once.

### Booking page

A public scheduling page at `/book/[slug]` (`app/book/[slug]`, outside the `(crm)` group, so no CRM chrome). Each person has at most one page per workspace (unique on `user_id, workspace_id`; the slug stays unique across Orbit, checked by `private.booking_slug_taken(slug, user, workspace)`). Settings, the assistant's links, `[[times]]` and the cold email playbook read the page for the current workspace and give no link when it has none. Settings › Booking page edits only that page; there is no copying from another workspace's page, and a workspace without one starts from the defaults. `proxy.ts` lets `/book` and `/book/*` through without a session; `/api/*` was already public at the proxy and each route authenticates itself.

| Table | What it holds |
| --- | --- |
| `crm.booking_pages` | One row per user (`user_id` unique): `slug` (unique, `^[a-z0-9]+(-[a-z0-9]+)*$`, 3 to 40 characters, reserved words refused by `booking_pages_slug_reserved`, kept in step with `RESERVED_SLUGS` in `lib/booking/rules.ts` by a test), `enabled` (default off), `title` (null means "Book a call with <first name>"), `intro` (up to 500), `duration_minutes` (15, 20, 30, 45, 60), `buffer_minutes` (0 to 60), `min_notice_minutes` (0 to 14 days), `horizon_days` (1 to 90), `weekly_hours` (`{"mon": [{"start": "09:00", "end": "17:30"}], …}`, checked by `private.booking_hours_valid`), `time_zone` (Europe/London), `background_video_url` (https, up to 1000), `background_poster` and `avatar` (bytea up to 1 MB, JPEG, PNG or WebP, with their mime types), `last_error` and `last_error_at` (why the last booking failed, shown in Settings), and timestamps. Owner-only RLS for `authenticated` (`private.session_user_id()` and the workspace check); agents and anonymous users have no access. |

Public access only goes through security-definer functions executable by `crm_app` alone: `private.booking_page_public(slug)` returns the page fields a visitor needs (no email, meeting link, workspace or image bytes; `meeting_kind` is just `whereby`, `link` or null, and `version` is a hash of `updated_at` for image URLs) for enabled pages only; `private.booking_page_image(slug, kind)` returns the avatar or poster bytes; `private.booking_busy(user_id, from, to)` returns busy intervals from `crm.calendar_events` across all the user's calendars (not cancelled, `show_as` not `free`, at most a 100-day window) and only for a user with an enabled page; `private.booking_page_owner(slug)` returns the owner's membership row, from which `memberActor` builds the background actor that does the booking; `private.booking_slug_taken(slug, user_id)` backs the live availability check in Settings. `lib/booking/pages.ts` wraps them and the owner's settings reads and writes; `publicView` is the only shape sent to the browser.

Slots (`lib/booking/slots.ts`, pure, also used by the browser for month maths): for each local date in the window, each weekly range, every `duration` minutes for 15, 20 and 30-minute meetings and every 30 minutes for longer ones, wall times are converted with `zonedTimeToDate`; times that don't exist when the clocks go forward are skipped, a range ending at `24:00` ends at the next midnight, and a slot must end by the range's end. A slot is offered when it starts at or after now plus the minimum notice, before the start of the local day `horizon_days + 1` days from today, and doesn't come within `buffer` minutes of a busy interval on either side. Results are UTC instants. `GET /api/book/[slug]/slots?month=YYYY-MM&tz=Area/City` returns `{month, timeZone, first, last, days}` with the slots of that month grouped by the visitor's local date (an unknown zone falls back to the page's); the panel defaults `tz` to the browser zone and offers every `Intl.supportedValuesOf("timeZone")`.

Booking (`POST /api/book/[slug]`, `bookSlot` in `lib/booking/book.ts`): rate limits through `private.consume_rate_limit` with HMAC-hashed keys (`booking:slots:<ip>` 10 a minute, `booking:attempts:<ip>` 5 an hour, `booking:email:<email>` 3 a day; the IP is the first `X-Forwarded-For` entry, which Vercel sets); a filled hidden `website` field is refused; name (1 to 120), email (`canonicalEmail`) and note (up to 1000) are validated; the start must be one of the generated slots against stored busy data. It then takes a per-owner session advisory lock (`pg_advisory_lock(hashtextextended('booking:<user_id>', 0))`) on a dedicated connection (`openClient`, so a waiting request doesn't hold a pool slot), re-reads busy data, opens the owner's sender (`openInviteSender` with the page's Invites from address, or the booking default: `Calendars.ReadWrite`, fresh token), refuses the organiser's own addresses, and reads Graph `calendarView` of the sender's calendar (the hold calendar for an SMTP sender) from start minus buffer to end plus buffer; a Graph failure there falls back to stored data. A clash is a 409 "That time was just taken. Pick another.". The meeting goes through `sendInvite` (the second half of `createInvite`) as the owner: subject "<owner first name> × <visitor name>", body "Note from <name>:" plus the note and the Join link, location the meeting link, the visitor as the only required attendee, in the page's time zone. With `createContacts` it calls `createContactFromAttendeeInDb` in a savepoint (internal addresses are skipped), saves the event with `created_by_orbit`, links it, and logs a `meeting` activity "Booked via your booking page" with `metadata {source: "booking", kind: "booking", eventId, providerEventId, startsAt, page}`, all before the lock is released. Not connected, missing write scope, or a Graph error are logged in `booking_pages.last_error` and shown to the visitor only as a 503 "Booking is unavailable right now"; a successful booking clears the error. After the booking is saved, `alertOwner` (in `after()`, inline outside a request) adds a `booking` notification linking to the contact and sends the owner a plain-text "New booking" email from their own mailbox to itself through `sendOwnMail`; either failing is logged and never affects the booking.

UI: `components/booking/booking-screen.tsx` (panel, slots, form, confirmation), `booking-calendar.tsx` (month grid with arrow-key, Home and End navigation), `booking-background.tsx` (fixed `<video autoplay muted loop playsinline>` with the poster, faded in once playing and dropped on error or for `prefers-reduced-motion`, otherwise a CSS-only aurora whose keyframes live in `globals.css` and stop under reduced motion), and `components/crm/booking-page-settings.tsx`. Images are served by `GET /api/book/[slug]/image/[kind]` (public, cached, `nosniff`) and `/api/booking-page/image` (owner: GET, multipart POST, DELETE; same-origin check; type from the file's magic bytes). Videos are only stored as links: a Vercel function response is capped at 4.5 MB and Postgres is the wrong place for large media. The page sets `robots: noindex` on top of the site-wide `robots.txt`.

Migration `20261026100000_booking_pages.sql` creates the table, policies and functions. It doesn't touch `crm.mailbox_connections`, `crm.email_messages` or `private.schema_migrations`, re-creates `private.session_user_id()`, and can be run more than once.

### ClickUp

`lib/clickup.ts` is the API v2 client (personal token in `Authorization` without a scheme, `CLICKUP_API_TOKEN`, base `CLICKUP_API_BASE_URL`): user, workspaces, the space › folder › list hierarchy (cached five minutes per process), list statuses and custom fields, task create, update and get, the filtered workspace task search, custom field values, and webhooks. On 429 it waits until `X-RateLimit-Reset` (at most 15 seconds) only when the request deadline leaves room, otherwise it gives up for this run. `lib/crm/clickup.ts` holds the sync.

| Column | What it holds |
| --- | --- |
| `crm.tasks.clickup_task_id` | The linked ClickUp task, unique per workspace when set. |
| `crm.tasks.clickup_list_id` | The list the task lives in. Set without a task id, it means "create this task in ClickUp" and the sync keeps trying until it succeeds. |
| `crm.tasks.clickup_url`, `clickup_synced_at`, `clickup_error` | The ClickUp link, the last successful exchange, and the last error shown on the Orbit task. |
| `crm.tasks.clickup_sync` | The last values both sides agreed on (`title`, `dueAt`, `done`), ClickUp's `date_updated` at that point, when Orbit last wrote to ClickUp (`pushedAt`), and a short-lived claim while the task is being created (`creatingAt`). |
| `crm.integration_state` (`source = 'clickup'`) | One row per Orbit workspace, so each workspace connects and chooses its own lists with the one token: the member it runs as, the ClickUp workspace (`team_id`), the token owner's ClickUp user id, the default list, the watched lists, the last list used in a form, the list names for the pickers (`list_choices`), the webhook id, its secret (encrypted with `APP_SECRET`) and scope (`team`, `space:<id>`, or `list:<id>`), the last sync, and the last error. |
| `crm.webhook_receipts` (`source = 'clickup'`) | `webhook_id:history item ids` (or `webhook_id:event:task_id` for deletions) seen in the last day. |

Merging is three-way against `clickup_sync`. A field Orbit changed since the last agreement is sent to ClickUp; a field ClickUp changed is written to the Orbit task through `updateTaskInDb`, with the audit source `clickup`; when both changed, the later of the task's `updated_at` and ClickUp's `date_updated` wins. A ClickUp task whose `date_updated` is not newer than the stored one is skipped, so Orbit's own writes coming back through the poll or the webhook change nothing, and a webhook event dated within 15 seconds of Orbit's last write to that task is dropped without fetching it. Imported tasks are created with `createTaskInDb`; while an Orbit-created task is being sent (`creatingAt` within two minutes), a ClickUp task in the same list with the same title is not imported, so the webhook for Orbit's own create cannot make a copy. Due dates are London time: midnight means a date without a time (`due_date_time: false`); from ClickUp, `due_date_time: false`, or a time of exactly 00:00 or 04:00 London when the flag is missing, becomes midnight. Done means a status of type `done` or `closed`.

Each sync claims the row with a five-minute gap (the cron and Sync force it), lists tasks in the watched lists and in lists that hold linked tasks, updated since the last complete sync less five minutes (14 days the first time), 100 a page, closed tasks and subtasks included, then sends up to 20 pending or changed tasks, then re-reads up to five linked open tasks not checked for six hours, archiving any whose ClickUp task is gone. Running out of time keeps `last_synced_at` where it was. `private.clickup_webhook_targets()` returns the stored webhook secrets for the public route, `/api/clickup/webhook`; it is a security-definer function executable only by `crm_app`.

Workspaces: the token (`CLICKUP_API_TOKEN`) is shared, while the ClickUp workspace, default list, watched lists, webhook and sync state are per Orbit workspace, so Eclipse tasks and Mark Ridgeon tasks go to different lists. A push (`pushClickUpTask`, `sendTaskToDefaultList`) runs as the person's actor for the task's own workspace (`taskWorkspaceActor`) and reads the task only within it, so a follow-up created in another workspace is sent to that workspace's list. Each workspace registers its webhook at `/api/clickup/webhook?workspace=<id>` and only replaces its own, so turning on instant sync in one workspace leaves the other's in place. Saving lists that another of the person's workspaces also watches or uses as its default says so (`sharedLists`), because tasks in a list both watch sync into both. The settings card names the workspace the lists are for.

### Enrichment

### AI fields

`supabase/migrations/20261231100000_ai_fields.sql` adds five tables, all with forced row-level security:

`lib/ai-fields/fields.ts` saves definitions (`saveAiField` checks the role, cleans options, which can't contain `|` or be `?`, and sets `fills_size` from `looksLikeStaff` unless given; changing the type or options deletes the web answers and keeps hand-set answers that still fit, matching options by case, and clears their kept web answer; changing the question makes the web answers due and drops their pending Task runs; yes or no and pick from list fields can ask at most 200 Decisions questions about a company between them, one per option for pick several), works out scopes (`scopeSql`: active, with a domain or website, and either the saved view's filters through `companyWhere`, or `CURRENT_FIT >= 2.5`; a deleted or unreadable view matches no companies and `scopeProblem` puts the reason on the field), counts coverage (`aiFieldStats`), scope sizes for the dialog and this month's spend. `lib/ai-fields/answers.ts` reads answers for a company or cell, sets manual answers (keeping the web answer in `web_answer`), restores the web answer, and records changes. `lib/ai-fields/cells.ts` gives `listCompanies` (`aiFields: true`) and `getCompaniesByIds` a cell per field: answered, unknown, checking (in scope and not yet answered) or outside.

The runner (`lib/ai-fields/runner.ts`, `runAiFields`) runs in the 10 minute sync as the `ai_fields` step (once per workspace, 12 seconds), after Save and fill, Check all again, Keep up to date and Check again (`kickAiFields` in `after()`, 50 seconds, polling Task runs every 4 seconds), and for a new company after enrichment and web checks (`autoAiFields`). It needs `PARALLEL_API_KEY`. Each pass first collects pending Task runs: `private.ai_field_run_lease` takes the run's rows for 90 seconds so only one pass reads a result, then `GET /v1/tasks/runs/{id}` and `GET /v1/tasks/runs/{id}/result?timeout=2` when completed (a run still going is released for the next pass; failed or cancelled runs are retried in 6 hours, runs older than 3 hours are given up; `private.ai_field_save` only writes when the row still carries that run). It stops for the month at $100 of spend, then claims due pairs: a company in scope with no answer row, or a non-manual row whose `next_check_at` has passed, not claimed in the last 3 minutes and without a pending run. `private.ai_field_claim` inserts or claims the row only under the same conditions, so two runners never ask twice; Check again, Check all again and question edits only make rows due and never clear a live claim. Up to 40 companies a pass (`COMPANIES_PER_RUN`) and 25 new Task runs, five at a time after the first. Parallel answering 401, 402, 403 or 429 (`stopsParallel`, from the status on `ParallelError`) stops the pass after that request and puts the message on the fields; a field whose every check in a pass failed gets that error, and a later clean pass clears it. Every request is bounded by the pass deadline, and no Task run starts with less than 6 seconds left. Per company, the yes or no and pick from list fields go into `decide()` requests of up to 100 questions each (`decisionBatches`): `noul` for yes or no (Yes at `TAG_THRESHOLD` 0.85, No at 0.15 or less), `choice` with an `unknown` option for pick one (70%), and one `noul` per option for pick several (each at 70%). Number and short text fields go into one `POST /v1/tasks/runs` with `processor: "base"` and a JSON output schema with one nullable property per field (`f_<field id without dashes>`); the run id is stored on the rows with `private.ai_field_run_start`. Results with `confidence: "low"` are Unknown, and number answers are read loosely (`looseNumber`: "about 1,200" is 1200, "10-20" is 15, "1.2 million" is 1200000; no digits is Unknown). Only the company's name, domain and website are sent. The reason is the source sentence that shares the most words with the question and answer (no model call); sources are the request's citations (Decisions) or the field's basis citations (Task API), six at most. `private.ai_field_save` writes an answer only when the row isn't manual and returns the old and new values; the next check is 30 days (monthly), 7 days (weekly) or never (only when asked). Failures keep the old answer, record the error and retry in 6 hours. `private.ai_field_note` records the last run and error on the field for the settings page.

A change of shown value (including the first answer) writes a `company.ai_field_changed` audit event on the company with `{fields: ["ai:<field id>"], before, after, aiField: {id, label}}` (values as shown, null for Unknown), source `parallel` from the background or operation `ai_field_manual` by hand. `eventTriggerTypes` maps it to `field_changed`, so a workflow trigger with field `ai:<field id>` (listed under AI fields in the trigger editor) runs with `{{change.from}}` and `{{change.to}}`. Background changes use `BACKGROUND_PROVENANCE` with `automatic: true`: `enqueueWorkflowEvent` stores them with no actor and `automatic` in the event data, and the engine treats them as nobody's change, so a trigger with Only when it's mine never runs for a web answer (or the Size it fills), whichever member's sync found it. AI field changes are left out of the assistant's recent changes (they can't be undone there). `crm_agent` reads `company_views` and `ai_field_spend` through `request_workspace_id()` policies, so a company an agent adds is checked as that agent. With `fills_size`, a number answer fills an empty Size (1-10, 11-50, 51-200, 201-1000, 1000+) through `updateCompany`.

Filters and sorting: `companyQueryFromSearchParams` reads `ai.<field id>=is:yes|no|unknown`, `range:5..30` (either end optional, `|?` keeps Unknown), `has:<text>` and `any:SEO|Content` (`|?` keeps Unknown), and `sort=ai.<field id>` with `order`. `companyWhere` (`lib/crm/company-query.ts`) is the one WHERE builder for the list, its count, saved view scopes and the REST API; AI filters become `exists` subqueries on answered rows (a filter on a field that no longer exists is ignored, and Companies leaves it out of the Filters count), and the AI sort orders by the value with nulls last. A saved view is current while the URL's normalised parameters match it; once they differ the View menu shows Edited with Update and Save as new view for owners and admins, and drops `view` from the URL for members.

## Assistant and AI accounts

### Assistant

`lib/assistant/chat.ts` runs a turn, `lib/assistant/gateway.ts` calls the model, `lib/assistant/tools.ts` holds the tool registry (every tool is listed in `docs/assistant.md`), and `lib/assistant/prompt.ts` builds the system prompt. `POST /api/assistant` resolves the user, checks `LLM_API_KEY`, takes the rate limit (`private.consume_rate_limit('assistant:<user>', 60, 600)`) and streams newline-delimited JSON with a `ping` every 10 seconds. The route has `maxDuration` 300 and gives a turn a 285-second deadline. Event types are `conversation`, `user`, `tool` (`running` or `done`), `message`, `actions`, `waiting` (an Orbit Agent turn that outlives the request), `error`, `ping` and `done`. A body with `conversationId` and `decisions` (`[{id, approve}]`, 1 to 100) decides on actions; any other body sends a message.

`crm.assistant_conversations` holds one row per chat (title, model, reasoning `low` to `max`, `web_search`, `archived_at`). `unreadBrief` (`lib/learning/nightly.ts`) returns the latest brief from the last 36 hours that isn't dismissed or read; the CRM layout passes it to the dock, which shows a dot on the Ask Orbit bar. Opening the dock while it is set calls `openBrief` (`lib/assistant/chat.ts`), which locks the brief row, reuses its live conversation if it has one, or creates a conversation titled `briefTitle(day)` ("Brief, Tue 4 Nov") with the dock's model settings and the brief as its first `assistant` message, then sets `read_at` and `conversation_id`. The brief message is stored with `model` `orbit-brief` (`BRIEF_MESSAGE_MODEL`): the nightly personal learner skips those messages so it never learns from Orbit's own brief as if the user said it, and a turn in a conversation that has one doesn't tell the model a brief is ready (`briefReady: false`). `history` puts a short user note before a conversation that starts with an assistant message, so roles alternate and the model knows the brief came from Orbit. The dock only opens the brief by itself when it has no chat on screen (`opensBriefOnExpand` in `lib/assistant/brief-dock.ts`); otherwise the header shows Brief. It remembers which brief it handled by id and `created_at`, so a brief rebuilt while the tab is open shows the dot again. `crm.assistant_messages` holds rows in `seq` order with `role` (`user`, `assistant`, `tool`), `content`, `tool_calls`, `tool_call_id`, `tool_name`, `actions` (the proposed changes and their status), `sources`, `model`, `usage`, `provider_state` and `steering` (`waiting` for a message sent while a turn ran and not yet read, `folded` once a running turn took it in; null otherwise). Conversations carry `turn_runner` and `turn_until`, the lease that keeps one turn at a time per conversation (see Steering in `docs/assistant.md`); writing them doesn't bump `updated_at`. `private.assistant_waiting_conversations` (security definer, `crm_app` only) lists conversations whose waiting messages nothing is answering, for the cron sweep. Both tables force row-level security with one `for all` policy to `authenticated` requiring `user_id = private.session_user_id()` in a workspace the user belongs to; `crm_agent` and `anon` get no grants. Updates are limited to the title, model, reasoning, web search, archive, `stopped_at` (set by Stop), the turn lease and timestamp on conversations, and to content, actions, `turn_context`, `steering` and `seq` (moved when a waiting message is picked up) on messages. Deleting a conversation cascades to its messages and Orbit Agent jobs. `crm.chat_files` holds the files attached in the assistant (owner-only, forced row-level security: name, content type, size up to 25 MB, the conversation and message once sent, and the extracted text once read); `assistant_messages.files` keeps each user message's file list for the chat and the model. The bytes live in the `email-attachments` bucket under `chat/<id>`. `deleteConversation` deletes the conversation's files and their objects; `private.claim_stale_chat_files` lets the cron remove files that are on no message and older than a day.

`sendMessage` trims the message (200,000 characters at most), normalises the model and reasoning with `settingsFor` (an unknown model becomes `claude-sonnet-5-5`; the reasoning drops to the highest level the model supports), refuses a ChatGPT or Claude account model whose account isn't connected, creates or updates the conversation, marks approved actions that have been `running` for over six minutes as `failed`, declines pending actions by writing `{declined: true}` tool results, inserts the user message and runs the loop. Each round rebuilds the history from stored messages (mention tokens expanded, tool calls without a stored result left out), calls `complete` with a timeout of the smaller of 240 seconds and the time left less five, stores the assistant message, runs read tools in parallel with `runTool` and stores each result as a `tool` message. Write calls are saved on that message as `pending` actions, emitted, and end the turn. The loop stops after 40 rounds, or writes a "carry on" message when less than 15 seconds are left or the turn has read more than the history budget. The history keeps old tool results to 100,000 characters and the current turn's to 400,000, and drops the earliest messages past 900,000 characters (about 225,000 tokens, under the smallest model's window). The system prompt stays the same from turn to turn for a person in a workspace; the time the message was sent, the Web switch, the brief, the page and the learned notes go in an `<orbit_context>` block at the end of the latest user message, and each round sends the core tools plus the areas loaded with `find_tools` (see `docs/assistant.md`, What the model gets and Tools per call). While a turn runs, `runLoop` checks every three seconds whether `stopped_at` changed or a newer user message arrived, and if so aborts the model call and stops. A closed connection alone doesn't stop the turn, so a phone that drops off still gets its answer.

`decideActions` checks every decided action belongs to one message, then claims them in one transaction (`select ... for update`, still `pending` or it refuses with "already been handled"), so a double submit runs nothing twice. It runs approved actions in order (`running`, then `done` or `failed` with the error), writes declined results, and once nothing on that message is pending runs the loop again so the model can report. `runTool` returns `{error}` instead of throwing, drops nulls the model sends for fields that don't accept them, marks results that carry outside text with a notice, and stops read tools after 90 seconds (approved actions always run to the end; Eclipse actions get an idempotency key derived from the tool call id). Write tools pass `provenance {operation, source: "assistant"}`. Action cards come from each tool's `describe`, with ids resolved to names by `recordNames` in one union query over companies, contacts, tasks, opportunities, stages, boards, workflows and workspace members (ids are collected from every string in the arguments, nested ones included). Workflow tools take a definition through `definitionFromInput` in `lib/workflows/definition.ts`: nested `steps` are converted with the legacy converter, `nodes` without positions are laid out with `autoLayout`, and both are checked with `graphProblem`.

The assistant reads and changes the current workspace. For someone in several workspaces, the main read tools (`WORKSPACE_READ_TOOLS`: `get_overview`, `search_records`, `list_companies`, `get_company`, `list_contacts`, `get_contact`, `list_tasks`, `get_pipeline`, `get_deal_history`, `pipeline_report`, `stalled_deals`, `list_boards`, `get_board`, `list_opportunities`, `list_activities`, `list_quiet_relationships`, `list_tags`, `search_knowledge`) take an optional `workspace` (`all`, or a name or id among the person's own memberships), and `runTool` runs them as the person's actor for that workspace (`workspaceActors`); only results from another workspace, or from `all`, are labelled with their workspace, and the current workspace's result stays as it was. A workspace they aren't in is refused, and any other tool given a `workspace` other than the current one returns an error naming the tools that support it. `crossWorkspaceRefusal` refuses a write that names another workspace (or `all`) or carries the id of a company, person, task, deal, activity, board, workflow or workflow run in one, telling the user to switch first; it runs when the call is proposed (so no card is shown) and again when an approved action runs. The system prompt's Workspaces section lists the workspaces. The MCP server and the REST API stay scoped to the token's workspace.

`complete` routes by the model's `source`. `orbit` posts to `<LLM_API_BASE_URL>/chat/completions` (or, for the Claude models when `ANTHROPIC_API_KEY` is set or `LLM_CLAUDE_MESSAGES` is `on`, to the Messages API, see `docs/assistant.md`) with the tool definitions, `tool_choice: "auto"`, `reasoning_effort`, `max_tokens` from `outputTokens` (16,000 to 96,000 by reasoning level, within the model's limit) and, with web search on, `web_search_options {search_context_size: "medium"}`; Gemini tool schemas are simplified (non-string enums move into the description; `minimum`, `maximum` and `additionalProperties` are dropped). Sources come from `url_citation` annotations or a top-level `citations` list, capped at 30. `chatgpt` goes to `lib/assistant/providers/chatgpt.ts`. `claude` never reaches `complete`: `runLoop` hands it to Orbit Agent.

Mentions (`lib/mentions.ts`) are stored as `@[Name](kind:uuid)` with kind `contact`, `company`, `task` or `opportunity`; names are capped at 200 characters with brackets and line breaks replaced by spaces. `expandMentions` turns each token into `Name [person id <uuid>]` before the model sees it, and titles use `plainMentions` (`@Name`). `searchMentionsAction` in `app/(crm)/search.ts` feeds the picker.

`GET /api/assistant/probe` (Bearer `CRON_SECRET`) asks each model, or the one in `?model=`, to call a test tool and use its result. `web=1` turns web search on, `full=1` adds the full tool list, `reasoning=` sets the level (default `low`), and `search=1` runs a web search check instead. It runs without a user, so account models fail it.

### Brand

`crm.workspace_brands` holds one row per workspace: `website`, `what_you_sell`, `tone` (how the business writes, added to each person's own How you write, never instead of it), `playbook` (the cold email playbook) and `outreach_brief` (what may be said about the product) with `playbook_updated_at`, and `former_names` (names the business used before, which the cold email checks treat as its own). `eclipse_tools` is no longer read; it stays only so code from before 9 Jan 2027 keeps working during a deploy, and can be dropped later. Ideal customer is not a column: it is `crm.enrichment_settings.icp_text`, the same text web checks score companies against, edited as Ideal customer in Settings › Brand, and saving it updates `icp_hash`. Nothing copies a profile between workspaces. The migration seeded the workspaces that existed before 5 Nov 2026 with the text that used to be written into the code (`lib/assistant/eclipse.ts` and `lib/assistant/cold-email.ts`), with Eclipse tools on; new workspaces start empty. The 9 Jan 2027 migration then moved Eclipse's own sales rules out of the code and into that workspace's profile (the one with `eclipse_tools` on): Cntent as its former name, the "piece" rule added to its tone, its playbook pointed at its Eclipse client instead of `eclipse_articles`, and its market topics added to its watchlist, each only when missing.

The assistant's system prompt, its tool list and the Orbit Agent's tools, the cold email tools, prepared replies and nudges (`brandWriterNote`) and overnight learning and the brief all read the current workspace's brand. ### Knowledge

`crm.knowledge_items` holds one row per document, link, video, episode, call transcript or email attachment: `scope` (`company` with a `company_id`, or `eclipse`), `kind` (`file`, `link`, `youtube`, `podcast`, `transcript`, `attachment`), title, `source_url`, `source_ref` (unique per workspace among live rows, `call:<insight id>` or `attachment:<hash>:<target>`), `file_path` in the private `knowledge` Storage bucket, status (`pending`, `indexing`, `ready`, `failed`), error, summary, the extracted `content` (up to 2,000,000 characters), counts and `archived_at`. `crm.knowledge_chunks` holds the passages (about 1,200 characters with 150 of overlap) with an `extensions.vector(1536)` embedding (HNSW, cosine) and a generated `tsvector` (GIN). Both force row-level security with one `for all` policy to `authenticated` for workspace members; items can't be deleted, only archived, and `crm_agent` and `anon` get no grants, so the agent API and MCP server don't see Knowledge.

`lib/knowledge/store.ts` adds, lists, renames, archives and reads items in 100,000 character windows. `lib/knowledge/indexing.ts` claims an item (the claim's `updated_at` is the token both the success and failure updates check), extracts text (`lib/knowledge/media.ts` for YouTube, podcasts and audio, `readWebPage` for links, `readAttachmentText` for files), chunks, embeds through `embedTexts`, summarises with `completeJson` and swaps the chunks in one transaction. `lib/knowledge/background.ts` runs indexing in `after()` with a 280 second budget; items left `pending` or `indexing` are picked up again when they are next listed. `searchKnowledge` resolves the ready items in scope, takes the nearest passages from the chunk table alone (three times the requested number, at least 60, so the HNSW index is used, with `hnsw.iterative_scan`), drops those further than 0.75, and fuses them with as many keyword matches by reciprocal rank. The assistant asks for up to 100 passages. Call summaries add their transcript when they finish (`lib/knowledge/calls.ts`), and the company page backfills up to 25 older ones in `after()`. Mail attachments are only added through `addMailAttachmentToKnowledge`, on request. `lib/knowledge/site.ts` maps a site from its sitemaps (indexes and gzip included) or by following links (six at a time, up to 400 pages fetched), lists up to 5,000 pages, and `addKnowledgePages` adds the chosen ones as links; while the panel is open, `resumeStale` keeps two runners working through pending pages. Adding, renaming and removing record `knowledge.added`, `knowledge.updated` and `knowledge.removed`.

### AI accounts

`crm.ai_accounts` has one row per user and provider (`unique (user_id, provider)`, provider `chatgpt` only): `status` (`pending` or `connected`), the account email as `label`, the ChatGPT `account_id`, encrypted `access_token` and `refresh_token`, `expires_at`, the encrypted device sign-in state in `pending`, and `last_error`. It uses the same owner-only policy as the assistant tables.

ChatGPT sign-in (`lib/ai-accounts/oauth.ts`) uses OpenAI's device flow on `auth.openai.com` with the Codex client id and `originator: orbit`. `startChatGptLogin` requests a user code and stores `{deviceAuthId, userCode, intervalMs, deadlineAt}` (15 minutes) encrypted in `pending`. The Settings card calls `pollChatGptLogin` at the given interval (at least two seconds): 403 or 404 means still waiting; on success it swaps the authorisation code and verifier for tokens at `/oauth/token` with redirect `https://auth.openai.com/deviceauth/callback`. The `chatgpt_account_id` claim is required and `email` becomes the label. `aiAccess` locks the row, returns the decrypted token when more than two minutes are left, otherwise refreshes and saves, or writes `last_error` and throws. `complete` retries once with a forced refresh after a 401.

The ChatGPT provider builds a Responses API request: the system prompt as `instructions`, the chat as input items, tools with `strict: false` (plus `{type: "web_search"}` when on), `parallel_tool_calls`, `reasoning {effort, summary: "auto"}`, `include: ["reasoning.encrypted_content"]`, `store: false` and `stream: true`. Output items are saved as `provider_state` and replayed on later rounds of the same model so encrypted reasoning carries over.

### Orbit Agent

Three owner-only tables back it:

- `crm.ai_companions`: one row per paired Mac, with name, `token_hash` (unique), `last_seen_at` and `revoked_at`. `authenticated` can read every column except `token_hash` and can only update `revoked_at`.
- `crm.ai_companion_pairings`: one-time codes (`code_hash`, `expires_at`, `used_at`).
- `crm.ai_companion_jobs`: `conversation_id`, the claiming `companion_id`, `status` (`queued`, `running`, `done`, `failed`, `cancelled`), `request`, `events` (tool progress), `result` (saved message ids), `error`, `claimed_at`, `finished_at`.

Pairing: `createPairingCode` deletes the user's used and expired codes and stores the SHA-256 of a new eight-character code (`XXXX-XXXX`, no `I`, `O`, `0` or `1`) with a 10-minute expiry. `POST /api/companion/pair` makes a token `oa_<32 random bytes, base64url>` and calls `private.redeem_companion_pairing(code_hash, token_hash, name)`, which marks the code used only if it is unused and unexpired and inserts the companion. The plaintext token is returned once and never stored. Both functions refuse callers other than `crm_app` or `postgres`.

On every agent request, `requireCompanion` hashes the bearer token and calls `private.authenticate_companion`, which returns the companion only when it isn't revoked and its user is still a workspace member, and updates `last_seen_at` at most every five seconds. The user's role and scopes are loaded fresh, and the request runs as that user through `withActor`. A Mac counts as online when seen in the last 75 seconds. Settings › Remove sets `revoked_at`, so the next request gets 401 and the agent deletes its config and exits. `private.team_remove` revokes a removed member's companions.

A Claude turn:

1. **Enqueue.** `runCompanionTurn` checks a Mac is online, cancels any queued or running job for the conversation, and inserts a job with the model's API name, `effort`, `webSearch`, the system prompt, the tool list with a `write` flag, and the prompt from `lib/companion/transcript.ts` (the chat as `<user>`, `<assistant>`, `<tool_call>` and `<tool_result>` blocks with closing tags escaped; tool results cut to 100,000 characters for earlier turns and 400,000 for the current one; oldest blocks dropped past 900,000 characters).
2. **Claim.** The agent long-polls `GET /api/companion/next`, which cancels the user's queued jobs older than 20 minutes, writing a reply into each chat, then claims the oldest queued job with `for update skip locked`. It retries every 1.5 seconds for up to 25 seconds. The agent backs off from one second, doubling up to 60, after an error.
3. **Run.** `companion/src/turn.ts` starts the Claude Agent SDK `query` with Orbit's tools as an in-process MCP server named `orbit`, `tools` limited to `WebSearch` when web search is on, `strictMcpConfig`, `settingSources: []`, `permissionMode: "dontAsk"`, `persistSession: false`, `maxTurns` 40, working folder `~/.config/orbit-agent/workspace`, and an environment without Anthropic API, Bedrock, Vertex or Foundry variables. Read tools post to `/api/companion/jobs/{id}/tool`, which checks the job is `running` and claimed by this Mac, refuses write tools, runs the tool as the user and appends a `tool` event. Write tools never call Orbit; they return a fixed "Proposed … has not happened yet" text to Claude.
4. **Stream.** While the job runs, the server reads it every second and passes new `tool` events to the browser. From 1.6.0 the agent also posts `/api/companion/jobs/{id}/messages` every three seconds and pushes any message sent in the chat meanwhile into the running Claude query (streaming input mode, `client_composed`); it reports the ones Claude Code confirmed reading (`user_message_uuids`) as `steered` on `/complete`. Email jobs get no messages.
5. **Heartbeat.** During a turn the agent posts to `/api/companion/jobs/{id}/heartbeat` every 15 seconds. That marks the job as alive (its `updated_at`), and a 409 (the job was cancelled, for example by a follow-up message or Stop) aborts the Claude query. A `running` job with no heartbeat or tool call for three minutes, or that was claimed over 20 minutes ago, is cancelled with a reply in its chat. Several copies of the agent can share one pairing, so a job is never judged by which copy asks for work. A Mac with a running job it keeps reporting on counts as online, and as busy for 45 seconds after its job was cancelled, so a follow-up waits for it. On Ctrl+C or SIGTERM the agent posts to `/fail`.
6. **Finish.** The agent posts `{steps, results, sources, model, usage, steered}` to `/complete` (up to 4 MB). `readCompanionResult` caps it (200 steps, 100 calls per step, 200,000 characters of text per step, 1,000,000 per tool result, 30 sources), the job is moved from `running` to `done` first (so a late cancel can't undo it), and `applyCompanionResult` writes assistant and tool messages in order, with write calls as `pending` actions on the last message, then saves their ids as the result. On an error the agent posts to `/fail`, which saves the error as a reply in the chat. Finished jobs are deleted after a day.

If no Mac claims the job within 20 seconds, the server cancels it. If the job is still running five seconds before the request deadline, the server emits `waiting` and the dock reloads the chat every six seconds, up to 30 times. Approved changes run on the server through `decideActions`, then a new job asks Claude to report back.

### LinkedIn capture

The Chrome extension in `extension/` (Manifest V3, side panel, permissions `sidePanel` and `storage`, host permissions for LinkedIn and Orbit only) talks to `/api/extension/*`. Three owner-only tables back it, each with forced row-level security:

- `crm.extension_browsers`: one row per connected browser, with name, `token_hash` (unique), `last_used_at` and `revoked_at`. `authenticated` can read every column except `token_hash` and can only update `name` and `revoked_at`.
- `crm.extension_browser_workspaces`: the workspaces each browser may reach. Its `(workspace_id, user_id)` references `crm.workspace_members` with `on delete cascade`, so leaving a workspace removes it from every browser.
- `crm.extension_pairings`: pending codes (`code_hash`, `secret_hash`, `expires_at`, `status` of `pending`, `approved`, `declined` or `used`). No grants: it is reached only through the functions below.

Connecting is the reverse of Orbit Agent's: the extension starts it. `POST /api/extension/pair` (10 per address every 10 minutes; like every extension `POST`, it needs the extension's `Origin`) makes an eight-character code and a 32-byte secret, stores both hashed with `private.extension_pairing_start` and a 10-minute expiry, and returns them with `/connect/chrome`. The code is never in that link: the panel shows it and the person types it on the page (signed in; sign-in returns to it), so a link someone else sends can't approve their browser. The page asks for the code, a name for the browser and the workspaces (only the home workspace is ticked to start with), and says to approve only a code shown in your own panel right now. Approve or Cancel calls `private.extension_pairing_decide(code_hash, user, name, workspace_ids, approve)`, which keeps only workspaces the person belongs to and changes only a pending, unexpired code. The panel polls `POST /api/extension/pair/redeem` with the code and the secret; `private.extension_pairing_redeem` returns `pending`, or once approved inserts the browser with the hash of a new `olx_<32 random bytes>` token and its workspaces and marks the code used, so the credential is handed over once and only to the extension holding the secret. An approved code not redeemed within 10 minutes is `expired` to both redeem and `private.extension_pairing_status`. Like the other `private.*` functions, these are executable only by `crm_app` (execute is revoked from `public`); they have no check of their own on the caller.

On every request `requireExtension` hashes the bearer token and calls `private.authenticate_extension`, which returns the browser only when it isn't revoked, with its workspaces that the person is still a member of (oldest membership first, then by workspace id, as `private.memberships_for` orders them), and updates `last_used_at` at most once a minute; 300 requests a minute per browser. `/me` also names the home workspace (the oldest membership, as `private.home_workspace_id`) when the browser has it, and the panel starts there unless the record is only in another workspace. `POST /revoke` signs out through `private.extension_revoke_browser(browser_id)`, keyed on the authenticated browser, and returns 404 when it was already revoked. A request names its workspace in `X-Orbit-Workspace`, which must be one of those, and runs through `withActor` as the person with only `crm:read` and the write scopes for companies, contacts, leads, activities, opportunities and tasks. Lookup runs in every allowed workspace. The routes only call `lib/extension/records.ts` and `lib/extension/capture.ts`, which read and write through the `lib/crm` functions, so row-level security still applies (tasks the person can't see stay hidden) and every change is audited with source `linkedin_extension` and the LinkedIn page as `source_url`. Mail, calendars, docs and chats have no extension route, and other APIs refuse `olx_` tokens. CORS headers go only to `chrome-extension://<id>` for IDs in `LINKEDIN_EXTENSION_ID`; any other `Origin` gets 403.

Matching (`lookupPage`, each workspace on its own so one failing doesn't hide the others): people by `normalized_linkedin` (on a lead page, the public profile link the panel read from it), then `sales_navigator_url` (unique per workspace among active contacts, `contacts_workspace_sales_navigator_active_uidx`; a contact can have only a lead link, which `contacts_identity` allows), then the same normalised name at a company with the same normalised name or LinkedIn page, which is returned only as candidates for a Possible match and never written. Same person saves the profile or lead link on that contact (`kind: link`). Saving a new person matches only on the LinkedIn profile or lead link, never on name, so Not them really adds someone new; when that finds someone already saved, only fields the page has are sent, the owner changes only when the person picked one, tags are added and the company is kept, and `lead.created` is recorded only for a new contact. Companies match on `linkedin_url` (`companies_workspace_linkedin_active_uidx`, unique among active companies; the migration skips it and keeps a plain index when a workspace already has duplicates), then domain, then normalised name, skipping a domain or name match whose saved LinkedIn page or domain differs from the page's: lookup returns those as `companyCandidates` for a Possible match, and saving adds a new company instead (without the domain when another company has it). A matched company gets only the domain, LinkedIn page, industry, size and description it is missing, and a company that is added or gains a domain is enriched. Company upserts everywhere match a LinkedIn page after the domain, never move a LinkedIn page from one company to another, and keep the matched company's domain and website. A logged conversation is one `linkedin` activity whose `metadata.linkedinMessageKeys` holds a hash of each message's direction, text and time to the minute (or, without a time, its place among identical messages), so the panel greys messages logged before, a second Log skips them, and the same words sent on another day log again. Record links go through `/open?workspace=&to=`, which switches to the record's workspace (when the person belongs to it) and opens the record.

### Agent mailbox

People email Orbit at an address in MachineMail (`lib/machinemail.ts`, `MACHINE_MAIL_API_KEY`), and the email runs as an assistant turn on Orbit Agent. The code is in `lib/agent-mail/`: `mailbox.ts` (set up, senders, access), `senders.ts` (address parsing, authentication and the verdict), `receive.ts` (the webhook), `jobs.ts` (the job lifecycle and the reply) and `store.ts` (the assistant's reads and sends).

Tables, all with forced row-level security:

- `crm.agent_mailboxes`: one row per workspace, so each workspace (Eclipse, Mark Ridgeon) has its own address, and an address belongs to one workspace only (unique): address, display name, MachineMail webhook id and URL, `webhook_secret` (encrypted with `APP_SECRET`; `authenticated` can write it but never read it), who set it up and when, `last_received_at` and `last_error` (never with a sender's address; Settings shows it to owners and admins only). Every member can read the row; only owners and admins (`private.is_workspace_admin`) can insert or update.
- `crm.agent_mailbox_senders`: who can give it work, per mailbox: a lowercased address, unique per workspace, never the mailbox's own or another workspace's agent mailbox, and the member (`(workspace_id, user_id)` references `workspace_members`, so the mapping goes when the member does). Owners and admins manage the list and see every row; a member sees their own. The first setup fills it with the addresses of the person setting it up (`ownSenderAddresses`: sign-in email, their other addresses, connected mailboxes, calendar accounts and sending addresses, leaving out any agent mailbox), all mapped to them.
- `crm.agent_mail_messages`: every message received or sent: MachineMail message and thread ids, event id and type, direction, from, to, cc, subject, time, the cleaned text (`trust.content.text`, else `extracted_text` with `text_cleaned` false; never the raw body), trust level, `authentication` (SPF, DKIM and DMARC results with domains), attachment metadata with MachineMail's risk, the mapped member (`user_id`, only for mail that was accepted), the linked conversation and user message, `status` (`received`, `working`, `replied`, `superseded`, `failed`, `ignored`, `refused`, `sent`) with a reason, the cards its reply listed (`confirm_message_id`, `confirm_action_ids`), and the job's bookkeeping (`turn_started_at`, `rounds`, `notice_sent_at`, `reply_claimed_at`, `reply_attempts`, `replied_at`, `reply_message_id`, `advancing_until`). A generated `search` tsvector backs `search_email` with `mailbox: "agent"`, and a partial index covers open jobs (`received` or `working`, not replied). Owners and admins read every row, the mapped member their own and may update only bookkeeping columns on it, pointing it only at their own conversations. Nobody inserts directly: inbound rows come from `private.agent_mail_receive` and sent ones from `private.agent_mail_record_sent`, which always records the mailbox's own address as sender.
- `crm.agent_mail_threads`: maps a MachineMail thread, per member, to their conversation, with the thread's `rounds` (owner only).
- `crm.agent_mail_events`: event ids already handled, kept 30 days. No grants; only `private.agent_mail_receive` writes it.
- `crm.ai_companion_jobs.agent_mail_id` links an Orbit Agent job to the email it answers.

Security-definer functions, executable only by `crm_app`: `private.agent_mailbox_targets()` (mailboxes and their encrypted secrets, for verifying deliveries), `private.agent_mail_receive(mailbox, event_id, message, actionable, reason)` (dedupes the event, looks up the sender's mapping among current members, stores the message as `received`, `ignored` (not on the list) or `refused` (on the list, but it failed the checks) and returns the id and member), `private.agent_mail_record_sent(...)`, `private.agent_mail_working(limit)` (jobs the cron should look at), `private.agent_mail_fail(id, reason)` (for a job whose member has gone) `private.agent_mailbox_note_error(mailbox, error)` and `private.agent_mailbox_address_taken(address, workspace)` (whether another workspace's mailbox has that address). `private.team_remove` also fails a removed member's open email jobs and deletes their thread mappings.

Set up (`setUpAgentMailbox`, owners and admins, needs `SITE_URL` to be https) first refuses an address another workspace already uses (409, before MachineMail is called, so one workspace can never take over another's inbox or webhook; a unique violation gives the same message), then: `POST /v0/inboxes` with `client_id`, treating 409 as fine when `GET /v0/inboxes/{address}` finds it in the organisation; `POST /v0/webhooks` for `message.received` on that inbox with a `client_id` from the address and URL (patched if it comes back with another URL or types; a webhook for an earlier URL is deleted), storing the encrypted secret; the default senders are added mapped to the person setting it up when the list is empty. A secret that can't be decrypted is skipped and noted on the mailbox ("Set up again").

The flow:

1. **Receive.** Every mailbox's webhook points at the one URL, `POST /api/machinemail/webhook`. It reads the raw body (5 MB at most), picks the mailbox whose address is the message's `inbox_id` and checks `X-MachineMail-Signature` against that mailbox's secret only (events without an inbox, such as `webhook.test`, are checked against each mailbox's secret) (`t=<unix>,v1=<hex HMAC-SHA256(secret, t + "." + body)>`, `timingSafeEqual`, at most 300 seconds off, never with an empty secret), requires the header and body event ids to match, ignores other event types and other inboxes, judges the message (`judgeMail`: `message.received`, `direction` inbound, a From with exactly one address that isn't the mailbox's own, a trust report with level verified, known or unknown, and DMARC pass for the From domain or a DKIM pass for that domain or a subdomain of it, never when `trust.authentication.aligned` is false) and calls `private.agent_mail_receive`. It answers at once; accepted mail is handed to `after()`.
2. **Start.** `processAgentMail` runs as the mapped member in the mailbox's workspace (its brand profile, records and Knowledge), using that row's own mailbox, under a five-minute lease on the row (taken only by an actor in the row's workspace; `continueAfterCompanion` switches to the email's workspace when Orbit Agent reports from another), which stays `received` until the turn is queued (or has failed with a reply), so a crash leaves it for the sweep. If another email in the same conversation holds a lease, it leaves this one for the next sweep. A conversation moved to a non-Claude model gets a reply saying so. A clear yes approves the cards the last reply listed (see `docs/assistant.md`, Email jobs). Otherwise unanswered jobs in the thread become `superseded`, attachments are downloaded (streamed, stopped at the limit, within 90 seconds) and imported as chat files, the lease is renewed and `sendMessage` adds the message without declining waiting cards.
3. **Queue.** Email turns are headless (`TurnOptions.headless`): `runCompanionTurn` enqueues the job with `agent_mail_id` and returns instead of waiting. With no Mac online it still queues (unless no Mac is paired, which fails the turn), and the first time any turn for that email is queued while the Mac is off, Orbit replies with the waiting note. `expireStale` gives email jobs 24 hours in the queue instead of 20 minutes.
4. **Continue.** `/api/companion/jobs/{id}/complete` and `/fail` (both `maxDuration` 300) call `continueAfterCompanion` in `after()`, and `/api/cron/mail-due` (every minute, `maxDuration` 300, starting rows for about 75 seconds) sweeps jobs left behind, fails those whose member has gone, and restarts a `working` row that has neither a job nor a conversation. `advanceAgentMail` does nothing while the job is queued or running. A job cancelled by a newer job from the app, or by Stop, is `superseded` with no reply. Otherwise it approves the email's own cards up to the first that needs a yes (`lib/assistant/email-policy.ts`) through `decideActions` with tool source `email`, then queues the next turn, within 8 rounds per email and 24 per thread.
5. **Reply.** When nothing is left to run, `finishWithReply` claims `reply_claimed_at` (taking over a claim older than 10 minutes) and posts `POST /v0/inboxes/{inbox}/messages/{message_id}/reply` with `to` set to the sender's own address and `reply_all` false. `/reply` honours an explicit `to` over Reply-To and copies no Cc unless `reply_all` is set, so it reaches only the sender. The body is the last assistant text since the job started, the actions that ran, the cards waiting with their lines and "Reply yes to go ahead, or tell me what to change.", and `<site>/?chat=<id>`, as text and simple HTML. There are three attempts in all: a network error, 408, 429 or 5xx frees the claim for another attempt; anything else, or the third failure, marks the job `failed` and notes the error on the mailbox.

Mail the webhook missed is picked up by `pollAgentMailboxes` (`lib/agent-mail/poll.ts`) from `/api/cron/mail-due` within a 20 second deadline: it lists the last 48 hours of every set up mailbox (`private.agent_mailbox_poll_targets()`), skips messages already stored (`private.agent_mail_known`) and fetches and stores up to 10 new ones per mailbox, so a busy mailbox never starves another, starting from a different mailbox each minute so the same ones aren't always last when the deadline hits. Polled messages are stored under the event id `poll:<mailbox id>:<message id>`, so two mailboxes listing the same message id each keep it; a mailbox that fails is skipped (a refused key is noted on it) and the rest still run.

`npm run build` runs `npm run companion:pack` (`scripts/pack-companion.mjs`), which bundles `companion/src/index.ts` with esbuild into `companion/dist/orbit-agent.mjs` (Node 20, ESM, with `@anthropic-ai/claude-agent-sdk` and `zod` left as dependencies) and packs it into `public/downloads/orbit-agent-<version>.tgz` (the version from `companion/package.json`, so npx never reuses an old copy) and `public/downloads/orbit-agent.tgz`. Both outputs are gitignored.

## Team

`crm.workspace_members` holds each person's role (`owner`, `admin`, `member`). Members have every scope except `admin`. Changes to membership only go through security-definer functions executable by `crm_app`, each of which checks the caller's role itself:

| Function | Rule |
| --- | --- |
| `private.team_invite(workspace, actor, email, role, token_hash)` | Owner or admin; only the owner may invite an admin; refuses an address already in the workspace; cancels earlier pending invites for it. Takes a lock per workspace and address, and `workspace_invites_one_pending_idx` keeps one pending invite per workspace and lower-case address, so invites sent at once leave one working link. |
| `private.team_revoke_invite(workspace, actor, invite)` | Owner or admin. |
| `private.invite_preview(token_hash)` | Public read for the join page: workspace, email, role, inviter, status (`revoked` when the inviter is no longer an owner or admin there). |
| `private.accept_invite(token_hash, user)` | The invite must be pending, unexpired, for the user's profile email, and sent by someone who is still an owner or admin of the workspace. Adds the membership to the invite's workspace only. Accepting twice by the same user is a no-op. A trigger on `crm.workspace_members` revokes every pending invite a person sent when they are removed or stop being an owner or admin. |
| `private.create_workspace(user, name, brand_source)` | The user must own at least one workspace; `brand_source` must be one of theirs. The app always passes null, so new workspaces start blank. |
| `private.team_set_role(workspace, actor, user, role)` | Owner only; the owner's own role never changes. |
| `private.team_remove(workspace, actor, user)` | Owner or admin; never the owner or yourself; only the owner removes an admin. Moves the person's companies, contacts, opportunities and tasks to the remover. If they are in another workspace, moves their mail, calendars and other personal rows there; otherwise disconnects their mailbox and calendar accounts, deletes their AI accounts and revokes their Orbit Agent pairings. Their Granola, Readwise and Recall keys move to their next workspace with the other personal rows when they have one (Readwise documents in this workspace are dropped and the sync starts again there; Knowledge items already imported stay); otherwise they are deleted. Then the membership. |

`crm.workspace_invites` stores the SHA-256 of the token (the token itself is only in the link), the email, role, inviter, expiry (14 days), and accepted or revoked times. `lib/auth/accounts.ts` creates the login for `/join/<token>`: `private.create_local_user` without Supabase, `auth.admin.createUser` with `email_confirm` when `SUPABASE_SERVICE_ROLE_KEY` (or `SUPABASE_SECRET_KEY`) is set, otherwise `auth.signUp` with a confirmation link to `/auth/callback`, which exchanges the code for a session. An address that already has a login proves its password instead.

Per-person Granola keys live in `crm.granola_keys` (encrypted with `APP_SECRET`, owner-only). `private.granola_key_members()` lets the scheduler add a sync step for each member with a key; the server key still syncs for the member whose email owns it.

Granola, Readwise and Recall keys (`crm.granola_keys`, `crm.readwise_keys`, `crm.recall_keys`) are one per person (`granola_keys_user`, `readwise_keys_user` and `recall_keys_user`, unique on `user_id`; `on conflict` names them) and are connected once in Settings › Connections for every workspace. Reads and deletes filter by user only. A new key is stored in the person's home workspace (`homeWorkspaceId`, the oldest membership); saving again keeps the row's workspace. That workspace is where the key's sync runs: a personal Granola sync runs as the key's workspace (`actorForWorkspace`) and still routes each note to every workspace that knows someone on it; `syncReaderToKnowledge` switches to the key's workspace, so Readwise documents always go into Knowledge there, also when Sync now is pressed in another workspace; Recall copies nothing. For someone in more than one workspace the Readwise card has Add to Knowledge in (`setReadwiseWorkspace`), which sets the key's workspace, deletes its `readwise_documents` and resets the sync cursors so the next sync starts again there; Knowledge items already imported stay. Granola and Recall have no such choice: Granola notes are routed to every workspace that knows someone on them, and unknown ones wait where the account's address is homed. `private.move_personal_rows` moves the keys with the person's other rows, and resets Readwise the same way. Migration `20270108100000_settings_simplified.sql` keeps the most recent key per person and service (Granola by `updated_at`, Readwise and Recall by `connected_at`; a dropped Readwise key's `readwise_documents` go with it, its Knowledge items stay), adds the `unique (user_id)` constraints next to the old `(workspace_id, user_id)` ones (kept so code from before the deploy still works during the deploy; a later migration can drop them), adds an index on `readwise_documents (user_id, document_id)`, and redefines `private.move_personal_rows`. It can run twice.

## Mail mirror

`lib/mail/` mirrors mailboxes so Orbit can show and search mail without asking the provider. `crm.mail_sources` has one row per mailbox (the main Microsoft connection, or an extra Microsoft account with `can_send`), with a provider (`microsoft` today, so Gmail can be added as another adapter), a lock (`locked_until`, five minutes) and the last error. `crm.mail_folders` holds each folder with its role (from Graph's well-known names: inbox, sentitems, drafts, archive, deleteditems, junkemail, outbox), counts, `sync_state` (`pending`, `backfill`, `live`, `skipped` for junk and outbox) and `sync_link`, the saved `@odata.nextLink` or `@odata.deltaLink`. `crm.mail_messages` holds every message: thread key (`conversationId`), subject, snippet, HTML body (up to 1.5 MB, else only text with `body_truncated`), plain text from `htmlToText`, sender, recipients, times, read, draft and flag state, attachments flag, categories, and a generated `search` tsvector (subject A, sender B, body C) with a GIN index. All three tables are owner-only with forced row-level security.

`syncMail` (`lib/mail/sync.ts`) loads the user's sources, claims each one, refreshes the folder tree every six hours (`listMicrosoftFolders`: the well-known ids, then up to five levels of child folders, at most 300), and splits the time between sources. Live folders run first (one delta round each), then pending and backfilling folders by role: inbox, sent, drafts, archive, others, deleted items. The first delta request selects the message fields with `$orderby=receivedDateTime desc`, `Prefer: odata.maxpagesize=50, outlook.body-content-type="html", IdType="ImmutableId"`. Each page is upserted in one statement through `jsonb_to_recordset`; partial items (only read or flag state) update those fields; `@removed` items delete the row from that folder only, so a message moved between folders keeps its row. A 410 or `SyncStateNotFound` resets the folder to `pending`. During a backfill, each page checks `pg_database_size` against `MAIL_STORAGE_LIMIT_MB` and pauses with a folder error when it is reached. Before any source runs, the database size is checked against `MAIL_HARD_STOP_MB` (default 18% above the limit); at or above it nothing syncs and every source gets `MAIL_HARD_STOP` as its error.

It runs from `/api/cron/mail` (`maxDuration` 300, a 240-second budget shared across users, with backfill), as the `mail_store` step of `/api/cron/sync` (15 seconds, new mail only) and after each CRM page load (10 seconds, new mail only). `lib/mail/store.ts` reads it: `searchMail` (`websearch_to_tsquery('english', …)` ranked by `ts_rank`, then newest; filters for sender, account and folder role), `getMailThread` (the thread in one source, oldest first, at most 100) and `mailSyncStatus` (stored against Graph's counts per folder).

### Mail on the timeline

`fileMailOnTimeline` (`lib/mail/timeline.ts`) runs at the end of every `syncMail`. As the user, it selects their mirrored messages from the last 60 days (not drafts, junk or outbox), pairs inbound mail with the sender and mail sent from one of their own addresses with each To and Cc address, and joins those addresses to workspace contacts by `normalized_email`. It skips any pair that already has an email activity on that contact with the same `mailMessageId` or `internetMessageId`, or, for activities logged at send time without those ids, the same title and direction within three minutes. For a contact it checks that contact's activities through the contact index. For mail filed on a company only, the JSON id lookups can't use an index under row-level security, so it reads the workspace's email activity ids once, and only when such rows exist. Up to 100 are filed per run, oldest first, as `email` activities with `source: microsoft`, `direction`, `account`, `mailMessageId` and `internetMessageId`. Filings older than a day carry `catchUp` in their provenance, and `enqueueWorkflowEvent` ignores events with `catchUp`. The old inbox sync (`lib/crm/inbox.ts`) skips a message whose `internetMessageId` is already on the contact. Every filer (this one, the old inbox sync and the send path) writes through `createEmailActivityOnce` (`lib/crm/activities.ts`), which takes a transaction-scoped advisory lock on the workspace and the message's `internetMessageId` (else its own id) and checks again before inserting, so filers that overlap write one activity and one `activity.created` audit event. A reply sent from Orbit is logged at send time with its `internetMessageId`, in the workspaces its conversation is filed in (`threadFiledWorkspaces` in `lib/mail/filing.ts`, the same rules as `effectiveFilingInDb`): nowhere when the conversation is ignored or only in Capture, and once in each workspace when it is filed in several. A contact newly cc'd into a reply on a thread routed elsewhere is logged where the thread is filed. New emails and forwards are logged in the current workspace. `sendContactEmail` (workflows, proposals and the contact page) sends with Graph's `sendMail`, which returns no message id, so its activity still relies on the title and time match.

### Mail home

`/mail` (`app/(crm)/mail/page.tsx`) renders the first page of the chosen view on the server and hands it to `components/mail/mail-screen.tsx`, which does everything else in the browser. `lib/mail/threads.ts` reads conversations: `listThreads` groups messages by source and thread key (`coalesce(thread_key, 'm:' || id)`) within a view (a folder role, one folder, or a search across every folder but junk and outbox) with window functions, takes the newest message for the row and `bool_or` for unread, flagged and attachments, and pages with a `(time, key)` cursor. `getThread` returns the whole conversation in every folder, oldest first, with HTML passed through `cleanEmailHtml` (`lib/mail/html.ts`: scripts, frames, forms, `base`, event handlers, `javascript:` links and `cid:` images removed) and `rich` set for designed emails. `mailNav` and `mailUnreadCount` count unread conversations per folder and account. The CRM layout doesn't wait for the count: `MailUnread` (`components/mail/mail-unread.tsx`) fetches `GET /api/mail/unread` (`mailUnreadCount`, which only classifies inbox threads with unread mail) after the page renders and again on focus at most once a minute, and Mail keeps it current through the companies store. `/mail` waits for the first page, the open conversation and the From accounts, and streams the nav to the browser as a promise (`use()` inside Suspense). Until it arrives the nav is `partial`: Mail shows the list, never the Connect Microsoft screen, and leaves the badge alone. If the nav fails on the server, the browser asks `/api/mail/nav` once. Client-safe types and URL parsing are in `lib/mail/view.ts`.

The browser talks to route handlers, not server actions, so reads are never queued behind writes: `GET /api/mail/threads`, `/api/mail/thread`, `/api/mail/nav`, `POST /api/mail/actions` and `POST /api/mail/sync` (an eight-second new-mail sync, returning the mail version). Migration `20270112100000_mail_speed.sql` adds `crm.mail_versions` (owner-only, one counter per user), bumped once per transaction by deferred triggers when something the list or nav shows changes: messages (folder, read, flag, subject, sender and the like), folder names and roles, mailboxes, reminders, scheduled drafts, sender rules, prepared replies, opens, and contacts' email addresses (for everyone in that workspace with mail). Sync bookkeeping (locks, delta links, counts, tokens) doesn't bump it, so a sync with no new mail leaves it alone. Changes it doesn't track show at the five-minute backstop or the next change: a mailbox's connected state (`mailbox_connections`, `calendar_accounts`), summaries, filing routes, subscriptions and capture dismissals. The poll every minute and on focus runs the sync and refetches the list and nav only when the version the sync returned differs from the one the last full refresh saw, or five minutes have passed. Reads, flags and moves update the nav counts in the browser (unread per account, inbox folder and split); after a move, Undo or failed read settles, one nav refetch runs 1.5 seconds later (later ones in that window ride along), so totals and the snoozed count stay right. Moving a sender to another split refetches the nav straight away. `/api/mail/thread` returns what the reader renders: plain text only when there is no HTML or for a draft, and the stored summary for the newest message as `cachedSummary`, or an empty one when the thread is too short or AI is off, so the browser skips `/api/mail/summary`. When a prefetched conversation arrives, the browser also fetches the attachment lists of the messages that open expanded (`loadAttachments` in `mail-cache.ts`, shared with `MessageAttachments`), so opening it never waits for Outlook. A conversation fetched before a local change or a forget is never stored over it. `components/mail/mail-cache.ts` keeps lists and conversations in memory for the session, collapses duplicate requests and prefetches two at a time: the first four of each list, the two after the selected conversation and the one before, and whatever the pointer rests on. Emails render in a sandboxed `iframe` (`allow-same-origin` and popups only, no scripts) with a content security policy that allows only images, styles and fonts, `<base target="_blank">`, and a height that follows the body.

`applyMailAction` (`lib/mail/actions.ts`) handles read, unread, flag, unflag, archive, trash, inbox and snooze for a conversation. Read touches every unread message and unflag every flagged one; unread and flag touch the newest message in the view. Moves take the messages in the current view (for a search, the inbox and your own folders for archive, everything but trash for trash, archive and trash for inbox), never drafts. It gets a token with `mailSourceToken`, calls Graph (`PATCH /me/messages/{id}` or `POST /me/messages/{id}/move` with a well-known destination, `IdType="ImmutableId"` so ids survive the move) four at a time, then updates the rows that succeeded, moving each to the folder Graph reports (or the folder with that role). The later delta for the old folder removes nothing, because the row is already in the new one. Changes to your own mailbox are not audit events, like notifications. The screen applies each change at once, undoes it if the request fails, and keeps moved conversations out of refreshed lists until the move is confirmed.

### Replies, drafts and read statuses

`lib/mail/compose.ts` writes new emails and replies as Outlook drafts. A new email (`mode` `new`) names its source account, starts with `POST /me/messages` and takes the draft's `conversationId` as its thread key; changing From on a saved one deletes it and starts again in the other mailbox. `components/mail/compose-dock.tsx` (`ComposerProvider` in `CrmChrome`, `useComposer().openComposer`) holds up to six floating cards, positioned along the bottom right until dragged, with minimised pills; Compose, `create-email` and Quick add's Send email open one, and `GET /api/mail/accounts` (`composeAccounts`: each mail source with its signature) fills From. `components/mail/mail-composer.tsx` is the editor shared by cards and inline replies. `saveMailDraft` checks the input (`readDraftInput`: mode, the message replied to, at most 100 addresses per field, 20,000 characters), and on the first save calls `createReply`, `createReplyAll` or `createForward` on that message with the source's token (`mailSourceToken`), which gives Outlook's subject and quoted history. It keeps the draft in `crm.mail_drafts` (owner-only: provider draft id, mode, the message, thread key, the quote, recipients, subject, body, tracking id). Every save PATCHes the draft with recipients, subject and `composeEmailHtml` (`lib/mail/html.ts`): the message as escaped paragraphs with links, the signature for the source's address, the read image, then the quote with any earlier read images removed, inserted after `<body>`. A draft deleted in Outlook is made again. `sendMailDraft` saves, adds attachments with `attachToDraft` (shared with large sends in `lib/microsoft/oauth.ts`), calls `send`, marks the tracking row sent, deletes the draft row and logs an outbound email activity on each matching contact in To and Cc. `discardMailDraft` deletes the Outlook draft and the mirrored copy. `getThread` returns the thread's drafts and leaves their mirrored copies out of the messages. The browser saves 1.5 seconds after typing stops, one save at a time, and sends any unsaved change with `keepalive` when the composer closes. Routes: `POST` and `DELETE /api/mail/drafts`, `POST /api/mail/drafts/send`, `DELETE /api/mail/draft-message?id=` (deletes a mirrored draft made outside Orbit, in Outlook and in the mirror), `GET /api/mail/people` (contacts and senders for the recipient fields).

Read statuses: when `crm.mail_preferences.read_statuses` is on (the default) and Orbit has a public `https` origin (`SITE_URL`, else the request), a draft gets a `crm.mail_tracking` row and its HTML a 1×1 image at `/api/mail/open/<id>`. That public route returns a GIF and calls `private.record_mail_open` (security definer, `crm_app` only), which records a row in `crm.mail_opens` unless the email is unsent or under five seconds old, the request comes from an address the owner used Orbit from in the last 30 days (`crm.mail_viewer_addresses`, an HMAC of the IP with `APP_SECRET`, noted after each CRM page load at most hourly), the last open was under two minutes ago, or there are already 200. The user agent is reduced to an app or device (`readerAgent`). The mail sync stores the tracking id on messages from the source's own address (`trackingIdIn`), and `listThreads` and `getThread` count and list the opens. `cleanEmailHtml` removes read images, so viewing mail in Orbit never counts as a read. Emails sent from a contact, a company or in bulk (`sendContactEmail`, also used by workflows and proposals) are sent as HTML through the same `composeEmailHtml` (with `plain`, so the text is escaped and linked but never formatted, and indentation, runs of spaces and blank lines are kept) and get the same tracking row and image. The row is marked sent after Graph accepts the email, deleted when Microsoft refuses it, and kept and marked sent when the outcome is unknown (a timeout); if the row can't be created the email goes untracked. It is linked to the timeline activity through `crm.mail_tracking.activity_id` in its own step after the activity is saved, so the shared activity carries no tracking id. Record pages read statuses with `timelineReads`, which reads `crm.mail_tracking` and `crm.mail_opens` inside `withActor`, so row-level security returns only the viewer's own.

### Remind me, Send later and Undo send

Undo send lives in the browser: `MailComposer` hands its content to `queueSend` in the compose dock and closes at once; the dock shows "Sent" with Undo and posts `/api/mail/drafts/send` after ten seconds, or straight away with `keepalive` on `pagehide`. The payload waits for any autosave in flight so a draft is never made twice. On the server, `writeDraft` reads the draft, its target and signature in one transaction and skips the Outlook PATCH when `content_hash` (subject, body, signature and recipients) hasn't changed since the last autosave, so a send is usually just Graph's `send`; a draft deleted in Outlook is made again and sent. A send by draft id first claims the row (`sending_at`, cleared on failure; the scheduler's `claimDueDrafts` sets it too), so Send now, the scheduler and a second click can't send the same draft twice: a row another send claimed in the last ten minutes is refused as already sending, and an id whose row has gone is refused as already sent or deleted. The composer sends a `sendKey` (a uuid made once per composer) and `crm.mail_send_keys` (owner-only) remembers it: a repeat of a key that already sent answers success without sending, a repeat while the first is still making its draft is refused as already sending, and a retry after a failure reuses the draft the first attempt made. Just before Graph's `send` (or SMTP for another address) the row gets `send_attempted_at` and `sent_internet_id`. A clear refusal (a 4xx, or a 500 with a specific Graph code, or an SMTP reply code) clears the mark; a lost answer (network error, timeout, 502, 503, 504) keeps it and answers "Outlook didn't confirm the send. Check Sent before resending." A later send of a marked draft first asks Outlook (`fetchDraftState` and `findSentCopy`). `findSentCopy` looks the email up by its `internetMessageId` when Orbit has one and trusts that answer alone; only without an id does it look in Sent Items for the same conversation and subject, sent at or after the attempt, to exactly the same recipients. A sent copy finishes the send without sending again ("Already sent."), and a Microsoft draft still in Drafts at least two minutes after the attempt is sent normally. Anything else, including every draft sent from another address (SMTP leaves the Outlook draft untouched, so its state proves nothing) and a draft that vanished when `send` answered 404, is refused with a 409 carrying `maybeSent` and the draft id: "May already be sent. Check Sent before using Send anyway." The composer that opens from that toast shows the message with Send anyway, which posts `force: true`; a forced send clears the mark and remakes the Outlook draft if it has gone. So Orbit never makes and sends a fresh draft on its own when the original's outcome is unknown; a draft already missing before the send is still made again. A failure that isn't a `CrmError` says "Outlook didn't confirm the send" only when the row was marked, otherwise "The email didn't send. Try again." Every send error carries the draft id, and the dock reopens the draft with that id and the same `sendKey`, so a retry reuses the server's draft. The browser hides a draft from the Mail cache (`holdQueuedDraft`) the moment its send is queued; Undo, a failure or any 409 releases it, which forgets and reloads every cached conversation it was hidden from. Attachments load alongside, and the timeline entry and attachment clean-up run in parallel after sending. `mailSourceToken` reads only the one source.

Snooze is the `snooze` mail action: `ensureMicrosoftFolder` finds or makes a top-level Snoozed folder (kept in `mail_sources.snooze_folder_id` and given the `snoozed` role on folder refresh), the conversation's inbox and own-folder messages move there, and a `crm.mail_reminders` row (`kind` `snooze`, owner-only) records when. Send later sets `mail_drafts.send_at` (with attachments, signature and `remind_hours`) through `POST /api/mail/drafts/schedule`; `DELETE` unschedules and `GET /api/mail/scheduled` lists them. A draft's files live only in Orbit, as `crm.email_attachments` ids in `mail_drafts.attachments` (the daily sweep skips any a draft still refers to), never in the Outlook draft: `writeDraft` carries them to the new row when changing From or remaking a lost draft, and each send attaches them once, just before `send`. `saveMailDraft`, `sendMailDraft` and `scheduleMailDraft` take `storedFiles`: the Mail compose routes pass `replace`, because the composer opens a draft with its files as removable chips (`MailDraft.attachments` from `threadDrafts` and `listScheduledDrafts`) and sends the whole list; the assistant, the MCP draft tool and the scheduled-send cron pass `keep`, which adds any new files to the stored ones. Sending with `remindHours` adds a `follow_up` reminder for the thread. Sending with `followUpDays` (1 to 10) instead adds one with `action` `send`, the written `follow_up_body` (or none), the `recipients`, the sending identity (`identity_id`, with `used_identity` so a deleted identity can't quietly change the From address) and `original_internet_id`, the `internetMessageId` of the email it was set on (read from the Outlook draft just before `send`, or the `Message-ID` of the MIME sent over SMTP), due at 09:00 London time that many working days later (`followUpDueAt` in `lib/mail/follow-up-rules.ts`, using the working days in `lib/crm/task-due.ts`), and closes any other waiting follow-up on the thread except a deferral. Drafts keep `remind_hours`, `follow_up_days` and `follow_up_body`, so a reopened or scheduled draft keeps the choice, and a scheduled one counts from when it actually sends.

`processDueMail` (`lib/mail/due.ts`) does nothing unless something is due. A reminder that throws is counted (`mail_reminders.attempts`, `last_error`) and tried again 5, 10, 15 and 20 minutes later; on the fifth failure it is surfaced as `due` with a notification ("Still snoozed" for a snooze) instead of retrying for ever. It claims due drafts (clearing `send_at` with `for update skip locked`) and sends them, recording `send_error` and a notification on failure; claims due reminders, moving snoozed conversations back to the inbox and marking the latest unread, and checking follow-ups for a newer message from anyone but the user's own addresses (done if there is one, otherwise a notification). A follow-up with `action` `send` (never an `automatic` one, which a check constraint forbids) goes through `sendDueFollowUp` (`lib/mail/follow-up.ts`): a reply marks it `replied`. It is only sent when the user's own message is still the latest in the thread, is the one it was set on (same `original_internet_id`, or, when either id is missing, sent no more than 5 minutes after the reminder was made), has the same To and Cc as the stored recipients, and the sending identity it was made with still exists. Otherwise it takes the written body or asks `writeNudge` with `unreviewed` (the thread and the user's voice samples only: no CRM context, call notes, edit examples or About you, since nobody reads it first; without the prepared replies setting or the daily limit) and stores the written body on the reminder before going further. It checks the mirror for a reply again, then asks Outlook directly (`fetchConversationMessages`: `GET /me/messages?$filter=conversationId eq '...'`) for any message in the conversation from an address that isn't the user's, newer than the reminder; a reply there marks it `replied`, and a failed check means it isn't sent. Only then does it move to `sending` (stamping `sending_at`) and send with `sendMailDraft` as a reply to that message, then `sent` with a "Follow-up sent to" notification. If any check stops it, or writing or sending fails, it stays `due`, which is the reminder, keeps any written text as a prepared nudge, and notifies with the reason. A row left in `sending` for over 10 minutes (the function died mid-send) is moved to `due` with the alert "Check Sent: follow-up may not have sent" and is never sent again automatically. `processDueMail` takes a `deadline` (20 seconds by default; `/api/mail/sync` passes what is left of its 30, the cron routes their own) and claims one draft or reminder at a time, stopping when less than 8 seconds (drafts) or 12 seconds (reminders) are left, so nothing is claimed that can't finish. `POST /api/mail/follow-up` saves, writes (rate limited), sends now (rate limited the same way when Orbit has to write it; a reply, a newer email, other recipients or a removed identity answer 409, a failed write, check or send 502), cancels (`cancelled`, also while the cron holds it as `due`, which stops the send; 409 "Already sending this follow-up." when it has moved past that) and restores one (only while its time is still to come and no other follow-up is waiting on the thread, else 409). The thread banner refreshes the thread after a 404 or 409. `getThread` returns the waiting follow-up with its body and recipients, and `followUpReplied` (who replied, and before which message) when the newest send follow-up on the thread was ended by a reply and no other follow-up is waiting; `listThreads` returns `followUpAt` while it waits. A surfaced reminder is `due`: `listThreads` sorts by the later of the newest message and `surfaced_at`, includes due follow-up threads in the inbox even when they hold only sent mail, and returns `reminder` and `snoozedUntil`. Archiving or trashing marks the thread's reminders done; unsnoozing ends its snooze. It runs from `/api/cron/mail-due` (`private.mail_due_members()` finds who has work), after each user in `/api/cron/mail`, in `/api/mail/sync` (Mail's minute poll) and after page loads.

### App and notifications

`app/manifest.ts` makes Orbit installable (standalone, `start_url` `/mail`, icons in `public/icons`), and `public/sw.js` shows pushed notifications and sets the app badge. Tapping one posts the link to an open Orbit window (iOS ignores `navigate()` on an existing window), or opens a new one; the worker also keeps the link for a minute so a window that starts up asks for it (`orbit-pending`). `PushRegistrar` opens it, and on Mail selects the conversation in place. `GET` and `POST /api/push/settings` read and save the mail level, meeting reminder minutes and first-read alerts; `POST /api/push/test` saves the device's subscription and sends it a test notification. The proxy lets `/sw.js` and the manifest through without signing in. `components/push/push-client.ts` registers the worker on every CRM page (`PushRegistrar`), subscribes with the VAPID public key from `GET /api/push/key`, and saves the subscription with `POST /api/push/subscribe` (owner-only `crm.push_subscriptions`); Mail sets the badge to the Important unread count. `isPushEndpoint` (`lib/push.ts`) only accepts `https` endpoints on the default port at FCM (`fcm.googleapis.com`, and `jmt17.google.com`, which current Chrome uses), Mozilla (`updates.push.services.mozilla.com`), Apple (`web.push.apple.com`, `*.push.apple.com`) and Windows (`*.notify.windows.com`), when subscribing and again before each send, so a member can't make the server call anything else. For anyone in more than one workspace, push, bell and booking email links go through `/open?workspace=&to=` (`alertLink` in `lib/crm/workspaces.ts`), so an alert from a workspace that isn't the current one switches to it first; `/open` only redirects to Orbit pages (`safeOpenTarget` in `lib/open-link.ts`), and the bell and `PushRegistrar` open a link for the current workspace in place.

`lib/push.ts` sends with `web-push`. The VAPID key pair is made on first use and kept in `private.push_keys` (the private key encrypted with `APP_SECRET`) through `private.push_key()`, so there is nothing to configure. Subscriptions the push service reports as gone (404 or 410) are deleted.

New mail: `storePage` returns the ids it inserted (`xmax = 0`), and for a live inbox those become `report.arrived`; after the sync `notifyNewMail` (`lib/mail/notify.ts`) keeps unread mail from others received in the last six hours, works out each one's split, applies the user's `notify_mail` level (`crm.mail_preferences`: important, all or none) and pushes one notification per message, or one summary for more than three. The first sync of a folder never notifies. For speed, each sync keeps a Graph change-notification subscription on the inbox (`created`, about three days, renewed within a day of expiry) pointing at `/api/microsoft/mail-webhook` with a random `clientState`; that public route echoes Graph's validation token, finds the owner through `private.mail_subscription_owner(id, clientState)` and runs a short new-mail sync after responding. Subscriptions need an https `SITE_URL`.

Other alerts go through `sendAlert` (`lib/alerts.ts`), which pushes, optionally adds a bell notification, and records a key in `crm.push_log` (owner-only, unique per user) so each alert goes out once. `calendarAlerts` (`lib/calendar-alerts.ts`) runs every minute from `/api/cron/mail-due` for the people `private.calendar_alert_members()` finds (a device set up and a meeting inside their lead time): one alert per meeting (keyed on iCal UID and start, so the same meeting in two calendars alerts once) whose link is the online meeting URL, which the service worker opens directly. `processDueMail` alerts on a failed scheduled send (always), an unanswered follow-up (with the bell) and a snooze coming back (both off when mail notifications are off). The tracking image route calls `alertFirstRead` after the first recorded open when `notify_reads` is on, using `private.mail_open_owner()`.

### Split inbox

Splits are worked out when listing, not stored, so a new contact or rule changes them at once. The one part that comes from the mirror is kept as it changes: `crm.mail_sent_threads` (owner-only, select only) has a row per source and thread with a message in a sent folder (keyed by user, not workspace, so moving between workspaces can't hide it), maintained by triggers on `mail_messages` and on a folder's role under a transaction advisory lock on the source and thread, so the sent check is one key lookup. `mail_messages.thread_key` is never null: a trigger sets `m:<id>` when Outlook sends no conversation, so code can compare the column directly and use its indexes. `lib/mail/split.ts` builds the SQL: `splitJoin` finds the user's rule for the sender's address or `@domain` in `crm.mail_sender_rules` (owner-only; the address wins), and `splitCase` applies, in order, the rule, a calendar subject or sender, a matching contact (`normalized_email`), a sent message in the same thread, automated sender patterns (news), Outlook's `inferenceClassification` (`mail_messages.focused`, false means other) and finally important. The mirror reads `inferenceClassification` with every message; `classifyFolder` fills it in once for mail already stored, page by page, and sets `mail_folders.classified_at`. `listThreads` takes `{ role: "inbox", split }` (URL `view=inbox:news`) and returns each thread's split; `mailNav` returns totals and unread per source and split, and `mailUnreadCount` (the side menu) counts Important only. `POST /api/mail/sender-split` saves or clears a rule. Bulk actions in the browser move or mark each selected conversation with up to four requests at a time and one toast with Undo.

### Unsubscribe and subscriptions

Migration `20261222100000_mail_unsubscribe.sql` adds three owner-only tables with forced row-level security. `crm.mail_subscriptions` holds one row per user and sender key (an address or `@domain`, the same keys as `mail_sender_rules`): `status` (`subscribed`, `kept`, `unsubscribed`, `research`, `blocked`), `unsubscribed_at`, the last `method` (`one_click`, `mailto`, `page`, `none`) and `outcome` (`unsubscribed`, `requested`, `needs_you`, `failed`, `none`), `ignored_at` and `ignored_count`, `cold_pitch_at`, `pitch_rule` (Orbit made an Other sender rule for a cold pitch), and the last `List-Unsubscribe` header Orbit read with `one_click`. When an address row and a domain row both match, the stricter status wins (blocked, research, unsubscribed, kept, subscribed, the address breaking a tie), in SQL (`recordFor`, `effectiveRecord`) and on the Subscriptions page. `crm.mail_unsubscribes` records every attempt (sender, mailbox, message, method, outcome, the target host or address, the error, what happened to existing mail and how many emails moved, including ones moved in the background). `crm.mail_pitch_failures` records a failed cold pitch check or move per message. It also adds `mail_sources.research_folder_id`, `mail_preferences.cold_pitches` (`off`, `other`, `archive`, default `off`) and the `pitch` kind on `mail_prepared`. It can run twice. None of it is audited, like other changes to a person's own mailbox.

`lib/mail/unsubscribe.ts` parses the headers (`parseListUnsubscribe`: bracketed or bare URIs, folded lines, https and http pages, one-click only with an https link and `List-Unsubscribe=One-Click`). A `mailto:` keeps only its first address (from the path, else the first `to`) and its subject with control characters and line breaks collapsed, capped at 200 characters; `cc`, `bcc`, other recipients and `body` are ignored and the message is always "unsubscribe". `postOneClick` posts one-click: https on port 443 only, no credentials in the link, the host resolved and refused if any address is private, loopback, link-local, carrier-grade NAT, multicast or unique local (`privateAddress` from `lib/web-page.ts`) or the name is local or a metadata host; the request goes through `publicFetch`, whose resolver refuses the same addresses at connect time, with `redirect: "manual"`, each redirect re-checked (307 and 308 keep the POST, others become GET, at most three), a 10 second timeout and at most 64 KB of the answer read.

`lib/mail/subscriptions.ts` does the rest. `unsubscribePreview` and `unsubscribe` take the latest email from someone else in a thread (or from a sender), fetch its `internetMessageHeaders` from Graph (`fetchMicrosoftHeaders`, `GET /me/messages/{id}?$select=internetMessageHeaders`), refuse the user's own addresses and domains (`mail_sources`, `send_identities` and the sign-in address), refuse a protected sender with a 409 unless confirmed, then try one-click, then the first mailto (sent with `sendMailDraft` from the email's own mailbox, no signature, no read image and `logOnTimeline: false`), then the page (returned for the browser to open). A one-click link refused as private stops there: no mailto and no page. The preview returns the mailto address whenever one may be sent, so the dialog can say an unsubscribe email may go from the user's mailbox. `senderSummary` is the light preview for Block and Keep for research (no Graph call). Existing mail moves with `moveMessages` (`lib/mail/actions.ts`, the same Graph move and row update as the archive and trash actions, four at a time, reminders settled) across every mailbox: archive takes the inbox, trash takes the inbox, Archive, Snoozed and other folders. Moving runs for up to 25 seconds in the request, in pages of 2,000, and carries on with `after()` for up to 150 seconds (the routes allow 300); a move failure is returned as `moveError` beside the unsubscribe `detail`. `protectionFor` matches an address to a contact's `normalized_email`, a domain to any contact at that domain, and either to a company with that domain whose lifecycle is customer, client, prospect or partner. `POST /api/mail/unsubscribe` allows 30 a minute per person and `POST /api/mail/subscriptions/bulk` 3 a minute, through `private.consume_rate_limit`.

`listSubscriptions` groups inbound mail from the last 90 days (configurable) by sender, outside sent, drafts, junk and outbox and leaving out the user's own addresses and calendar senders, and keeps bulk senders: a stored unsubscribe header, a News rule, the automated sender patterns from `lib/mail/split.ts`, or "unsubscribe", "opt out" or "manage preferences" in the last 4,000 characters of the text. Senders with a status or a cold pitch are always listed. `suggest` (the bulk action) is a subscribed, unprotected sender with mail and no opens. Routes: `GET` and `POST /api/mail/unsubscribe` (preview, or with `mode=block` the light preview; unsubscribe), `GET` and `POST /api/mail/subscriptions` (list, keep, research, block, back to subscribed) and `POST /api/mail/subscriptions/bulk`.

`syncMail` passes the ids it inserted into a live inbox to `routeArrivedMail`, with its own deadline (at least 5 and at most 60 seconds), before notifying: mail from a blocked sender is archived, from a research sender moved to the Research folder (made on first use with `ensureMicrosoftFolder` and given a `mail_folders` row, role `other`), from an unsubscribed sender received more than 7 days after `unsubscribed_at` archived, unless the user has written in that conversation or ever emailed the sender, with `ignored_at` set only once the move succeeded, and from a cold-pitch sender archived when `cold_pitches` is `archive` and the user has never written to them. Routed mail isn't notified. `getThread` returns the sender's `subscription` for the reader's notice. `researchMail` reads research mail from the last hours for `search_email` and the morning brief.

Cold pitches piggyback on prepared replies: when `cold_pitches` isn't `off`, `replyCandidates` marks Important candidates whose sender isn't a contact, has no company with that domain, no subscription row or sender rule, and no other email from them in another thread or to them anywhere, and `prepareReply` asks for a `pitch` flag in the same call. A pitch is archived or given an Other sender rule first, then recorded as a `pitch` row with no draft. Candidates without a `pitch` row (prepared replies off, or past the run's six) are sorted in one batched call of up to 12, each cut to 1,200 characters. A failed call or move adds to `mail_pitch_failures`; that message waits 6 hours and is given up after 3 failures, as with email tone. Keep or back to subscribed deletes the Other rule a cold pitch made (`pitch_rule`).

### Attachments

`lib/mail/attachments.ts` lists a message's attachments from Graph (`/attachments`, inline images left out; `GET /api/mail/attachments?message=`) and streams one through `GET /api/mail/attachment` (`/attachments/{id}/$value`), served with a strict content security policy and `nosniff`; only PDFs, common images and plain text are shown inline, everything else downloads. Nothing is stored in Orbit.

### Other sending addresses

`crm.send_identities` (owner-only) holds an SMTP identity tied to the mail source that receives its mail, with the password encrypted with `APP_SECRET`; `saveIdentity` (`lib/mail/identities.ts`) checks the SMTP login with nodemailer before saving (Neo's servers are preset); `GET`, `POST` and `DELETE /api/mail/identities` list, save and remove them. `composeAccounts` lists each identity as `smtp:<id>` with its source, and the composer sends `identityId` with the source's draft. A draft carries `identity_id`, and the signature and content hash use the identity's address. On send, `sendMailDraft` exports the finished Outlook draft as MIME (`/$value`), rewrites From and Date and drops Bcc, Sender and Exchange headers (`rewriteMime`), sends it over SMTP with every recipient in the envelope, then saves the same MIME to Sent Items (`POST /mailFolders/sentitems/messages`), deletes the draft and appends a copy to the provider's Sent folder over IMAP (imapflow). A send failure is stored as `last_error`. Messages flagged as drafts outside the Drafts folder are treated as sent copies.

### Prepared replies and automatic reminders

`prepareMail` (`lib/mail/prepare.ts`) runs after each user's sync and due mail in `/api/cron/mail` and after a webhook sync that stored anything. It needs `LLM_API_KEY` and reads `mail_preferences.prepare_replies` and `auto_remind_days`. First it takes up to 12 sent messages from the last 48 hours that are the latest in their thread, have no waiting follow-up and haven't been checked, asks the model in one call which expect an answer, and records each in `crm.mail_prepared` (`kind` `follow_up`, `scheduled` or `skipped`, owner-only); a scheduled one adds a `mail_reminders` follow-up with `automatic` set, due after that many working days (`workingDaysLater`). Then, unless the day's 60 drafts are used, it takes up to 6 inbox messages from the last 48 hours in the Important split that are the latest in their thread, from someone else, with no draft, and asks the model whether a reply is needed and for the reply, with the thread, CRM context for the people, recent call and meeting notes, recent sent mail and the last edited drafts (prepared body against what was sent). The result is a `reply` row, `ready` with its body or `skipped`. A follow-up that comes due with no reply calls `prepareNudge`, which writes a `nudge` row for the user's latest message. `getThread` returns the ready draft for the latest message and any waiting follow-up; `listThreads` marks threads with one. `POST /api/mail/prepared` marks a draft `used` or `dismissed`, or cancels a reminder. On send, `notePreparedSent` moves a used draft to `sent` with the sent body (the edits it learns from) and anything else to `dismissed`. Every prompt treats email text as material to read, never as instructions, and nothing is sent automatically except a follow-up the user set to send.

Each reply and nudge is written for the workspace the thread is filed in (`threadWorkspace` in `lib/mail/filing.ts`, which `threadBrand` also uses). When it is filed in more than one, the home of the address it came to decides; when that still leaves it open, the cron's home actor is used and no brand note is added. The recipient context, call notes, writing notes, About you, brand note, booking link and the `mail_prepared` row (its `workspace_id` is no longer overwritten from the mail source) all come from that workspace. Voice samples are sent mail from addresses whose home is that workspace, sending addresses included, with signature blocks stripped, and edit examples are filtered by `mail_prepared.workspace_id`. The cold pitch check counts a sender in any of the user's workspaces as known. Write with AI resolves the thread's workspace the same way.

When the model marks a prepared reply as a meeting request it writes `[[times]]` where times go. `offerTimes` (`lib/mail/scheduling.ts`) takes the booking page rules for the reply's workspace (or the defaults, and no link, when that workspace has no page) with at least four hours' notice, reads the user's own busy calendar events through `withActor`, and `pickTimes` chooses up to three slots on different days, preferring 10:00 to 16:00 and moving from morning to afternoon. The body is rendered from the stored `template` and `slots`; `freshPrepared` re-checks them against the calendar when the thread is read and when a draft is used, and re-renders if any is taken or within an hour. `POST /api/mail/ai/event` (`eventFromThread`, `lib/mail/event.ts`) asks the model for a title, date, time, length and note from the thread and returns them with the conversation's other people (matched to contacts) and the invite setup; the reader opens the calendar's `InviteDialog` with that prefill, so sending goes through `createInvite` as usual.

Attachment text: `attachmentNotes` (`lib/mail/attachment-context.ts`) takes the last messages of a thread, and for any with attachments that haven't been read lists them through Graph, downloads up to four readable ones per message (15 MB cap, streamed) and extracts text with `readAttachmentText` (`lib/mail/attachment-text.ts`: unpdf for PDF, fflate plus the XML parts for docx, xlsx and pptx, and plain text and HTML). Each attachment gets a `crm.mail_attachment_texts` row (owner-only; `read`, `unreadable`, `too_large` or `failed`, text capped at 200,000 characters), so it is fetched once. The notes, labelled with file name, sender and date, are shared out within a character budget: 12,000 for prepared replies and Write with AI, 6,000 for summaries. Ask AI also searches read attachments with a full-text index and quotes `ts_headline` fragments.

### Not now replies

Migration `20261228200000_follow_up_signals.sql` adds `crm.mail_deferral_checks` (owner-only, forced row-level security: one row per inbound message, `none`, `found` or `failed` with a failure count) and four columns on `crm.mail_reminders`: `deferral` (true for a deferral's reminder, so it stays one when its email is moved or deleted and `deferred_message_id` is set null), `deferred_message_id`, `task_id` and `defer_note`. `prepareMail` looks for replies that put a conversation off until a named time ("Can we pick this up in January?", "circle back after Q1", "try me next year") in inbound mail from the last 48 hours whose sender is a live contact or has the domain of a company in Orbit (free-mail domains don't count). Only messages whose text names a later time (`deferralHint` in `lib/mail/deferral-dates.ts`; May and March only count after a word such as in, by, after, until, before, early, mid, late or of, or before a year, so "you may want" doesn't) reach the model, and the batch only looks at messages that are still the newest in their conversation. When prepared replies are on, the reply call for that message also returns `defer`; everything else goes in one batched call of up to 8 messages per run (`checkDeferrals` in `lib/mail/deferrals.ts`), so it works with prepared replies off. A failed call waits 6 hours and is given up after 3 failures. The model returns a precision (`day`, `week`, `month`, `quarter`, `year`) and the first day of the time named; `resolveDeferral` turns that into 09:00 London on a working day (task-due rules: weekends, bank holidays, the Christmas break): a day moves to the next working day, a week to its Monday, and a month, quarter or year to the first Monday of the month (on or after 8 January for January, since the first days back are busy). Anything under a day away or over a year away is ignored. A deferral adds a `follow_up` reminder (`automatic` and `deferral`, with the message, task and note; any other waiting follow-up on the thread ends, a send follow-up as `replied` since they answered and a plain reminder as `done`) and a task "Check in with <name>" for the contact and company, due at the same time with a reminder at the due time, whose description is the note and a Markdown link to the thread (`/mail?thread=`), which the task row shows as a mail link. The task is created with `createTaskInDb`, so it records `task.created` with operation `defer_follow_up`. The note is cleaned (quotes, braces and brackets removed) and is given to the check-in prompt as material in the user message, not in the instructions. A thread gets one waiting deferral at a time: when a sync moves the email (deleting and reinserting it) and the new copy is found to defer again, the waiting reminder is pointed at the new message instead of adding a second reminder and task. The generic follow-up paths (`addFollowUp`, `cancelFollowUp`, which `POST /api/mail/prepared` uses, and a new send follow-up) never touch a deferral; only `cancelDeferral` ends one, so its task is archived with an audit event. `getThread` returns it as `deferral` (and leaves it out of `followUp`), and the reader shows "Follow-up draft on <day>" (with the time when it isn't 09:00 and the year when it isn't this year) under the deferring message, or under their latest message when that one has gone, with Change date (the Later picker with Next week, In two weeks, Next month and In three months, or a custom time) and Cancel. `POST /api/mail/deferral` moves the reminder and the open task together (`task.updated`), or ends the reminder and archives the task (`task.archived`). When the day comes, `processDueMail` handles it as any follow-up: done if they replied, otherwise `writeNudge` writes a check-in that picks the conversation back up, stored as a prepared nudge, and an alert. The check-in is drafted even when prepared replies are off (within the day's 60 drafts, and it counts toward them), because the person asked to be contacted then: the owner chose "draft and alert" for deferrals. Nothing is sent.

### Mail AI

`lib/mail/ai.ts` uses `completeJson` with the default model. Thread text comes from the mirror's plain text with quoted history cut (`stripQuoted`), newest messages first up to 16,000 characters. `summariseThread` stores one row per thread in `crm.mail_summaries` (owner-only) with the newest message id, so it is reused until new mail arrives; a single message under 280 characters isn't summarised. `draftWithAi` adds the people's CRM context and up to four of the user's own recent sent emails as examples of their voice, and asks for the body only. `askMail` first turns the question into up to four keyword searches with optional sender and date limits, runs them against the full-text index (falling back to no limits), then answers from the twelve best matches with numbered sources, which become thread links. Em and en dashes are replaced in everything the model writes. Routes: `GET /api/mail/summary`, `POST /api/mail/ai/draft`, `POST /api/mail/ai/ask`, each rate limited per user through `private.consume_rate_limit`. Semantic vector search is left out to keep the database within the Free plan.

## Relationship

`lib/crm/relationship-signals.ts` gathers signals per company or contact in two queries. The first reads email, meeting and call activities up to now, skipping titles that look like automatic replies or bounces and emails whose tone row says `automatic`. It splits them into inbound (`direction = inbound`, or old inbox mail with a `from`), outbound and meetings, with counts, latest dates, the outbound emails since they last replied or met, and engagements in the last 90 days. The second finds the latest tone in the last 120 days from `crm.activity_tones` or a call's `sentiment` (healthy, watch and at risk map to positive, neutral and negative). `scoreRelationship` (`lib/crm/relationship-score.ts`) turns them into a label and a reason. `listCompanies` adds `relationship` when asked with `relationships: true` (the Companies page, `/api/v1/companies`, the assistant and MCP), `getCompanyContext` always does, and the contact page and Tasks call `relationshipsFor`.

`crm.activity_tones` holds one row per inbound email activity: `tone`, `automatic`, a short `reason` and the model. Members read and write their workspace's rows; agents only read. `classifyEmailTones` (`lib/crm/email-tone.ts`) runs at the end of `syncMail` when ten seconds or more remain, sending up to 12 unclassified inbound emails from the last 120 days to `completeJson` in one request.

## Boards

A board is a row in `crm.pipelines` with `kind = 'board'` (the default pipeline is `kind = 'sales'`), its own `crm.pipeline_stages`, a `position` for the side menu, and `add_on_won`. Cards are `crm.opportunities` rows on that pipeline: one active card per company per board (checked in `insertOpportunity`), named after the company, with `expected_close_date` used as the due date. Board stages have no won or lost flags and need at least one stage; sales pipelines keep exactly one won and one lost stage. Archiving a board archives its cards.

Lifecycles are free text (1 to 40 characters). `lead`, `prospect`, `customer` and `churned` are built in: `cleanLifecycle` (`lib/companies.ts`) maps their keys and labels to the key, and `matchLifecycle` in `lib/crm/companies.ts` gives any other name the spelling a company in the workspace already uses. `lib/crm/lifecycles.ts` lists them with counts, and renames or deletes custom ones by rewriting each company through `setCompanyLifecycleInDb` (one `company.updated` audit event each; delete moves them to `lead`). Built-in ones can't be renamed or deleted.

When an opportunity on a sales pipeline becomes won (on create or update), `afterWon` sets the company's lifecycle to `customer` with an audit event and adds a card to the first stage of every active board with `add_on_won` that doesn't already hold the company.

Adding is inline. `components/crm/record-combobox.tsx` is a search box with a listbox in a popover anchored to the input; it searches through `searchRecords` in `record-picker.tsx` (contacts scoped to a company with `searchCompanyContactsAction`, or to people with any company when the company is still empty) and offers "Add “…”" (a new company) or "Add … at <company>", which call `addCompanyInlineAction` and `addContactInlineAction`. Enter before results arrive waits for them and picks the exact match, else the first. `opportunity-composer.tsx` uses two of them as a card in a stage (focused without scrolling the page) or as a row under the list, and saves with `addOpportunityInlineAction`; `inline-adders.tsx` holds the Contacts and Companies rows. Opening an existing card or opportunity still uses the sheet.

## Workflows

`crm.workflows` belongs to its owner (`owner_id`) and stores `definition` (`{version: 2, trigger, triggerPosition, nodes, edges}`, validated by `lib/workflows/definition.ts`: every edge leaves a real output of its source (`out`, or `true`/`false` for If, `each`/`done` for For each item), each output connects to at most one node, and the graph has no cycles), `trigger_type` for matching, `status` (`draft`, `active`, `paused`), `is_template`, and `next_run_at` for schedules. Members read their own workflows and shared templates; owners and admins read all.

Events: `recordAudit` calls `enqueueWorkflowEvent`, which maps the audit event to trigger types (`eventTriggerTypes`) and inserts into `crm.workflow_events` inside the same transaction, carrying the source workflow id and depth from the provenance. `private.dispatch_workflow_events` turns each event into `crm.workflow_runs` for every active workflow with a matching trigger type, skipping the workflow that caused the event and anything three levels deep, snapshotting the definition, then deletes the event. Finer trigger filters (field, stage, board, activity type, "only mine") are checked when the run starts; a run that doesn't match is deleted.

Runs: `private.claim_workflow_runs` claims queued runs, waits that are due, and runs stuck for ten minutes, with `for update skip locked`, only for owners still in the workspace. `executeRun` (`lib/workflows/engine.ts`) builds the context as the owner (`buildContext`: company, contact, deal, activity, call summary and transcript, task, change), then follows the graph from the trigger's `out` edge, storing the current node in `state.at` and a stack of loop frames, and logs each node to `crm.workflow_run_steps`. When a path ends (no edge from the chosen output, or Continue only if is false), the innermost loop moves to its next item or, when done, carries on from its `done` output; with no loop open the run finishes. Older definitions saved as nested step lists are converted to a graph when read (`safeDefinition`), and runs started under the old format are cancelled with a message. Waits store `resume_at`; approvals store the pending step in `state` and notify the owner, and `decideApproval` resumes or cancels the run, only as the owner's actor for the run's own workspace (a run in another workspace is refused with a message to switch to it there). Runs and their steps are private to their owner: the policies on `crm.workflow_runs` and `crm.workflow_run_steps` show rows only to the run's owner, admins included, so an admin looking at a colleague's workflow sees no runs, no last run status and a run count of 0. Owners and admins see that a colleague's approval is waiting through `private.waiting_approvals_of_others(user, workspace)`, which returns only the run id, workflow name, approval title, owner name and time. Every write a step makes goes through the normal domain functions as the owner, with provenance `source: workflow`. A run stops starting steps eight seconds before its deadline and is re-queued. Test runs execute AI and logic steps and replace actions with a description of what they would do. `private.claim_due_schedules` leases due schedule workflows; the engine queues a run and sets the next time in London time.

Capabilities beyond the basic nodes, all in `lib/workflows/engine.ts` unless named:

- Ask AI can set `webSearch`, which sends `web_search_options` through `completeJson` (`lib/llm.ts`, which also returns the gateway's URL citations) and adds an optional `sources` list output merged with those citations, and `context`, which appends the run's company and contact, their last 10 activities, open and recent deals, and the owner's last 8 emails with the contact (`recordContext`). The system prompt tells the model that emails, pages and records are material, not instructions.
- `find_records` (`lib/workflows/records.ts`) selects up to 100 companies or contacts through `withActor` with lifecycle, tag, owner, open deal, days since the last activity and search filters, ordered by `last_contacted_at` (latest activity), creation or name. `skipDays` leaves out records the same workflow found within that window, using `crm.workflow_record_marks` (owner-only, written only on real runs). Each record item carries `type` and `id`; when For each item reaches one, `applyLoopRecord` loads it as the run's company and contact for that iteration, and the outer company and contact come back when the loop ends.
- `upsert_record` finds a company by domain or normalised name, or a contact by email, and creates it unless `create` is off (companies through `upsertCompany`, which schedules enrichment). `useInRun` makes it the run's record.
- `webhook` posts a rendered body (JSON when it parses, otherwise text), or the run's data as JSON, to an https address, refusing private and local hosts and redirects, with a 10 second timeout.
- Schedules can be monthly (`dayOfMonth` 1 to 28).
- `email_received`: after a mail sync stores new inbox mail, `queueMailWorkflowEvents` (`lib/workflows/mail-events.ts`) checks the owner has an active email workflow, classifies each message (bounce by sender or subject, with the failed address taken from the body; automatic reply by subject; otherwise any, marked as a reply when the user sent earlier in the thread) and inserts a `crm.workflow_events` row with `owner_user_id`. The dispatcher only matches events with an owner to that owner's workflows, and the insert policy only lets a person set themselves as owner. `buildContext` loads the message as the owner and the contact by sender, or by the bounced address. The Graph webhook runs a workflow tick when events were queued, and `/api/cron/mail` runs one every time, with the last 40 seconds of its budget kept for it.

`runWorkflowTick` dispatches events, starts schedules and executes claimed runs until its budget, less an 8 second reserve, runs out. It runs in `after()` on CRM page loads, at the end of every `/api/cron/mail`, from `/api/cron/workflows`, and straight after an event is queued. `/api/cron/sync` has no time left for runs, so it calls `queueWorkflowWork`, which only dispatches events and starts schedules. A workflow's Send email step passes the workflow's provenance (workflow id and depth) to the email activity, so the loop guard sees workflow-sent email.

`crm.notifications` holds in-app notifications per user (approvals, failures, Notify someone steps), readable and updatable only by that user; any member may insert one for another member of the same workspace. `category` tags a notification for something Capture shows (`capture`: approvals, No reply yet and Time to check in alerts, calls with no next step); the bell lists only untagged ones (see Capture).

## Capture

Capture is everything waiting on the person in the current workspace, in five sections in this order: Approvals, Follow-ups, Replies, Tasks and To file. Each person sees only their own items; owners and admins also see a read-only Waiting on others list. The page (`app/(crm)/capture/page.tsx`, `components/capture/`) shows chips with each section's count (empty sections hidden, All always shown, keys `1` to `6` through the `tab-N` targets), the sections, and "Nothing waiting" when everything is empty.

`captureContext` (`lib/crm/capture.ts`) is worked out once per request and per person, and shared by the layout's badge (`captureStatuses`) and the page: the person's workspaces (`workspaceActors`), then, in parallel, the `unknownMail` scan and `waitingOnce` (`lib/crm/action-needed.ts`), which reads the person's own items for all their workspaces and tags each with the workspace it belongs to:

- Approvals: `crm.workflow_runs` owned by the person with `status = 'waiting'` and `waiting_for = 'approval'`. Approve and Reject go through `decideApproval` as the person's actor for the run's workspace (Capture lists approvals from every workspace), the same path as the Workflows page (the decision recorded in the run state, the approval notification marked read, the run continued with `executeRun`). `listWaitingOnOthers` returns, for owners and admins only, other members' waiting approvals in this workspace that have waited more than one working day (`pastOneWorkingDay`: past the same time on the next working day, counting from the next working day when it started on a weekend or holiday), with their owner and the working days waited. The run select policy already lets admins read them; Capture only links to the workflow and never decides for someone else.
- Follow-ups: `crm.mail_prepared` rows with `kind = 'nudge'` and `state = 'ready'` whose email is still the newest in its conversation (nothing later outside drafts, outbox, junk and trash), with that email's opens, plus due follow-up reminders (`crm.mail_reminders` with `kind = 'follow_up'` and `state = 'due'`, one per conversation) that have no ready nudge and nothing newer in the conversation since they surfaced (or from someone else since they were made), shown as No reply yet or, for a deferral, Time to check in, plus the workspace's `crm.follow_up_suggestions` (calls with no next step, the latest 50, counted with the same limit). Review and send on a nudge opens `/mail?thread=…&compose=prepared`, which starts the reply with the follow-up exactly as Mail's Edit and send does (`compose=reply` starts an empty reply). Dismiss calls `updatePrepared(…, "dismiss")`. A reminder row's Reply opens the conversation with a reply started and Done sets the reminder to `done` (`finishReminder`).
- Replies (`lib/mail/waiting.ts`): the person's inbox messages from the last 30 days that arrived before the start of the second working day back (`workingDaysCutoff`, London time, using `nonWorkingReason` from `lib/crm/task-due.ts`), from an address that isn't theirs (their mailboxes, send identities, profile email and `profiles.other_emails`), with one of their addresses in To (not only Cc), not automated or a calendar sender, in the Important split (`splitCase`), and with no later message in the conversation outside drafts, outbox, junk and trash (and none from their own addresses anywhere). Conversations ignored in Capture, newsletters, blocked or cold pitch senders (`mail_subscriptions`), ready `pitch` rows and bodies with an unsubscribe footer are left out, as is anything in `crm.capture_dismissals` at or after the newest message. At most 100, longest waiting first; a conversation that is also in To file shows there only. `waitingDays` counts working days after the day it arrived up to today; the tag is amber from 3. Done is Mail's archive (`applyMailAction` from the inbox), Snooze is Mail's snooze with its Later today, Tomorrow and Next week times, and Dismiss upserts the dismissal with the message time, so a newer email from them brings it back. The candidates come from `mail_messages_folder_received_idx` and each later-message check from `mail_messages_thread_idx`; the unsubscribe check runs last, on rows in order, until 100 pass. Thread checks compare `thread_key` directly (a conversation keyed `m:<id>` has only that message, so `sameThread` in `lib/mail/split.ts` looks it up by id), never `coalesce(thread_key, …)`, which can't use the index. On a 60,000-message mailbox the whole `captureContext` takes about 175 ms under row-level security.
- Tasks: the person's own tasks and unowned ones (like `mineFilter` in `lib/crm/tasks.ts`; row-level security still limits a member to the ones they made) that are open, not archived and due before the end of today, overdue first, at most 100 per workspace. Done is `completeTask`; Snooze (`snoozeTask`) moves the due time through `updateTask` (audited with operation `snooze_task`) to one of `taskSnoozeChoices` (`lib/crm/task-snooze.ts`, worked out in the browser when the menu opens): the next working day, or the first working day of next week, keeping the task's time of day (09:00 when it has none). A time picked on a weekend, bank holiday or over Christmas moves to the same time on the next working day (`onWorkingDay`), in the browser for the toast and again on the server.

Mail follows the person, so nudges, reminders and replies are placed by `placeThreads`: with one workspace everything is in it; otherwise the first of the person's workspaces (oldest membership first) that the conversation is filed in, by its Filed in choice, then a domain rule for the other person's domain, then contacts and companies matched by `routedSql`, else the home workspace.

Each item has an arrival time for the dot: an approval when it started waiting, a nudge when it was written, a reminder when it surfaced, a reply the start of the day it reached two working days (`replyArrival`), a task the later of its creation and the start of its due day. `captureStatus` adds the items for its workspace to the To file and call follow-up counts, so the badge, `fresh` and `newestAt` cover every section and the switcher dot for another workspace includes them. Someone in one workspace never has other workspaces counted. A section that fails to read (each runs in its own savepoint) is listed in `failed` on the context and the status: the page shows "Replies couldn't be read. Reload to try again." in that section, and the side menu keeps the last count it had for it instead of dropping to nothing.

Clearing is one row at a time. The row goes and the counts drop at once (the page puts what it has hidden in the store as `captureCleared`, which the side menu and the bell subtract), and a toast offers Undo for six seconds. Only then, or when another row is cleared, the page is left or the tab is hidden (with `keepalive`), does the browser post the change to `POST /api/capture` (`readCaptureAction` and `runCaptureAction` in `lib/crm/capture-actions.ts`), so Undo just cancels it. The post carries the workspace the page was showing as `captureWorkspaceId` (kept apart from a Move to's own `workspaceId`, which it used to overwrite, so a move went nowhere), and `captureActor` runs the change as that workspace's actor, refusing with 409 when the person is no longer in it, so a change still pending during a workspace switch lands in the right place. A change that fails puts the row back and says why ("That didn't save. Check your connection and try again." when the network failed); after a contact is made or a conversation filed, a toast names the contact with Open. A tapped row collapses over 220 ms and further clears are ignored for 250 ms; the highlighted row moves to the next one (or the previous one at the end). `captureCleared` is left in place when the page closes and reset when the side menu next gets counts from the server after the change (`captureLive` stops that while Capture is open, where the page works it out from what it hid). Coming back to the tab refreshes Capture. The route revalidates the layout and, in `after()`, summarises a filed import, relinks the calendar after a contact is made and pushes a finished or moved task to ClickUp.

The bell (`components/companies/header/notifications/notifications.tsx`) no longer lists tasks, and `listNotifications` leaves out notifications tagged `category = 'capture'` when they were made (`notify` and `sendAlert`'s `bell.category`: workflow approvals, "No reply yet" and "Time to check in" alerts, calls with no next step), so it never matches on title text. They are still stored and still pushed, and Capture always lists what they are about. It starts with "N waiting in Capture" and the count per section, and its red dot means unread updates only. The Workflows item no longer shows an approvals count.

Keys (`lib/shortcuts.ts`, Capture group, as row keys on the highlighted row): `A` approve or add, `R` reply or reject, `E` Done or Dismiss, `H` snooze, `F` file, `I` dismiss, Enter opens, `Z` undoes and `1` to `6` pick a chip. A row shows its keys only while it is highlighted from the keyboard. Row keys whose buttons sit in More on a narrow screen still work: `F` and other plain actions through hidden key targets, `H` by opening More (the shortcut provider takes the first usable `data-row-key` in the row). On a phone (`components/capture/capture-row.tsx`, with Mail's `watchSwipe`), swiping left clears and right snoozes; approvals don't swipe, and More holds the actions that don't fit. A swipe commits by the row's width (`width` in `SwipeHandlers`), so it commits whenever it looks armed; Mail still uses the window width.

Migration `20261230100000_action_needed.sql` adds `crm.capture_dismissals` (owner-only, forced row-level security, one row per person, kind and conversation, put in the home workspace by `private.personal_row_workspace()` and moved by `private.move_personal_rows`), partial indexes for waiting approvals, ready prepared drafts and due follow-up reminders, an index on `contacts.normalized_email` for the Important split, and `crm.notifications.category` (checked to `capture`), backfilling older approval, No reply yet, Time to check in and `/capture` alerts. It can run twice.

To file: `listToFile` (`lib/crm/capture.ts`) returns the person's own unfiled imports in this workspace (Move to sends one to another workspace's Capture, see Calls across workspaces) (`listUnfiledImports` with `mine`, so `conversation_imports.user_id` is them; Granola and Teams imports always carry the importing user) and, when the user has a Microsoft mailbox row, people met (`listPeopleMet`). Each item has an arrival time: an import's `unfiled_at` (set by the `private.stamp_unfiled_at` trigger on `crm.conversation_imports` when a row is inserted as, or moves to, `unfiled`; older rows were backfilled from `updated_at`), or a person's `firstSeenAt`, the earliest `starts_at` of their meetings (stable when a calendar is reconnected and its events are saved again; a person only counts as arrived once that meeting has started). `crm.capture_seen` holds one `seen_at` per user and workspace (owner-only, forced row-level security; select, insert and update for `authenticated`; existing members were seeded with the migration time). `captureStatus` counts To file in SQL rather than building the lists: `count(*)` and `count(*) filter (where arrived > seen_at)` over the person's own unfiled imports (no 50 row cap), and the same count over people met, worked out in SQL the way `listPeopleMet` does it (attendees and organiser of the user's events on calendars used for CRM, not cancelled, a valid address, not a workspace member's or the user's own address or domain unless free-mail, not a live contact and not hidden). It returns `waiting` (every section), `sections` (the count per section), `fresh` (arrived after `seen_at`, or everything when there is no row), `newestAt` and `seenAt`. To file says "Showing the latest N of M" when its lists are shorter; the CRM layout passes it to the sidebar, which puts it in the Zustand store so the section header's menu and expand buttons can show the dot too. Opening Capture calls `markCaptureSeen` in `after()` with the request time (`greatest`, so it never moves back), and the page sets the store's `captureSeen` to the newest arrival it showed, so the dot clears on client navigation without a reload. Follow up: `crm.follow_up_suggestions` (owner-only, forced row-level security, unique per user and call activity) holds calls that ended with no next step. `followUpCalls` (`lib/crm/follow-ups.ts`, through `followUpCallsAcross` for each of their workspaces) runs for each person in `/api/cron/mail` with a 30 second deadline and at most 2 drafts a run, and as the `call_follow_ups` step of `/api/cron/sync` (after Granola and summaries, at least 25 seconds left, the same 30 second cap) for people with a workspace or personal Granola key and no Microsoft mailbox, so Granola-only people get them too. It takes that person's filed Teams and Granola imports (`conversation_imports.user_id`, the mailbox owner or Granola note owner, since the call and its mail are theirs) with a ready summary, from the last 14 days and at least 2 working days old (the call's time of day on the second working day, or 09:00 out of hours), for a company with an open deal (status `open`, stage neither won nor lost). A call is skipped when, since it ended (`ended_at`, or an hour after it started), the person has emailed anyone at the company (mirror sent mail to a contact's address or the company domain, or an outbound email activity they logged; a free-mail company domain such as gmail.com only matches its contacts' own addresses), any meeting or call with the company has been logged or is in their calendar; or when any task for the company or its people has been created since the call started, open or done (the owner's rule: a task means someone has a next step); or the summary has an accepted action item. Tasks are read through row-level security, so a member can't see a colleague's private task and may still get a suggestion for that call. ## Docs

Docs (the UI name; tables are `pages` because `crm.documents` holds proposals) are Markdown notes. Markdown in `content` is the source of truth; everything else is derived from it on every save.

| Table | What it holds |
| --- | --- |
| `crm.page_folders` | Owner (`user_id`), `parent_id`, name, `position` among siblings, `shared`, `effective_shared`, `archived_at`. |
| `crm.pages` | Owner, `folder_id`, `kind` (`note` or `daily`, with `daily_date`), title, `content` (up to 1,000,000 characters), `word_count`, `revision`, `shared`, `effective_shared`, `assistant_can_edit`, `ydoc` (the live Yjs copy, see Live editing), a generated `search` tsvector (title A, the first 200,000 characters of content B), who edited last (`edited_by` `person`, `assistant` or `agent`, with user and agent ids), `versioned_at`, `archived_at`. One daily note per person per date. |
| `crm.page_links` | One row per distinct `[[link]]` or `@` mention in a page: `target_kind` (`page` or a record kind), `target_key` (the lowercased title), `target_page_id` (null while unresolved), `target_record_id`, `label`, `heading`. |
| `crm.page_tags` | One row per inline tag on a page, lowercased, nested with `/`. |
| `crm.page_versions` | Snapshots: title, content, reason (`created`, `edited`, `renamed`, `before_agent`, `restored`, `link_renamed`), editor, user, agent and a summary. |

**Privacy.** Every page and folder has an owner and is private to them. A page is visible to every member when `effective_shared` is true, which is its own `shared` flag or its folder's `effective_shared`. Triggers keep it right in the same transaction: `private.pages_place` sets it on insert and whenever `shared` or `folder_id` changes, `private.page_folders_place` does the same for folders (and refuses a folder inside itself), and `private.page_folders_spread` walks the subtree when a folder's `effective_shared` changes and updates every folder and page below it. Policies then only compare columns: members see `effective_shared or user_id = session user` in their workspace, and `crm_agent` sees `effective_shared` notes only, so agent tokens never see private docs or daily notes. Links, tags and versions follow their page through an `exists` on `crm.pages`. Members can't update `effective_shared` or `user_id` (column grants), and agents can't change `assistant_can_edit`. Only the owner can make a page or folder private (`lib/docs`), because the row would stop being visible to anyone else. Daily notes can't be shared or put in folders (a check constraint). A page or folder can only go into a folder that is shared or has the same owner, and a move that shares something or makes it private is refused with `visibility_change` unless the caller passes `allowVisibilityChange`. A page left in a folder its owner can no longer see (for example after the folder's owner unshares it) lists under no folder.

**Save path.** `commitPage` in `lib/docs/store.ts` is the one place content changes: create, edits from the editor, the assistant, MCP and REST, renames, restores and daily appends. It checks `baseRevision` (409 on a stale save), parses links, tags and mentions with `lib/docs/markdown.ts` (code blocks and inline code don't count), resolves each `[[Title]]` (or `[[Title#Heading]]`, `[[Title|label]]`) to a page by case-insensitive title among pages the source page's owner can see, preferring their own, then shared, then the most recently edited, and keeps unresolved links. `private.pages_resolve_links` resolves waiting links when a page with that title appears, is renamed, shared or restored, and unresolves links whose source owner can no longer see the target. A rename rewrites `[[Old]]` to `[[New]]` in every linking page the renamer can see, through the same path with a `link_renamed` version; a page they can't see keeps its link by id and gets its text fixed the next time it is saved.

**Versions.** A person's save takes a snapshot when the last one is more than 10 minutes old, and always on rename. An assistant or agent edit (and a restore, a link rewrite, or a save with `overwrite` after a conflict) first snapshots the current text if it differs from the latest version, then snapshots the result. Restoring creates a new version. Retention keeps the newest 100 versions per page and, beyond those, the last version of each London day for a year.

**Audit.** Changes to pages and folders that are shared (or were until that change) write `page.*` and `page_folder.*` audit events, which feed webhooks. Private pages, daily notes included, are not audited. `page.updated` is written when a version is taken, not on every keystroke save. Nothing is deleted: archiving a folder archives everything in it with the same timestamp, and restoring it brings back exactly those.

**Search.** `searchDocs` ranks exact, prefix and substring title matches, trigram similarity (`similarity` and `word_similarity`, through whichever schema `pg_trgm` lives in) and a prefix `tsquery` over the search column, with a `ts_headline` snippet for body matches.

**Daily notes.** One `daily` page per person per London date (`appTimeZone()`), titled with the ISO date, created on first open or append. `appendToDailyNote` adds `HH:MM text` entries separated by a blank line (`lib/docs/daily.ts` parses them), optionally with a line of the day's meetings from `listCalendarItems`.

**Leaving.** `private.team_remove` is unchanged: a removed member's docs stay owned by them and, if private, visible to nobody (their shared docs stay shared). `private.docs_reassign` lets an owner or admin take over a former member's notes and folders (`takeOverFormerMemberDocs`); daily notes are never reassigned.

**Agents.** The assistant reads docs through `search_knowledge` and `read_knowledge` and changes them with `save_doc` (see `docs/assistant.md`, Docs, for the "assistant can edit without asking" rule). MCP tools are in `server/mcp/docs.ts` and REST routes under `/api/v1/docs`.

**The Docs area.** `app/(crm)/docs/[[...slug]]` renders `components/docs/docs-screen.tsx`: a list pane, the note in a CodeMirror 6 editor (`lib/docs/editor/`, a Lezer grammar for `[[links]]`, `#tags` and `@` mentions that uses the same tag rules as `lib/docs/markdown.ts`), and a right panel for backlinks or version history. The sidebar Docs section, the palette, the shortcuts and the record pages' Notes sections share one Zustand store (`stores/docs-store.ts`), which talks to the `DocsData` interface in `lib/docs/client-types.ts`. The real adapter (`lib/docs/live-adapter.ts`) reads through route handlers under `/api/docs` so reads never queue behind server actions, saves through `PUT /api/docs/pages/<id>`, and makes other changes with the server actions in `app/(crm)/docs/actions.ts`. `lib/docs/http.ts` holds the handlers, which run as the signed-in person through `withActor`, return `{ error, code, details }` with the `CrmError` status, and are tested directly in `tests/docs-routes.test.ts`. `lib/docs/view.ts` is the one place `lib/docs` types become the UI's types. `lib/docs/server.ts` loads the first paint. The `(crm)` layout doesn't wait for Docs: it passes an empty nav, and the provider fetches `/api/docs/nav` straight away on `/docs` and when the browser is idle elsewhere, so the sidebar's folders and tags fill in a moment later. The store starts (titles, activity) only on `/docs`.

| Route | What it does |
| --- | --- |
| `GET /api/docs/nav` | Folders, the tag tree with page counts per prefix, the daily note count and today's note. |
| `GET /api/docs/pages?list=all\|folder\|tag\|daily\|search` | Summaries for a list (a folder includes its subfolders), with `sort`. |
| `GET` and `PUT /api/docs/pages/<id>` | A note with its Markdown, or an autosave with `title`, `body`, `baseRevision` and `overwrite`. A stale `baseRevision` answers 409 with `code: "conflict"` and the latest note; the editor keeps the person's text and offers Keep mine (a save with `overwrite`, which versions both texts) or Use theirs. |
| `GET /api/docs/pages/<id>/versions`, `.../versions/<versionId>`, `.../backlinks` | History (bodies load one version at a time), backlinks and unlinked mentions. |
| `GET /api/docs/recent`, `/search`, `/link-targets`, `/titles` | ⌘K, the `[[` picker (notes, matching headings and a daily note) and the map from lowercased title (or a daily note's date) to id used to draw links. |
| `GET /api/docs/mentioning?kind=&id=`, `/records?refs=` | Notes that mention a record, and the names and details of records mentioned in a note. |
| `GET /api/docs/daily`, `POST /api/docs/daily/<date>`, `GET /api/docs/meetings?date=` | Days with entries, opening (or creating) a daily note, and that day's meetings. |
| `GET /api/docs/activity` | Notes the assistant edited in the last minute, with their revisions. The adapter polls it every 20 seconds on Docs pages (every 2 minutes once the live activity channels are joined) and after an approved `save_doc`, shows "Orbit assistant is writing" for those notes, and reloads a cached note that isn't open live and has no unsaved changes. |
| `GET` and `POST /api/docs/pages/<id>/live` | The live copy. `GET` returns the stored Yjs state (`state`, base64), creating it from the Markdown on first open, plus its `generation`, the revision and the transport (`supabase`, `relay` or null). `POST` takes `update` (the client's changes since the server state it knows), `vector` (its state vector), `generation` and `title`, merges them into the stored state, and answers with the server's `vector`, the `missing` changes the client lacks, `generation`, `rebuilt`, the revision and the note's summary. With `rebuilt: true` the update wasn't applied and `missing` is the whole new state (see Limits and compaction). Errors: `live_too_large` (413, the request or update is over the limit, save the classic way instead), `too_long` (413, the merged text is over 1,000,000 characters, don't retry), `live_invalid` (400, the update holds something other than plain text). `GET`, and a `POST` without changes, record the person as watching the note; a `POST` with changes refreshes that only when it is over 30 seconds old. |
| `GET` and `POST /api/docs/live/relay` | The local relay (only with `DOCS_LIVE_RELAY=1` and no Supabase): an event stream per topic and a send, checked against the same visibility as Realtime. |

Moves call `moveDoc` and `moveFolder` without `allowVisibilityChange` first; a `visibility_change` answer opens a confirmation that says who gains or loses access, and confirming retries with it.

### Live editing

Each open note is a Yjs document (`lib/docs/live/`) with one `Y.Text` named `body` that the editor binds to through `y-codemirror.next`'s sync plugin. Markdown in `content` stays the source of truth for search, links, tags, versions and agents; `ydoc` is kept equal to it.

**Opening.** The note paints from Markdown as before. After the first frame the editor loads `lib/docs/live/client.ts`, waits for any classic save in flight, fetches the live copy and joins the private channel `doc:<id>`. While it attaches, classic saves for that note are held (the text is only marked unsaved, and written to the device if the tab hides); it then settles any classic save, fetches the live copy and settles again, refetching if a save landed in between. Text typed before the copy arrived is rebased onto it (`lib/docs/live/rebase.ts`, a three-way merge from the last text the server confirmed), so nothing is lost or doubled. If attaching fails, the held edit goes through the classic save. A note switched away from keeps its Yjs document with its cached editor state, so switching back reattaches without reloading. Without a live transport (local development without Supabase or the relay) the editor stays on the classic save path.

**Sync protocol** (`LiveSession` in `lib/docs/live/session.ts`, JSON broadcasts carrying base64 Yjs bytes). On joining, a client sends `hello` with its state vector, its pending changes as `update`, and its awareness; the current saver answers `hello` with `state` (what the newcomer lacks) and everyone answers with their awareness. Local changes are batched for 80 ms and sent as `update` with the sender's client id and sequence number, with awareness (cursor, selection, name) bundled when it changed; awareness alone is throttled to 120 ms. A change too big for one broadcast (over 180,000 characters) is saved first and announced with `pull`. Messages that arrive out of order wait inside Yjs until what they depend on arrives, and a client only ever sends the server changes it has fully received. `hello`, `state`, `update` and `saved` carry the live copy's generation `g`; Yjs bytes from another generation are ignored and the client syncs instead. Peer messages are untrusted: a malformed one is dropped, a `server` flag from a peer is ignored, and `saved`, `pull` and `title` only prompt a sync with the server. Assistant and agent cursors are labelled as such only while a `writing` event for that note and agent (which only the server can send) is active; otherwise they show as a person.

**Saving.** One client saves for everyone: the lowest awareness client id among the people in the note. It posts its changes since the last server state 1.2 seconds after the last change (at most 4 seconds after the first), then broadcasts `saved` with the server's state vector and revision. A `saved` message is only a hint: a client with unconfirmed changes of its own, or one behind the vector, syncs with the server, and a change counts as confirmed only when that client's own sync carried it and the server's reply covers it. Anyone whose own changes stay unconfirmed for 6 seconds saves them itself. A departing saver saves and announces `saved` before it leaves the channel. Every client syncs with the server every 30 seconds while visible (without a channel, every 8 seconds while it has unsaved changes, backing off to a minute otherwise) and when the tab returns, comes back online or reconnects. The status reads Live with a joined channel and Offline only when the browser is offline or the server can't be reached; without a channel it shows the usual Saving and Saved. A 403 or 404 stops the session, leaves the channel, makes the note read-only and says it doesn't exist or is private to someone else; 401 asks to sign in again; other 400, 409 and `too_long` errors stop retrying and show the error until the next edit; `live_too_large` and `live_invalid` hand the note to the classic save. Network errors, 408, 429 and 5xx retry with backoff. When a reply says the copy was `rebuilt`, the client builds a new Yjs document from `missing`, rebases its text onto it from the last confirmed server text, rebinds the editor and syncs again, resending any pending title. On `pagehide` a client removes its cursor first, then sends its unconfirmed changes with a keepalive request when they fit in 60,000 characters, and keeps them on the device either way. The route merges with `Y.applyUpdate` under the row lock (`syncLiveDoc` in `lib/docs/store.ts`), so concurrent or repeated saves are harmless, then derives the Markdown and saves it through `commitPage` (versions every 10 minutes per person, links, tags, search). A merge that changes nothing textual stores the Yjs state without a new revision. Unconfirmed changes are also kept in local storage as a Yjs update tagged with the generation (up to 750,000 bytes, falling back to only this client's changes; when neither fits or storage is full the note warns that the text isn't kept on the device) and merged back on the next open. Titles travel with the next save and are announced with `title`.

**Server-side changes.** `commitPage` keeps `ydoc` in step for every other write (classic saves, REST, MCP, the assistant, restores, link rewrites): it diffs the stored text against the new Markdown (`lib/docs/live/text-diff.ts`, Myers on lines then characters, never splitting a surrogate pair) and applies the result as `Y.Text` deletes and inserts, so typing elsewhere survives. After the transaction commits (`afterCommit`, run through `after()`), `publishLiveChange` in `lib/docs/live/broadcast.ts` posts the update to Realtime's REST broadcast endpoint with the service key (`POST /realtime/v1/api/broadcast/<topic>/events/<event>?private=true`, falling back to the batch `POST /realtime/v1/api/broadcast` with `private: true` on each message when an older Realtime answers 404, each request with a 5 second timeout), only if someone opened the note in the last 90 seconds (`crm.page_watchers`, read through `private.page_watched`). Without `SUPABASE_SERVICE_ROLE_KEY` nothing is published, and open notes pick the change up on their next sync, within 30 seconds; the seed's `livePublish` says which. Edits by the assistant or an agent are coalesced into at most 24 steps and streamed over 1 to 3 seconds (15 ms a character), each step with an awareness entry for "Orbit assistant" or the agent's name and a cursor at the insertion, cleared 1.5 seconds after the last step. Links rewritten by a rename go out as one plain update per linking note, sent four at a time within 8 seconds. Broadcasts carry the copy's `generation` as `g`. The version before an agent edit is still taken. `writing` events on `docs-workspace:<workspace>` (shared notes) or `docs-person:<owner>` (private notes) drive "is writing" in the note list.

**Limits and compaction.** The live copy only ever holds plain text in `body`: an update that adds another root type, an embed, a nested type or formatting is refused, and a stored copy found holding any of those is rebuilt from the Markdown. An update that refers to changes the server doesn't have (one sent before what it builds on, or from an older copy) isn't kept; the reply has `rebuilt: true`. Requests are capped at about 580,000 characters, decoded updates at 360,000 bytes and state vectors at 64 KB. `ydoc` keeps the whole edit history, so it is compacted: when a note is opened, nobody has watched it for 90 seconds, and the stored state is over 64 KB and over four times the size of a fresh copy, it is rebuilt from the Markdown (`stateFromMarkdown`). A state over 4,000,000 bytes is rebuilt straight away. Every rebuild adds one to `crm.pages.ydoc_generation` and broadcasts `pull` with the new `g`. A client holding an older generation gets `rebuilt: true` on its next sync, swaps in the new state and rebases its unsaved text onto it with `lib/docs/live/rebase.ts`. Making a note private, moving it into a private folder or archiving it deletes the `crm.page_watchers` rows of people who can no longer see it (a trigger on `crm.pages`), so nothing more is published to them.

**Authorization.** Channels are private. Policies on `realtime.messages` (migration `20261216100000_docs_realtime.sql`) let a signed-in person receive and send on `doc:<id>` only when `crm.pages` row-level security lets them see that page (sending also needs it unarchived), listen on `docs-person:<their id>` and `docs-workspace:<a workspace they belong to>`, and nothing else. Realtime evaluates them as `authenticated` with the person's JWT claims, the same `request.jwt.claims` that `withActor` sets, so `private.session_user_id()` and the page policies behave exactly as in the app, and daily notes stay with their owner. The browser joins with the Supabase session from the `@supabase/ssr` cookies (`createBrowserClient`, which refreshes the token and hands it to Realtime). `tests/docs-live.test.ts` checks the policies against a stand-in `realtime` schema (`supabase/bootstrap/local-realtime.sql`) the way Realtime does: insert a message for the topic, switch to `authenticated` with the claims and `realtime.topic`, read it back, then try to insert.

## Learning

`crm.memories` holds what the assistant has learned: `scope` is `personal` (with `user_id`, readable only by that person), `business` or `market` (shared with the workspace), plus kind, title, body, sources, confidence, pinned, an optional company, origin (`learning`, `assistant` or `manual`), `source` (where the content came from, from most to least trusted: `manual`, `chat`, `crm`, `learned`, `call`, `email`, `market`, `web`; migration `20270112300000_assistant_isolation.sql` set existing learned business notes to `learned`, which counts as outside content) and a generated full-text `search` column. The business learner numbers each line of its material ([d1] deal moves, [w1] won and lost deals, [n1] notes, [c1] call summaries, [m1] meetings, [e1] email tone, [r1] research), each with its company, and asks for the lines behind each note. A note is only added to or changed in the shared business memory when it cites a deal or note line for the note's own company (any company when the note has none); otherwise it is held back (`heldBack` in the run summary). It is labelled with the least trusted source among the lines it cites and every line about its company. An update or the weekly merge never moves a note to a more trusted source (`lessTrusted`). A personal note keeps the workspace it was learned in (`workspace_id`) and `all_workspaces` (migration `20270103100000_personal_memory_workspaces.sql`): true when it is about how the person works, writes and wants the assistant to behave anywhere, false when it is about that business (its products, pitch, ICP, clients, partners, people, boards or deals), null when not sorted yet. Settings › Memory lists all of the person's own personal notes from every workspace (`listMemories` with `allWorkspaces`), each with where it applies for people in more than one workspace; Settings › Learning shows business and market notes. Every other read of personal notes (the assistant's learned notes and `recall`, the nightly learner, the weekly tidy and the brief) uses `visibleMemorySql`: notes learned in this workspace, plus the person's notes from their other workspaces only when `all_workspaces` is true, so null and false stay where they were learned. Notes added by hand or by `remember` are this workspace only unless the person picks All workspaces; business and market notes leave the column null. The personal learner runs in every workspace the person belongs to, from that workspace's assistant chats and approval decisions (and the draft edits in its Mail mirror, which lives in the home workspace), and skips a workspace with nothing new without a model call. It decides `allWorkspaces` for every note it adds or updates; a change to an all workspaces note learned elsewhere is made to that note when it still applies everywhere; when the learner decides the change is about this business, the change is saved as a new note here and the original becomes only in the workspace it was learned in. The weekly tidy only merges notes that apply in the same place. Before learning, a personal run sorts the person's unsorted notes in every workspace with one `completeJson` call (`sortPersonalMemories`: up to 60 notes a run, newest first, so later runs carry on with the rest; the default model, a 45 second timeout inside the run's deadline, each note shown with the workspace it was learned in, and every workspace the person belongs to with its What you sell); a note the model leaves out is set to false. Someone with one workspace gets false for every unsorted note without a model call. `crm.learning_runs` for `personal` are per workspace and person. `crm.market_notes` is the inbox Grok Bot writes to through MCP (agents with `market:write` may insert and read in their workspace; a link is unique per workspace), `crm.watchlist` is what it researches, `crm.learning_runs` records each run per unit (workspace and kind, plus user for `personal` and `brief`) and `crm.daily_briefs` holds one brief per person per day, with `read_at` and `conversation_id` (the assistant conversation it opened as, `on delete set null`). Rebuilding a brief with different text clears both. `lib/learning/nightly.ts` gathers material inside `withActor`, calls the model outside the transaction, and applies the returned additions, updates and retirements in another; only notes with origin `learning` that aren't pinned can be changed or retired by it. The brief also reads the person's own research mail since the last brief (at most 72 hours back, 20 emails, 2,000 characters each, to keep a nightly per-person call small), inside their own `withActor`, so it never reaches shared notes. `private.issue_market_agent` creates or re-keys the Grok Bot agent (scopes exactly `market:write`) for an owner or admin, and `private.market_agent_status` reports when it was connected and last used.
