# Architecture

PostgreSQL is the source of truth. The web UI, REST API, and MCP server call the same company service in `lib/crm/companies.ts`. Matching, partial updates, idempotency, and audit writes are not reimplemented in each client.

```
Browser  -> server actions -> domain services -> PostgreSQL
Agent    -> /api/v1        -> domain services -> PostgreSQL
Agent    -> /api/mcp       -> domain services -> PostgreSQL
Person   -> /api/mcp       -> domain services and lib/mail -> PostgreSQL
```

The MCP server lives in `server/mcp/`. Agent tokens and personal tokens both reach it (see Personal tokens and MCP mail).

Zustand (`stores/companies-store.ts`) holds which panel is open and the Mail unread count. Lists are rendered from the database. A reload reads PostgreSQL again.

## Tenancy

Every business row has `workspace_id`. Human sessions resolve a user id, then `withActor` sets the JWT claims and `SET LOCAL ROLE authenticated` for the transaction. Agent sessions set `app.workspace_id` and `SET LOCAL ROLE crm_agent`. Policies use those settings. The table owner is not the role the request runs as, and row-level security is forced.

Business tables are in the `crm` schema so the Supabase Data API does not expose them. Privileged functions live in `private` and are executable by the `crm_app` login, not by `authenticated` or `crm_agent`. Policies may call `private` helpers such as `private.user_workspace_ids()`, `private.session_user_id()` and `private.is_workspace_admin()`, but queries run inside `withActor` cannot: `authenticated` has no usage on the schema.

Most business rows are visible to every workspace member. The exceptions are enforced by policy, not by the UI: mailboxes, email messages, call records, calendars, calendar accounts and their events (except events from a Use for CRM calendar that list a contact or company, which every member can read), unfiled Teams transcripts, assistant conversations, AI accounts, Orbit Agent pairings, personal tokens, Granola keys, email signatures, unsent email attachments, the Mail mirror and everything built on it (`mail_sources`, `mail_folders`, `mail_messages`, `mail_drafts`, `mail_reminders`, `mail_summaries`, `mail_prepared`, `mail_attachment_texts`, `mail_tracking`, `mail_opens`, `mail_viewer_addresses`, `mail_sender_rules`, `mail_preferences`), sending addresses (`send_identities`), push subscriptions and the push log, booking pages, workflow runs and their steps, and notifications are owner-only. Tasks are visible to their owner, their creator, and the workspace owner and admins (`private.is_workspace_admin`); the update policy uses the same rule, and its check allows handing a task to someone else only when the editor still sees it afterwards.

## People and agents

Humans sign in with Supabase Auth when `NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_ANON_KEY` are set. `proxy.ts` and `getUserActor` (`lib/auth/user.ts`) check the session with `auth.getClaims()`, which refreshes an expired session and then verifies the ES256 token locally against the project's cached public keys, so a page makes no Auth request; `getUserActor` is wrapped in React `cache()`, so a request looks up its memberships once. Membership is still read from the database on every request, so removing someone takes effect at once even though their token lasts until it expires. Without those, a local password session is used. `supabase/bootstrap/local-auth.sql` creates a small `auth.users` table and `auth.uid()`. Do not run that file on a hosted Supabase project.

Agents are rows in `crm.agents`, not user accounts. A credential is a random token stored as a SHA-256 hash. The plaintext is shown once. Revoke it by setting `revoked_at`. Scopes are `crm:read`, `companies:write`, `contacts:write`, `leads:write`, `activities:write`, `opportunities:write`, `tasks:write`, `market:write`, and `admin`. `admin` implies the others. `market:write` only allows reading the watchlist and adding market notes. A lead ingestion checks `leads:write` and the write scope of each record it actually creates or updates.

The service role key is never given to an agent. Agents use their own bearer token against this application's API.

### Personal tokens and MCP mail

`crm.personal_tokens` holds each person's MCP tokens (owner-only, forced row-level security): name, prefix, the SHA-256 of the token, and last used and revoked times. `lib/auth/personal.ts` creates (`orbit_…`, shown once, at most 10 active per person), lists and revokes them; the card is Settings › API and webhooks › Your mail in Claude. `/api/mcp` treats a bearer token starting with `orbit_` as a personal token: `private.authenticate_personal_token` (security definer, executable only by `crm_app`) returns the person only when the token isn't revoked and they are still a member of its workspace, and updates `last_used_at` at most once a minute. The request then runs as that person, with their role's scopes, through `withActor`, limited to 120 requests a minute per token. `server/mcp/server.ts` registers the mail tools in `server/mcp/mail.ts` only for a person, so workspace agent tokens and stdio (`npm run mcp`) never get them. The mail tools read the Mail mirror and its attachments, ask questions with `askMail`, and save or discard Outlook drafts through `lib/mail/compose.ts`. There is no tool that sends email.

## Companies

Active companies in a workspace are unique by canonical domain. When neither has a domain, a company also matches another company with the same normalised name. Create and update follow exactly that rule, so creating "Mercury" with `mercury.com` succeeds even when a "Mercury" without a domain exists. Upsert is the one exception: an upsert with a domain that matches no company falls back to a company with the same normalised name and no domain, and attaches the domain to it. The same display name with two different domains stays two companies. Writes take a workspace advisory lock, then unique indexes stop a race.

Name normalisation lowercases, strips accents, keeps letters and digits in any script plus `+` and `#`, and drops a trailing legal suffix such as Inc or GmbH. When an upsert or create gives a website but no domain, the domain comes from the website host, unless that host is a shared one such as LinkedIn, Facebook, Instagram, X, GitHub, Medium, Google Sites, Notion, Wix, Squarespace, or YouTube.

`PATCH` and upsert leave omitted fields alone. An explicit `null` clears an optional field. A domain-only upsert does not replace an existing name. A company or contact write whose values all equal the stored ones changes nothing: no audit event, no webhook, and `updated_at` stays put.

`Idempotency-Key` is stored per workspace and actor. The same key and body replays the stored response. The same key and a different body returns 409.

Deletes archive. `archived_at` is set and the row stays. There is no hard delete on the API.

## Audit

`crm.audit_events` is append-only. A trigger rejects updates and deletes, and those grants are not given out. Mutations write an event with the actor type (`user` or `agent`), agent id, credential id, source, and source URL when the caller provides them. Each event also queues a delivery for every enabled webhook subscribed to that event type, and, when the event can start a workflow, a row in `crm.workflow_events` (see Workflows). Delivery signs the body with HMAC SHA-256 and retries a failed attempt for about three hours.

## People, opportunities, activity, and tasks

Contacts match an active email, then an active LinkedIn profile, then the same normalised name at the same company. Opportunities use the workspace default pipeline unless `pipelineId` names a board (see Boards). A primary contact must work at the opportunity's company (`assertContactCompany`, on create and whenever the company or contact changes); otherwise the write fails with `invalid_input` on `primaryContactId`. Won-deal board cards copy the contact only if it still works there. Omitting the stage picks the first stage. A won or lost stage sets the status, and setting the status to won or lost moves the opportunity to that stage. `opportunity.stage_changed` is written when the stage or status changes.

Activities are append-only: `authenticated` and `crm_agent` can insert them but not update them. A company timeline reads activities stored against that company. Tasks live in `crm.tasks`; the Tasks page (`/tasks`, which `/actions` redirects to) opens on All, every open task with overdue first and undated last. Completing a task sets `completed_at` and leaves that timestamp in place if it is completed again.

`POST /api/v1/leads` and the `add_lead` tool run company, contact, activity, opportunity, and task writes in one transaction, through the same functions the individual endpoints use. A second lead with the same domain and email updates those rows instead of creating new ones.

Company, contact, opportunity, and task references must belong to the same workspace. That check is a trigger, so a foreign id cannot be attached even when the caller's row-level policy would otherwise hide it. It checks a reference only when that reference, the row's company, or its workspace changes, so moving a contact to another company leaves its existing tasks and opportunities editable.

## Conversations

`record_email` and `record_meeting` file an interaction on a contact matched by email, or on a company matched by the email's domain. When that company has no open task, the CRM adds a follow-up due in two days.

The inbox connects one Microsoft mailbox per user. `MICROSOFT_CLIENT_ID` and `MICROSOFT_CLIENT_SECRET` come from an Entra app with delegated `Mail.ReadWrite`, `Mail.Send`, `User.Read`, `Calendars.ReadWrite`, and `offline_access`. Signatures: `crm.email_signatures` (owner-only RLS) holds one plain-text signature per user and sending address (lowercased, up to 2,000 characters); `saveSignature` only accepts the user's own senders and deletes on empty. `sendContactEmail` appends the sender's signature after a blank line unless `signature: false`, and logs the message without it. Senders: `listSenders` returns the main mailbox (`primary`) and every connected Microsoft extra account with `can_send`; `sendContactEmail` takes `from` (an account id, default the mailbox), refreshes and stores that account's token, and records `metadata.from` on the email activity. Attachments: `prepareAttachment` (`lib/crm/email-attachments.ts`) records a row in `crm.email_attachments` (owner-only RLS: name, content type, size up to 25 MB) and returns a signed upload URL from `lib/storage.ts`, which talks to the Supabase Storage REST API with the service key (bucket `email-attachments`, private, created on first use); the browser PUTs the file there. `sendContactEmail` takes the attachment ids, reads each object back (its size must match), and `sendGraphMail` sends up to 3 MB in total inline through `sendMail`, otherwise creates a draft (`POST /me/messages`, which needs `Mail.ReadWrite`; a 403 asks to reconnect), adds small files directly and large ones through `createUploadSession` in 3,200 KiB chunks, then sends it, deleting the draft on failure. After sending, the rows and objects are deleted unless the caller keeps them (bulk email discards them once all messages are out), and the email activity records `metadata.attachments` (`{name, size}`). `private.claim_stale_email_attachments` lets the cron remove rows older than a day, whose objects are then deleted. The refresh token is encrypted with `APP_SECRET`. Filing for Capture (`lib/crm/inbox.ts`) is separate from the Mail mirror below: opening Capture, or choosing Sync, reads messages received since the last sync (the first sync looks back 14 days, up to 100 messages). From a contact, Send email delivers through that mailbox and files the message on the contact. A mailbox connected before Mail.Send was granted has to be disconnected and connected again. A message attaches to a contact by email address, otherwise to a company by domain. The mailbox's own address is not the contact. A match from the last 48 hours files an email activity and, when the company has no open task, suggests a follow-up. Mail that matches neither stays in Capture as not attached. Gmail is not connected. The Outlook calendar is described below.

Teams phone calls come from Graph `getPstnCalls`, which only accepts an app-only token, so Orbit uses the client-credentials flow with the same Entra app and the `CallRecords.Read.All` application permission. The tenant is `MICROSOFT_TENANT` when it names one, otherwise the `tid` claim of the connected mailbox's access token, cached on the sync state. Only rows whose user principal name is the mailbox address (or whose user id is the mailbox user) and whose type is `user_in` or `user_out` count. `crm.call_records` stores one row per call log id per workspace: direction, the other party's number in E.164, start time, duration, and the contact, company, and activity it was filed on. A row with no matching contact phone keeps those empty and is filed on a later sync. `crm.call_sync_state` keeps one row per mailbox connection with the tenant id, the last synced and attempted times, and the last error. Both tables are readable and writable only by the mailbox owner. The CRM layout runs a sync after the response through `after()`, claiming the attempt so Graph is called at most once every five minutes; Sync calls in Capture forces one. Each sync re-reads from 24 hours before the last sync, and syncs for a connection run one at a time under an advisory lock.

`crm.call_insights` holds at most one summary per call or meeting activity, since activities are append-only and never updated. It stores the workspace, the activity, the contact and company copied from it, the source (`manual` for a pasted transcript, `teams` for a Teams transcript, `granola` for a Granola meeting), the transcript as compact `Speaker: line` text (up to 200,000 characters), the summary, key points, suggested action items, the model, a status (`pending`, `ready`, or `failed`), and the last error. Each action item is `{id, title, owner, dueDate, status, taskId}`: owner is `me`, `them`, or null, the due date is a London calendar day, and accepting one creates a task through the normal task path and records its id. Workspace members and agents can read and insert rows in their workspace, and can update only the summary, key points, action items, model, status, and error; the transcript, links, and source never change. Summarising needs `activities:write` and accepting an action needs `tasks:write`. The model call (`lib/llm.ts`) runs outside the database transaction against `LLM_API_BASE_URL` with `LLM_API_KEY`, times out after 25 seconds, and retries once on a gateway 5xx, a network failure, or a reply that is not the expected JSON. The summary prompt also asks for `health` (`healthy`, `watch`, `at_risk` or null) and `healthReason`, stored as `sentiment` and `sentiment_reason` with `sentiment_checked_at`. In the same transaction, `applyCallHealth` copies a non-null sentiment to `crm.companies.health`, `health_reason`, `health_at` (the call's `occurred_at`) and `health_activity_id`, for the call's company or else its contact's company, skipped when the company's `health_at` is later than the call (a newer call, or a hand-set health, which stamps `now()` and clears the activity). A change records `company.updated` with fields `health` and/or `healthReason` (operation `call_health`), which feeds webhooks and field-changed workflows; the actor needs `companies:write`. `private.claim_unjudged_calls` (for `crm_app`) claims ready summaries with no sentiment that were never checked, marking them checked; `backfillCallHealth` (`lib/crm/call-health.ts`) runs one per cron request through `judgeCallSentiment`, a smaller sentiment-only prompt, as the call's creator or else the workspace owner. Company context and the contacts page load the summaries for every call they show in one query, without the transcript, which is fetched only when Transcript is opened.

### Automatic transcripts

Transcripts arrive from Granola (`lib/granola.ts`, `lib/crm/granola.ts`) and Teams (`lib/microsoft/transcripts.ts`, `lib/crm/teams-transcripts.ts`). Both go through `lib/crm/conversations.ts`, which records the import, matches people, creates the activity through `createActivityInDb`, and summarises through `summariseCall` outside the import transaction.

| Table | What it holds |
| --- | --- |
| `crm.conversation_imports` | One row per imported transcript. Granola rows are unique per workspace and note id and visible to every member. Teams rows are unique per mailbox owner and transcript id, fileable and updatable only by that owner (`user_id = private.session_user_id()`), and readable by that owner until filed, then by every member. `source` is `granola` or `teams`, `kind` is `meeting` or `call`. Keeps the title, start and end times, participants (`[{name, email}]`), the external link, the transcript as `Speaker: line` text, Granola's own summary, the Teams `call_id`, the status (`pending`, `filed`, `unfiled`, `ignored`), the filed activity, contact and company, the last error, and attempts. Members can insert and update only the import columns, never the workspace, source, or ids. |
| `crm.integration_state` | Granola: one row per workspace, with the member it runs as, the webhook id, and its signing secret (encrypted with `APP_SECRET`). Teams transcripts and the Outlook calendar: one row per mailbox connection and source (unique on `connection_id, source`), readable only by its owner; transcripts keep the Graph subscription id (unique), expiry, and `clientState` (encrypted), and the calendar keeps `scope_missing` and `granted_scopes` (the last token response's `scope` list). All keep last synced and attempted times and the last error. |
| `crm.webhook_receipts` | Granola delivery ids seen in the last ten minutes, unique per workspace, so a replayed delivery is acknowledged and ignored. |
| `crm.call_records.teams_call_id` | The `callId` from the PSTN call log, which equals a transcript's `callId`. Set on new rows and filled on existing rows the next time a sync sees them. |

Matching: a Granola note matches attendees and calendar invitees against contacts by email, then companies by domain, skipping free-mail domains, the note owner, every workspace member, and the owner's and members' own domains. A match files a `meeting` activity and the import as `filed`, otherwise `unfiled`. A Teams transcript is stored as `pending` and attaches to the activity of the call record with the same `teams_call_id`; this is retried on every transcript sync and every Teams call sync, and a transcript still pending after 48 hours becomes `unfiled`. Filing a Teams transcript from Capture creates the call activity on the chosen contact and links the call record to it; a call record that arrives later for that call reuses the filed activity instead of logging a second call. A note or transcript that fails to import is stored as `pending` with its error and attempt count and retried on later syncs; after three attempts it becomes `unfiled`. Item failures do not hold back `last_synced_at`; only a failed listing or running out of time does. Summaries are retried at most three times for errors that leave no summary row, and a summary left `pending` for more than three minutes (a run that was cut off) is picked up again and shows Try again on the timeline.

Background work runs without a session. `private.background_members()` lists workspace members; each workspace acts as every member who owns a connected mailbox (or as its owner when none does), through the same `UserActor` and row-level security as a signed-in page. Public routes do the cheap check first: `private.granola_webhook_targets()` returns the stored Granola signing secrets in one query, the Standard Webhooks signature (HMAC SHA-256 over `id.timestamp.body`, timestamps within five minutes) is checked against them, and only then is the delivery id recorded and the note fetched in `after()`; a delivery with no note id runs the normal rate-limited sync. The Graph routes (`/api/microsoft/notifications` for transcripts and `/api/microsoft/lifecycle` for subscription lifecycle events) echo `validationToken` as `text/plain`, reject more than 50 notifications per request, resolve all subscription ids with one call to `private.transcript_subscriptions(ids)`, accept a notification only when its `clientState` matches, answer 202, and fetch the transcript in `after()`. Lifecycle events renew (`reauthorizationRequired`), recreate (`subscriptionRemoved`), or poll (`missed`). These security-definer functions are executable only by `crm_app`. `/api/cron/sync` checks `Authorization: Bearer <CRON_SECRET>` in constant time. Every background path carries a deadline about 50 seconds from the start of the request: the model call timeout shrinks to fit and skips its retry when time is short, Graph paging and Granola rate-limit backoff stop early, and no step starts without enough time left.

### Outlook calendar

A user's calendars come from two kinds of Microsoft connection. The main mailbox connected in Capture (`crm.mailbox_connections`, unchanged) supplies the main account's calendars. Extra accounts (`crm.calendar_accounts`) are connected from Settings, Calendars, through the same `/api/microsoft/connect` and `/api/microsoft/callback` routes: the signed state cookie carries `purpose: "calendar_account"` (or `"send_account"` for Add mail, which adds `Mail.Send Mail.ReadWrite` and sets `can_send` from the granted scopes; a later calendar-only reconnect keeps it), the scopes are `openid offline_access User.Read Calendars.Read`, the authority is `MICROSOFT_TENANT` (default `common`), and `prompt=select_account` (plus `login_hint` on Reconnect) lets the user pick a different account. The callback reads `/me` (`mail`, else `userPrincipalName`, and `displayName`), refuses the main mailbox's own address, upserts the account with encrypted tokens and the tenant id from the ID token's `tid` claim, and syncs it in `after()`. Authorization or token errors naming AADSTS50020, 700016, 65001, 90094, 50194, 90008, 500011, `consent_required`, admin approval or consumer accounts become the "organisation doesn't allow Orbit yet" message, because they mean the app registration's supported account types or the other tenant's consent policy block it. Connecting a mailbox in Capture removes an extra account with the same address.

`lib/microsoft/calendar.ts` lists `GET /me/calendars` (`$select=id,name,color,hexColor,isDefaultCalendar,canEdit,owner`, at most five pages) and reads `GET /me/calendars/{id}/calendarView` per calendar for 30 days back to 60 days ahead with `$select` limited to the fields below, `$top=100`, and `Prefer: outlook.timezone="UTC"`, following `@odata.nextLink` (only on graph.microsoft.com) for at most ten pages and stopping early when the deadline is close. It does not use `calendarView/delta`, because a delta link keeps the window of its first request, does not accept `$select`, and only covers the default calendar. A calendar's colour is Graph's `hexColor`, else its named `color`, else a palette colour (kept once chosen).

### Calendar links (iCal)

Settings, Calendars, Add calendar by link (`addCalendarFeedAction` → `lib/crm/calendar-feeds.ts`) accepts `https://` and `webcal://` (rewritten to `https://`) links without credentials, checks the host, inserts an `ics` row in `crm.calendar_accounts`, and runs a forced sync of just that account; if that first sync fails the row is deleted and the error shown. A duplicate link (same HMAC) is refused. Settings and the Calendar page only ever see `feed_host` plus `…`.

`lib/ical/fetch.ts` reads the link server-side. Before every request, and again for each of at most three redirects, it resolves the host and refuses it when any address is loopback, private (RFC 1918, CGNAT, unique-local), link-local (including 169.254.169.254), multicast, reserved, documentation, IPv4-mapped/compatible, NAT64, 6to4 or Teredo; redirects must stay on `https`. The production transport (`node:https`) also checks the addresses inside its connection `lookup`, so DNS rebinding between check and connect is refused too. Requests time out after 20 seconds (less near the deadline), bodies over 10 MB are refused, `If-None-Match`/`If-Modified-Since` are sent when the last full read is under six hours old, and a body without `BEGIN:VCALENDAR` is an error. Error messages name the host only, never the path. Tests inject the request function and the DNS lookup; there is no environment override.

`lib/ical/parse.ts` and `lib/ical/recurrence.ts` are a small RFC 5545 reader (no dependency): line unfolding, quoted parameters, text unescaping, `VEVENT` with `DTSTART`/`DTEND`/`DURATION` as `VALUE=DATE` (all-day, stored at UTC midnight like Graph's), UTC (`Z`), `TZID` or floating (the calendar's `X-WR-TIMEZONE`, else London). A `TZID` is used when it is an IANA name (Google and iCloud use those), else a common Windows name is mapped, else a path ending in an IANA name is used; anything else is read as UTC. `VTIMEZONE` definitions are not interpreted. `RRULE` supports `FREQ` `DAILY`/`WEEKLY`/`MONTHLY`/`YEARLY` with `INTERVAL`, `COUNT`, `UNTIL`, `BYDAY` (with ordinals such as `2MO` and `-1FR`), `BYMONTHDAY` (negative too), `BYMONTH`, `BYSETPOS` and `WKST`; instances are generated in the event's wall-clock time and converted in its zone, so they keep their local time across DST. Rules with other parts (`BYHOUR`, `BYWEEKNO`, hourly and so on) keep only the first instance. `RDATE` adds instances, `EXDATE` removes them, and a `RECURRENCE-ID` override replaces its instance (a cancelled override is kept cancelled). At most 1,000 instances per event and 5,000 events per calendar inside the window; hitting a cap marks the read incomplete, so only events before the window are deleted.

`lib/ical/events.ts` maps an event: id is the `UID` for a single event and `UID/<instance start>` (`20261019T080000Z`, or `20261019` for all-day) for each instance and its override, hashed when longer than 400 characters, and the same value is the iCal uid of an instance so Meetings cards don't merge a series; `SUMMARY`, `LOCATION`, `URL` (the Open event link, only when present), `STATUS:CANCELLED`, `TRANSP:TRANSPARENT` → `free`, `STATUS:TENTATIVE` → `tentative`, else `busy`; `ORGANIZER` and `ATTENDEE` (`CN`, `mailto:` or `EMAIL`, `PARTSTAT`, `CUTYPE=RESOURCE`/`ROOM` skipped); the Join link from `X-GOOGLE-CONFERENCE`, `X-MICROSOFT-SKYPETEAMSMEETINGURL`, or the first Google Meet, Teams, Zoom, Webex, Whereby, Jitsi, Chime or GoTo `https` link in `LOCATION` then `DESCRIPTION`. The calendar's name is the user's name, else `X-WR-CALNAME`, else the host; its colour is `X-APPLE-CALENDAR-COLOR` (or `COLOR`) when it is hex, else a palette colour.

`lib/crm/calendar.ts` runs the sync from the CRM layout through `after()`, the `calendar` cron step (which now also runs for users with only extra accounts), Sync calendar in Capture and Sync now in Settings (forced), and after connecting. Each account is claimed at most once every five minutes (`integration_state` for the mailbox, `calendar_accounts.last_attempt_at` for extra accounts). Sources are routed by provider (`PROVIDERS` in `lib/crm/calendar.ts`): `microsoft` sources are skipped when the Microsoft app isn't configured, and `ics` sources read their link as above, keep a single `feed` calendar row (Use for CRM off at first), skip the request entirely when that calendar is hidden and not used for CRM, treat 304 as synced with nothing changed, and record fetch and parse errors on the account and the calendar. The etag is stored only after events were saved. For each Microsoft account it refreshes the token, saves the calendar list (removing calendars Graph no longer lists after a complete listing), then reads every calendar that is shown or used for CRM, least recently attempted first, each in its own transaction under an advisory lock. Running short of time (45 seconds by default, or the cron deadline) stops between calendars; the next run starts with the ones it skipped. A calendar Graph refuses with 403 (for example a shared calendar that needs `Calendars.Read.Shared`) keeps its own error and does not fail the account.

Migration `20261022100000_multi_calendar.sql` creates a `__default__` calendar for each existing mailbox connection and moves its events onto it, so nothing is lost and no one reconnects. The first sync renames that row to the real default calendar's Graph id, keeping its settings and event rows.

Every sync upserts the events it read. After a complete read of a calendar it deletes that calendar's events that Graph no longer returned (removed, moved out of the window, or older than it), except events Orbit created (`created_by_orbit`) that start after the window, which the sync can't see yet; a partial read only drops events that ended before the window. Cancelled meetings are kept with `is_cancelled` and hidden everywhere. Links are recomputed for all of the user's events after each sync, after Create contact and after Use for CRM changes: events in calendars not used for CRM have no links, and in the others an organiser or attendee who is not internal (the workspace members' addresses, their other addresses, and their non-free-mail domains, plus the mailbox and calendar account addresses) links the active contact with that email and that contact's company, plus active companies with that domain unless it is a free-mail domain.

Missing permission: a connection made before `Calendars.Read` was added keeps working for mail. A token refresh never sends `scope`, so old connections keep refreshing. When the token response's `scope` lacks `Calendars.Read` (or `Calendars.ReadWrite`), or listing calendars answers 403 `ErrorAccessDenied`, the sync sets `scope_missing` and stops without an error; Capture, Settings and the Meetings card then ask to reconnect. Reconnecting clears the flag and runs a forced sync after the redirect. Write access is tracked the same way: the callback and every token refresh store the token response's `scope` in `integration_state.granted_scopes`, and `grantsCalendarWrite` reads it. No `Calendars.ReadWrite` there means `canWriteCalendar = false` and the invite dialog asks to reconnect; reads and mail are untouched. When nothing is stored yet (a connection from before this change whose access token is still valid), sending an invite first refreshes the token to learn the scopes. Orbit does not decode Graph access tokens, since Microsoft documents them as opaque to clients; it only reads `tid` from the ID token issued to Orbit itself.

Meetings card: up to five meetings that have not ended (the first shown as Next) and five that have, for the contact (`contact_ids`) or company (`company_ids`), from calendars used for CRM, with the same meeting in two calendars (same iCal uid) shown once. A Granola `meeting` activity within two hours of the start, on the same contact (or, on a company page, on the company or one of the meeting's contacts), is linked as Notes in Granola. People you've met: outside organisers and attendees of non-cancelled events in calendars used for CRM, without an active contact or a hidden entry, grouped by address with their last and next meeting, people met most recently first, then upcoming-only people, at most 25. Create contact checks the address is in the user's calendar and goes through `createContactFromAttendee`, the same path Unfiled conversations uses.

Calendar page (`app/(crm)/calendar`): `?date=YYYY-MM-DD&view=day|week`. Without `view` it shows the week on large screens and the day as an agenda list below that. The server loads the visible calendars' non-cancelled events overlapping the range (padded a day for all-day events) with contact ids for every attendee and the overlapping Granola note. Ranges and positions are London wall-clock days (`lib/calendar-view.ts`), so DST days are 23 or 25 hours; all-day events, which Graph returns at UTC midnight, sit on their calendar date. Overlapping events are packed into side-by-side columns per cluster. Toggling a calendar updates `is_visible` optimistically.

### Meeting invites

`lib/crm/invites.ts` sends and cancels invites for the signed-in user through the main mailbox only (extra calendar accounts stay read-only). Pure rules shared with the browser (durations, limits, the https-only link check, the default slot and 15-minute snapping) live in `lib/invite-rules.ts`; the Graph calls live in `lib/microsoft/calendar.ts`.

- `crm.profiles.meeting_link`: the user's https meeting link (at most 500 characters, checked in `checkMeetingLink` and by the `profiles_meeting_link_https` constraint), edited in Settings, Meeting link.
- `createInvite(actor, input)` validates before any network call: a title (at most 200 characters), `startLocal` `YYYY-MM-DDTHH:mm` in London time that must exist (times skipped when the clocks go forward are refused), be in the future and within two years, a whole-minute duration from 5 to 480, 1 to 50 guests (each a valid address; duplicates merged case-insensitively; the user's own addresses, i.e. sign-in, profile, other emails, mailbox and calendar-account addresses, dropped), notes up to 4000 characters, and `includeMeetingLink` (default: on when a link is saved; asking for it without a link is an error). It then needs a connected mailbox, refuses with "Reconnect Microsoft to send invites" when the stored scopes lack `Calendars.ReadWrite`, and posts to `POST /me/calendars/{default calendar id}/events` (or `POST /me/events` before the calendar list has synced) with `Prefer: outlook.timezone="UTC"` and: `subject`; `body` `{contentType: "HTML"}` holding the notes HTML-escaped with line breaks as `<br>` and `Join: <a href=link>link</a>`; `start` and `end` as London wall-clock times with `timeZone: "GMT Standard Time"` (the Windows name for London; times in the repeated autumn hour, and other app time zones without a mapping, are sent in UTC instead); `location.displayName` set to the link; attendees as `required`; `isOnlineMeeting: false`; `responseRequested: true`; `allowNewTimeProposals: true`; and a `transactionId`. The dialog makes one random UUID per submission and keeps it across retries of that submission; the server retries once, with the same id, after a network error or a 502, 503 or 504, and makes its own id when none is given. Graph sends the invitations itself; that can't be turned off.
- On success the returned event (UTC) is upserted into `crm.calendar_events` with `created_by_orbit = true` on the mailbox's default calendar row (creating the `__default__` row if the list hasn't synced), linked with the usual rules (`linkEvents` limited to that event), and every guest who is an active contact (the contact chosen in the dialog wins over a duplicate with the same email) gets a `meeting` activity "Invited <name> to <subject>" with the London date and time, the link and the notes, `occurred_at` now, and `metadata {source: "orbit", kind: "invite", eventId, providerEventId, startsAt}`. A failure after Graph accepted the event returns a warning instead of an error, so the user isn't tempted to send it twice.
- `cancelInvite(actor, eventId, comment?)` needs the event to be in the main mailbox's calendars, not cancelled, not started, and organised by the user (`created_by_orbit`, or the organiser is one of their addresses). It posts `POST /me/events/{id}/cancel` with `{comment}` when there is one (the organiser-only action that notifies attendees; Delete would not), sets `is_cancelled`, and logs "Cancelled <subject>" on each guest contact. A 404 from Graph is treated as already gone; a 400 saying only the organiser can cancel is explained.
- Errors: 401 asks to connect again, 403 `ErrorAccessDenied` (and similar) asks to reconnect for `Calendars.ReadWrite`, other 403s say the mailbox can't change that calendar, 429 reports Graph's `Retry-After`, and anything else is the sanitised Graph message.
- `listCalendarItems` adds `createdByOrbit` and `canCancel` (same rules as above, and at least one guest who isn't the user) for the event popover.

UI: `components/crm/invite-dialog.tsx` is shared by the Calendar page (New event in the header, a click on an empty grid slot, New event on an empty agenda day) and the contact header (calendar button next to Call in Teams, disabled without an email). Guests are searched with `searchContactsToFileAction`. Sending shows a notice ("Invite sent to Jane Doe") and refreshes the page. Server actions: `sendInviteAction` and `cancelInviteAction` in `app/(crm)/calendar/actions.ts`, `saveMeetingLinkAction` in `app/(crm)/settings/actions.ts`.

Migration `20261024100000_meeting_invites.sql` adds `profiles.meeting_link`, `calendar_events.created_by_orbit` and `integration_state.granted_scopes`. It doesn't touch `crm.mailbox_connections`, `crm.email_messages` or `private.schema_migrations`, so it runs in the hosted SQL editor as `postgres`, and it can be run more than once.

### Booking page

A public scheduling page at `/book/[slug]` (`app/book/[slug]`, outside the `(crm)` group, so no CRM chrome). `proxy.ts` lets `/book` and `/book/*` through without a session; `/api/*` was already public at the proxy and each route authenticates itself.

| Table | What it holds |
| --- | --- |
| `crm.booking_pages` | One row per user (`user_id` unique): `slug` (unique, `^[a-z0-9]+(-[a-z0-9]+)*$`, 3 to 40 characters, reserved words refused by `booking_pages_slug_reserved`, kept in step with `RESERVED_SLUGS` in `lib/booking/rules.ts` by a test), `enabled` (default off), `title` (null means "Book a call with <first name>"), `intro` (up to 500), `duration_minutes` (15, 20, 30, 45, 60), `buffer_minutes` (0 to 60), `min_notice_minutes` (0 to 14 days), `horizon_days` (1 to 90), `weekly_hours` (`{"mon": [{"start": "09:00", "end": "17:30"}], …}`, checked by `private.booking_hours_valid`), `time_zone` (Europe/London), `background_video_url` (https, up to 1000), `background_poster` and `avatar` (bytea up to 1 MB, JPEG, PNG or WebP, with their mime types), `last_error` and `last_error_at` (why the last booking failed, shown in Settings), and timestamps. Owner-only RLS for `authenticated` (`private.session_user_id()` and the workspace check); agents and anonymous users have no access. |

Public access only goes through security-definer functions executable by `crm_app` alone: `private.booking_page_public(slug)` returns the page fields a visitor needs (no email, meeting link, workspace or image bytes; `meeting_kind` is just `whereby`, `link` or null, and `version` is a hash of `updated_at` for image URLs) for enabled pages only; `private.booking_page_image(slug, kind)` returns the avatar or poster bytes; `private.booking_busy(user_id, from, to)` returns busy intervals from `crm.calendar_events` across all the user's calendars (not cancelled, `show_as` not `free`, at most a 100-day window) and only for a user with an enabled page; `private.booking_page_owner(slug)` returns the owner's membership row, from which `memberActor` builds the background actor that does the booking; `private.booking_slug_taken(slug, user_id)` backs the live availability check in Settings. `lib/booking/pages.ts` wraps them and the owner's settings reads and writes; `publicView` is the only shape sent to the browser.

Slots (`lib/booking/slots.ts`, pure, also used by the browser for month maths): for each local date in the window, each weekly range, every `duration` minutes for 15, 20 and 30-minute meetings and every 30 minutes for longer ones, wall times are converted with `zonedTimeToDate`; times that don't exist when the clocks go forward are skipped, a range ending at `24:00` ends at the next midnight, and a slot must end by the range's end. A slot is offered when it starts at or after now plus the minimum notice, before the start of the local day `horizon_days + 1` days from today, and doesn't come within `buffer` minutes of a busy interval on either side. Results are UTC instants. `GET /api/book/[slug]/slots?month=YYYY-MM&tz=Area/City` returns `{month, timeZone, first, last, days}` with the slots of that month grouped by the visitor's local date (an unknown zone falls back to the page's); the panel defaults `tz` to the browser zone and offers every `Intl.supportedValuesOf("timeZone")`.

Booking (`POST /api/book/[slug]`, `bookSlot` in `lib/booking/book.ts`): rate limits through `private.consume_rate_limit` with HMAC-hashed keys (`booking:slots:<ip>` 10 a minute, `booking:attempts:<ip>` 5 an hour, `booking:email:<email>` 3 a day; the IP is the first `X-Forwarded-For` entry, which Vercel sets); a filled hidden `website` field is refused; name (1 to 120), email (`canonicalEmail`) and note (up to 1000) are validated; the start must be one of the generated slots against stored busy data. It then takes a per-owner session advisory lock (`pg_advisory_lock(hashtextextended('booking:<user_id>', 0))`) on a dedicated connection (`openClient`, so a waiting request doesn't hold a pool slot), re-reads busy data, opens the owner's Outlook sender (`openInviteSender`: connected mailbox, `Calendars.ReadWrite`, fresh token), refuses the organiser's own addresses, and reads Graph `calendarView` of the default calendar from start minus buffer to end plus buffer; a Graph failure there falls back to stored data. A clash is a 409 "That time was just taken. Pick another.". The meeting goes through `sendInvite` (the second half of `createInvite`) as the owner: subject "<owner first name> × <visitor name>", body "Note from <name>:" plus the note and the Join link, location the meeting link, the visitor as the only required attendee, in the page's time zone. With `createContacts` it calls `createContactFromAttendeeInDb` in a savepoint (internal addresses are skipped), saves the event with `created_by_orbit`, links it, and logs a `meeting` activity "Booked via your booking page" with `metadata {source: "booking", kind: "booking", eventId, providerEventId, startsAt, page}`, all before the lock is released. Not connected, missing write scope, or a Graph error are logged in `booking_pages.last_error` and shown to the visitor only as a 503 "Booking is temporarily unavailable"; a successful booking clears the error. After the booking is saved, `alertOwner` (in `after()`, inline outside a request) adds a `booking` notification linking to the contact and sends the owner a plain-text "New booking" email from their own mailbox to itself through `sendOwnMail`; either failing is logged and never affects the booking.

UI: `components/booking/booking-screen.tsx` (panel, slots, form, confirmation), `booking-calendar.tsx` (month grid with arrow-key, Home and End navigation), `booking-background.tsx` (fixed `<video autoplay muted loop playsinline>` with the poster, faded in once playing and dropped on error or for `prefers-reduced-motion`, otherwise a CSS-only aurora whose keyframes live in `globals.css` and stop under reduced motion), and `components/crm/booking-page-settings.tsx`. Images are served by `GET /api/book/[slug]/image/[kind]` (public, cached, `nosniff`) and `/api/booking-page/image` (owner: GET, multipart POST, DELETE; same-origin check; type from the file's magic bytes). Videos are only stored as links: a Vercel function response is capped at 4.5 MB and Postgres is the wrong place for large media. The page sets `robots: noindex` on top of the site-wide `robots.txt`.

Migration `20261026100000_booking_pages.sql` creates the table, policies and functions. It doesn't touch `crm.mailbox_connections`, `crm.email_messages` or `private.schema_migrations`, re-creates `private.session_user_id()`, and can be run more than once.

### ClickUp

`lib/clickup.ts` is the API v2 client (personal token in `Authorization` without a scheme, `CLICKUP_API_TOKEN`, base `CLICKUP_API_BASE_URL`): user, workspaces, the space › folder › list hierarchy (cached five minutes per process), list statuses and custom fields, task create, update and get, the filtered workspace task search, custom field values, and webhooks. On 429 it waits until `X-RateLimit-Reset` (at most 15 seconds) only when the request deadline leaves room, otherwise it gives up for this run. `lib/crm/clickup.ts` holds the sync.

| Column | What it holds |
| --- | --- |
| `crm.tasks.clickup_task_id` | The linked ClickUp task, unique per workspace when set. |
| `crm.tasks.clickup_list_id` | The list the task lives in. Set without a task id, it means "create this task in ClickUp" and the sync keeps trying until it succeeds. |
| `crm.tasks.clickup_url`, `clickup_synced_at`, `clickup_error` | The ClickUp link, the last successful exchange, and the last error shown on the Orbit task. |
| `crm.tasks.clickup_sync` | The last values both sides agreed on (`title`, `dueAt`, `done`), ClickUp's `date_updated` at that point, when Orbit last wrote to ClickUp (`pushedAt`), and a short-lived claim while the task is being created (`creatingAt`). |
| `crm.integration_state` (`source = 'clickup'`) | One row per workspace: the member it runs as, the ClickUp workspace (`team_id`), the token owner's ClickUp user id, the default list, the watched lists, the last list used in a form, the list names for the pickers (`list_choices`), the webhook id, its secret (encrypted with `APP_SECRET`) and scope (`team`, `space:<id>`, or `list:<id>`), the last sync, and the last error. |
| `crm.webhook_receipts` (`source = 'clickup'`) | `webhook_id:history item ids` (or `webhook_id:event:task_id` for deletions) seen in the last day. |

Merging is three-way against `clickup_sync`. A field Orbit changed since the last agreement is sent to ClickUp; a field ClickUp changed is written to the Orbit task through `updateTaskInDb`, with the audit source `clickup`; when both changed, the later of the task's `updated_at` and ClickUp's `date_updated` wins. A ClickUp task whose `date_updated` is not newer than the stored one is skipped, so Orbit's own writes coming back through the poll or the webhook change nothing, and a webhook event dated within 15 seconds of Orbit's last write to that task is dropped without fetching it. Imported tasks are created with `createTaskInDb`; while an Orbit-created task is being sent (`creatingAt` within two minutes), a ClickUp task in the same list with the same title is not imported, so the webhook for Orbit's own create cannot make a copy. Due dates are London time: midnight means a date without a time (`due_date_time: false`); from ClickUp, `due_date_time: false`, or a time of exactly 00:00 or 04:00 London when the flag is missing, becomes midnight. Done means a status of type `done` or `closed`.

Each sync claims the row with a five-minute gap (the cron and Sync now force it), lists tasks in the watched lists and in lists that hold linked tasks, updated since the last complete sync less five minutes (14 days the first time), 100 a page, closed tasks and subtasks included, then sends up to 20 pending or changed tasks, then re-reads up to five linked open tasks not checked for six hours, archiving any whose ClickUp task is gone. Running out of time keeps `last_synced_at` where it was. `private.clickup_webhook_targets()` returns the stored webhook secrets for the public route, `/api/clickup/webhook`; it is a security-definer function executable only by `crm_app`.

## Assistant and AI accounts

### Assistant

`lib/assistant/chat.ts` runs a turn, `lib/assistant/gateway.ts` calls the model, `lib/assistant/tools.ts` holds the tool registry, and `lib/assistant/prompt.ts` builds the system prompt. `POST /api/assistant` resolves the user, checks `LLM_API_KEY`, takes the rate limit (`private.consume_rate_limit('assistant:<user>', 60, 600)`) and streams newline-delimited JSON with a `ping` every 10 seconds. The route has `maxDuration` 300 and gives a turn a 285-second deadline. Event types are `conversation`, `user`, `tool` (`running` or `done`), `message`, `actions`, `waiting` (an Orbit Agent turn that outlives the request), `error`, `ping` and `done`. A body with `conversationId` and `decisions` (`[{id, approve}]`, 1 to 100) decides on actions; any other body sends a message.

`crm.assistant_conversations` holds one row per chat (title, model, reasoning `low` to `max`, `web_search`, `archived_at`). `crm.assistant_messages` holds rows in `seq` order with `role` (`user`, `assistant`, `tool`), `content`, `tool_calls`, `tool_call_id`, `tool_name`, `actions` (the proposed changes and their status), `sources`, `model`, `usage` and `provider_state`. Both tables force row-level security with one `for all` policy to `authenticated` requiring `user_id = private.session_user_id()` in a workspace the user belongs to; `crm_agent` and `anon` get no grants. Updates are limited to the title, model, reasoning, web search, archive, `stopped_at` (set by Stop) and timestamp on conversations, and to content and actions on messages. Deleting a conversation cascades to its messages and Orbit Agent jobs.

`sendMessage` trims the message (200,000 characters at most), normalises the model and reasoning with `settingsFor` (an unknown model becomes `claude-sonnet-5-5`; the reasoning drops to the highest level the model supports), refuses a ChatGPT or Claude account model whose account isn't connected, creates or updates the conversation, marks approved actions that have been `running` for over six minutes as `failed`, declines pending actions by writing `{declined: true}` tool results, inserts the user message and runs the loop. Each round rebuilds the history from stored messages (mention tokens expanded, tool calls without a stored result left out), calls `complete` with a timeout of the smaller of 240 seconds and the time left less five, stores the assistant message, runs read tools in parallel with `runTool` and stores each result as a `tool` message. Write calls are saved on that message as `pending` actions, emitted, and end the turn. The loop stops after 40 rounds, or writes a "carry on" message when less than 15 seconds are left or the turn has read more than the history budget. The history keeps old tool results to 4,000 characters and the current turn's to 40,000, and drops the earliest messages past 360,000 characters. The system prompt is a fixed part followed by "Right now" (the user, the time, web search and the links); learned notes go in a `learned_notes` message before the chat rather than in the system prompt. While a turn runs, `runLoop` checks every three seconds whether `stopped_at` changed or a newer user message arrived, and if so aborts the model call and stops. A closed connection alone doesn't stop the turn, so a phone that drops off still gets its answer.

`decideActions` checks every decided action belongs to one message, then claims them in one transaction (`select ... for update`, still `pending` or it refuses with "already been handled"), so a double submit runs nothing twice. It runs approved actions in order (`running`, then `done` or `failed` with the error), writes declined results, and once nothing on that message is pending runs the loop again so the model can report. `runTool` returns `{error}` instead of throwing, drops nulls the model sends for fields that don't accept them, marks results that carry outside text with a notice, and stops read tools after 90 seconds (approved actions always run to the end; Eclipse actions get an idempotency key derived from the tool call id). Write tools pass `provenance {operation, source: "assistant"}`. Action cards come from each tool's `describe`, with ids resolved to names by `recordNames` in one union query over companies, contacts, tasks, opportunities, stages, boards, workflows and workspace members (ids are collected from every string in the arguments, nested ones included). Workflow tools take a definition through `definitionFromInput` in `lib/workflows/definition.ts`: nested `steps` are converted with the legacy converter, `nodes` without positions are laid out with `autoLayout`, and both are checked with `graphProblem`.

`complete` routes by the model's `source`. `orbit` posts to `<LLM_API_BASE_URL>/chat/completions` with the tool definitions, `tool_choice: "auto"`, `reasoning_effort`, `max_tokens` 16,000 and, with web search on, `web_search_options {search_context_size: "medium"}`; Gemini tool schemas are simplified (non-string enums move into the description; `minimum`, `maximum` and `additionalProperties` are dropped). Sources come from `url_citation` annotations or a top-level `citations` list, capped at 30. `chatgpt` goes to `lib/assistant/providers/chatgpt.ts`. `claude` never reaches `complete`: `runLoop` hands it to Orbit Agent.

Mentions (`lib/mentions.ts`) are stored as `@[Name](kind:uuid)` with kind `contact`, `company`, `task` or `opportunity`; names are capped at 200 characters with brackets and line breaks replaced by spaces. `expandMentions` turns each token into `Name [person id <uuid>]` before the model sees it, and titles use `plainMentions` (`@Name`). `searchMentionsAction` in `app/(crm)/search.ts` feeds the picker.

`GET /api/assistant/probe` (Bearer `CRON_SECRET`) asks each model, or the one in `?model=`, to call a test tool and use its result. `web=1` turns web search on, `full=1` adds the full tool list, `reasoning=` sets the level (default `low`), and `search=1` runs a web search check instead. It runs without a user, so account models fail it.

### AI accounts

`crm.ai_accounts` has one row per user and provider (`unique (user_id, provider)`, provider `chatgpt` only): `status` (`pending` or `connected`), the account email as `label`, the ChatGPT `account_id`, encrypted `access_token` and `refresh_token`, `expires_at`, the encrypted device sign-in state in `pending`, and `last_error`. It uses the same owner-only policy as the assistant tables.

ChatGPT sign-in (`lib/ai-accounts/oauth.ts`) uses OpenAI's device flow on `auth.openai.com` with the Codex client id and `originator: orbit`. `startChatGptLogin` requests a user code and stores `{deviceAuthId, userCode, intervalMs, deadlineAt}` (15 minutes) encrypted in `pending`. The Settings card calls `pollChatGptLogin` at the given interval (at least two seconds): 403 or 404 means still waiting; on success it swaps the authorisation code and verifier for tokens at `/oauth/token` with redirect `https://auth.openai.com/deviceauth/callback`. The `chatgpt_account_id` claim is required and `email` becomes the label. `aiAccess` locks the row, returns the decrypted token when more than two minutes are left, otherwise refreshes and saves, or writes `last_error` and throws. `complete` retries once with a forced refresh after a 401.

The ChatGPT provider builds a Responses API request: the system prompt as `instructions`, the chat as input items, tools with `strict: false` (plus `{type: "web_search"}` when on), `parallel_tool_calls`, `reasoning {effort, summary: "auto"}`, `include: ["reasoning.encrypted_content"]`, `store: false` and `stream: true`. Output items are saved as `provider_state` and replayed on later rounds of the same model so encrypted reasoning carries over.

### Orbit Agent

Three owner-only tables back it:

- `crm.ai_companions`: one row per paired Mac, with name, `token_hash` (unique), `last_seen_at` and `revoked_at`. `authenticated` can read every column except `token_hash` and can only update `revoked_at`.
- `crm.ai_companion_pairings`: one-time codes (`code_hash`, `expires_at`, `used_at`).
- `crm.ai_companion_jobs`: `conversation_id`, the claiming `companion_id`, `status` (`queued`, `running`, `done`, `failed`, `cancelled`), `request`, `events` (tool progress), `result` (saved message ids), `error`, `claimed_at`, `finished_at`.

Pairing: `createPairingCode` deletes the user's used and expired codes and stores the SHA-256 of a new eight-character code (`XXXX-XXXX`, no `I`, `O`, `0` or `1`) with a 10-minute expiry. `POST /api/companion/pair` makes a token `oa_<32 random bytes, base64url>` and calls `private.redeem_companion_pairing(code_hash, token_hash, name)`, which marks the code used only if it is unused and unexpired and inserts the companion. The plaintext token is returned once and never stored. Both functions refuse callers other than `crm_app` or `postgres`.

On every agent request, `requireCompanion` hashes the bearer token and calls `private.authenticate_companion`, which returns the companion only when it isn't revoked and its user is still a workspace member, and updates `last_seen_at` at most every five seconds. The user's role and scopes are loaded fresh, and the request runs as that user through `withActor`. A Mac counts as online when seen in the last 75 seconds. Settings › Remove sets `revoked_at`, so the next request gets 401 and the agent deletes its config and exits. `private.team_remove` revokes a removed member's companions.

A Claude turn:

1. **Enqueue.** `runCompanionTurn` checks a Mac is online, cancels any queued or running job for the conversation, and inserts a job with the model's API name, `effort`, `webSearch`, the system prompt, the tool list with a `write` flag, and the prompt from `lib/companion/transcript.ts` (the chat as `<user>`, `<assistant>`, `<tool_call>` and `<tool_result>` blocks with closing tags escaped; tool results cut to 8,000 characters for earlier turns and 40,000 for the current one; oldest blocks dropped past 600,000 characters).
2. **Claim.** The agent long-polls `GET /api/companion/next`, which cancels the user's queued jobs older than 20 minutes and any job still `running` on this Mac (it only asks when idle), writing a reply into each chat, then claims the oldest queued job with `for update skip locked`. It retries every 1.5 seconds for up to 25 seconds. The agent backs off from one second, doubling up to 60, after an error.
3. **Run.** `companion/src/turn.ts` starts the Claude Agent SDK `query` with Orbit's tools as an in-process MCP server named `orbit`, `tools` limited to `WebSearch` when web search is on, `strictMcpConfig`, `settingSources: []`, `permissionMode: "dontAsk"`, `persistSession: false`, `maxTurns` 40, working folder `~/.config/orbit-agent/workspace`, and an environment without Anthropic API, Bedrock, Vertex or Foundry variables. Read tools post to `/api/companion/jobs/{id}/tool`, which checks the job is `running` and claimed by this Mac, refuses write tools, runs the tool as the user and appends a `tool` event. Write tools never call Orbit; they return a fixed "Proposed … has not happened yet" text to Claude.
4. **Stream.** While the job runs, the server reads it every second and passes new `tool` events to the browser.
5. **Heartbeat.** During a turn the agent posts to `/api/companion/jobs/{id}/heartbeat` every 15 seconds. That keeps the Mac online, and a 409 (the job was cancelled, for example by a follow-up message or Stop) aborts the Claude query. A `running` job whose Mac hasn't been seen for three minutes, or that was claimed over 20 minutes ago, is cancelled with a reply in its chat. A Mac with a running job it keeps reporting on counts as online, and as busy for 45 seconds after its job was cancelled, so a follow-up waits for it. On Ctrl+C or SIGTERM the agent posts to `/fail`.
6. **Finish.** The agent posts `{steps, results, sources, model, usage}` to `/complete` (up to 4 MB). `readCompanionResult` caps it (200 steps, 100 calls per step, 200,000 characters of text per step, 1,000,000 per tool result, 30 sources), the job is moved from `running` to `done` first (so a late cancel can't undo it), and `applyCompanionResult` writes assistant and tool messages in order, with write calls as `pending` actions on the last message, then saves their ids as the result. On an error the agent posts to `/fail`, which saves the error as a reply in the chat. Finished jobs are deleted after a day.

If no Mac claims the job within 20 seconds, the server cancels it. If the job is still running five seconds before the request deadline, the server emits `waiting` and the dock reloads the chat every six seconds, up to 30 times. Approved changes run on the server through `decideActions`, then a new job asks Claude to report back.

`npm run build` runs `npm run companion:pack` (`scripts/pack-companion.mjs`), which bundles `companion/src/index.ts` with esbuild into `companion/dist/orbit-agent.mjs` (Node 20, ESM, with `@anthropic-ai/claude-agent-sdk` and `zod` left as dependencies) and packs it into `public/downloads/orbit-agent.tgz`. Both outputs are gitignored.

## Team

`crm.workspace_members` holds each person's role (`owner`, `admin`, `member`). Members have every scope except `admin`. Changes to membership only go through security-definer functions executable by `crm_app`, each of which checks the caller's role itself:

| Function | Rule |
| --- | --- |
| `private.team_invite(workspace, actor, email, role, token_hash)` | Owner or admin; only the owner may invite an admin; refuses an address already in the workspace; cancels earlier pending invites for it. |
| `private.team_revoke_invite(workspace, actor, invite)` | Owner or admin. |
| `private.invite_preview(token_hash)` | Public read for the join page: workspace, email, role, inviter, status. |
| `private.accept_invite(token_hash, user)` | The invite must be pending, unexpired, and for the user's profile email. Adds the membership. Accepting twice by the same user is a no-op. |
| `private.team_set_role(workspace, actor, user, role)` | Owner only; the owner's own role never changes. |
| `private.team_remove(workspace, actor, user)` | Owner or admin; never the owner or yourself; only the owner removes an admin. Moves the person's companies, contacts, opportunities and tasks to the remover, disconnects their mailbox and calendar accounts, deletes their AI accounts and Granola key, revokes their Orbit Agent pairings, then deletes the membership. |

`crm.workspace_invites` stores the SHA-256 of the token (the token itself is only in the link), the email, role, inviter, expiry (14 days), and accepted or revoked times. `lib/auth/accounts.ts` creates the login for `/join/<token>`: `private.create_local_user` without Supabase, `auth.admin.createUser` with `email_confirm` when `SUPABASE_SERVICE_ROLE_KEY` (or `SUPABASE_SECRET_KEY`) is set, otherwise `auth.signUp` with a confirmation link to `/auth/callback`, which exchanges the code for a session. An address that already has a login proves its password instead.

Per-person Granola keys live in `crm.granola_keys` (encrypted with `APP_SECRET`, owner-only). `private.granola_key_members()` lets the scheduler add a sync step for each member with a key; the server key still syncs for the member whose email owns it.

## Mail mirror

`lib/mail/` mirrors mailboxes so Orbit can show and search mail without asking the provider. `crm.mail_sources` has one row per mailbox (the Capture connection, or an extra Microsoft account with `can_send`), with a provider (`microsoft` today, so Gmail can be added as another adapter), a lock (`locked_until`, five minutes) and the last error. `crm.mail_folders` holds each folder with its role (from Graph's well-known names: inbox, sentitems, drafts, archive, deleteditems, junkemail, outbox), counts, `sync_state` (`pending`, `backfill`, `live`, `skipped` for junk and outbox) and `sync_link`, the saved `@odata.nextLink` or `@odata.deltaLink`. `crm.mail_messages` holds every message: thread key (`conversationId`), subject, snippet, HTML body (up to 1.5 MB, else only text with `body_truncated`), plain text from `htmlToText`, sender, recipients, times, read, draft and flag state, attachments flag, categories, and a generated `search` tsvector (subject A, sender B, body C) with a GIN index. All three tables are owner-only with forced row-level security.

`syncMail` (`lib/mail/sync.ts`) loads the user's sources, claims each one, refreshes the folder tree every six hours (`listMicrosoftFolders`: the well-known ids, then up to five levels of child folders, at most 300), and splits the time between sources. Live folders run first (one delta round each), then pending and backfilling folders by role: inbox, sent, drafts, archive, others, deleted items. The first delta request selects the message fields with `$orderby=receivedDateTime desc`, `Prefer: odata.maxpagesize=50, outlook.body-content-type="html", IdType="ImmutableId"`. Each page is upserted in one statement through `jsonb_to_recordset`; partial items (only read or flag state) update those fields; `@removed` items delete the row from that folder only, so a message moved between folders keeps its row. A 410 or `SyncStateNotFound` resets the folder to `pending`. During a backfill, each page checks `pg_database_size` against `MAIL_STORAGE_LIMIT_MB` and pauses with a folder error when it is reached. Before any source runs, the database size is checked against `MAIL_HARD_STOP_MB` (default 18% above the limit); at or above it nothing syncs and every source gets `MAIL_HARD_STOP` as its error.

It runs from `/api/cron/mail` (`maxDuration` 300, a 240-second budget shared across users, with backfill), as the `mail_store` step of `/api/cron/sync` (15 seconds, new mail only) and after each CRM page load (10 seconds, new mail only). `lib/mail/store.ts` reads it: `searchMail` (`websearch_to_tsquery('english', …)` ranked by `ts_rank`, then newest; filters for sender, account and folder role), `getMailThread` (the thread in one source, oldest first, at most 100) and `mailSyncStatus` (stored against Graph's counts per folder).

### Mail on the timeline

`fileMailOnTimeline` (`lib/mail/timeline.ts`) runs at the end of every `syncMail`. As the user, it selects their mirrored messages from the last 60 days (not drafts, junk or outbox), pairs inbound mail with the sender and mail sent from one of their own addresses with each To and Cc address, and joins those addresses to workspace contacts by `normalized_email`. It skips any pair that already has an email activity on that contact with the same `mailMessageId` or `internetMessageId`, or, for activities logged at send time without those ids, the same title and direction within three minutes. Up to 100 are filed per run, oldest first, as `email` activities with `source: microsoft`, `direction`, `account`, `mailMessageId` and `internetMessageId`. Filings older than a day carry `catchUp` in their provenance, and `enqueueWorkflowEvent` ignores events with `catchUp`. The old inbox sync (`lib/crm/inbox.ts`) skips a message whose `internetMessageId` is already on the contact.

### Mail home

`/mail` (`app/(crm)/mail/page.tsx`) renders the first page of the chosen view on the server and hands it to `components/mail/mail-screen.tsx`, which does everything else in the browser. `lib/mail/threads.ts` reads conversations: `listThreads` groups messages by source and thread key (`coalesce(thread_key, 'm:' || id)`) within a view (a folder role, one folder, or a search across every folder but junk and outbox) with window functions, takes the newest message for the row and `bool_or` for unread, flagged and attachments, and pages with a `(time, key)` cursor. `getThread` returns the whole conversation in every folder, oldest first, with HTML passed through `cleanEmailHtml` (`lib/mail/html.ts`: scripts, frames, forms, `base`, event handlers, `javascript:` links and `cid:` images removed) and `rich` set for designed emails. `mailNav` and `mailUnreadCount` count unread conversations per folder and account; the layout passes the Important unread count (see Split inbox) to the side menu, and Mail keeps it current through the companies store. Client-safe types and URL parsing are in `lib/mail/view.ts`.

The browser talks to route handlers, not server actions, so reads are never queued behind writes: `GET /api/mail/threads`, `/api/mail/thread`, `/api/mail/nav`, `POST /api/mail/actions` and `POST /api/mail/sync` (an eight-second new-mail sync). `components/mail/mail-cache.ts` keeps lists and conversations in memory for the session, collapses duplicate requests and prefetches two at a time: the first four of each list, the two after the selected conversation and the one before, and whatever the pointer rests on. Emails render in a sandboxed `iframe` (`allow-same-origin` and popups only, no scripts) with a content security policy that allows only images, styles and fonts, `<base target="_blank">`, and a height that follows the body.

`applyMailAction` (`lib/mail/actions.ts`) handles read, unread, flag, unflag, archive, trash, inbox and snooze for a conversation. Read touches every unread message and unflag every flagged one; unread and flag touch the newest message in the view. Moves take the messages in the current view (for a search, the inbox and your own folders for archive, everything but trash for trash, archive and trash for inbox), never drafts. It gets a token with `mailSourceToken`, calls Graph (`PATCH /me/messages/{id}` or `POST /me/messages/{id}/move` with a well-known destination, `IdType="ImmutableId"` so ids survive the move) four at a time, then updates the rows that succeeded, moving each to the folder Graph reports (or the folder with that role). The later delta for the old folder removes nothing, because the row is already in the new one. Changes to your own mailbox are not audit events, like notifications. The screen applies each change at once, undoes it if the request fails, and keeps moved conversations out of refreshed lists until the move is confirmed.

### Replies, drafts and read statuses

`lib/mail/compose.ts` writes new emails and replies as Outlook drafts. A new email (`mode` `new`) names its source account, starts with `POST /me/messages` and takes the draft's `conversationId` as its thread key; changing From on a saved one deletes it and starts again in the other mailbox. `components/mail/compose-dock.tsx` (`ComposerProvider` in `CrmChrome`, `useComposer().openComposer`) holds up to six floating cards, positioned along the bottom right until dragged, with minimised pills; Compose, `create-email` and Quick add's Send email open one, and `GET /api/mail/accounts` (`composeAccounts`: each mail source with its signature) fills From. `components/mail/mail-composer.tsx` is the editor shared by cards and inline replies. `saveMailDraft` checks the input (`readDraftInput`: mode, the message replied to, at most 100 addresses per field, 20,000 characters), and on the first save calls `createReply`, `createReplyAll` or `createForward` on that message with the source's token (`mailSourceToken`), which gives Outlook's subject and quoted history. It keeps the draft in `crm.mail_drafts` (owner-only: provider draft id, mode, the message, thread key, the quote, recipients, subject, body, tracking id). Every save PATCHes the draft with recipients, subject and `composeEmailHtml` (`lib/mail/html.ts`): the message as escaped paragraphs with links, the signature for the source's address, the read image, then the quote with any earlier read images removed, inserted after `<body>`. A draft deleted in Outlook is made again. `sendMailDraft` saves, adds attachments with `attachToDraft` (shared with large sends in `lib/microsoft/oauth.ts`), calls `send`, marks the tracking row sent, deletes the draft row and logs an outbound email activity on each matching contact in To and Cc. `discardMailDraft` deletes the Outlook draft and the mirrored copy. `getThread` returns the thread's drafts and leaves their mirrored copies out of the messages. The browser saves 1.5 seconds after typing stops, one save at a time, and sends any unsaved change with `keepalive` when the composer closes. Routes: `POST` and `DELETE /api/mail/drafts`, `POST /api/mail/drafts/send`, `DELETE /api/mail/draft-message?id=` (deletes a mirrored draft made outside Orbit, in Outlook and in the mirror), `GET /api/mail/people` (contacts and senders for the recipient fields).

Read statuses: when `crm.mail_preferences.read_statuses` is on (the default) and Orbit has a public `https` origin (`SITE_URL`, else the request), a draft gets a `crm.mail_tracking` row and its HTML a 1×1 image at `/api/mail/open/<id>`. That public route returns a GIF and calls `private.record_mail_open` (security definer, `crm_app` only), which records a row in `crm.mail_opens` unless the email is unsent or under five seconds old, the request comes from an address the owner used Orbit from in the last 30 days (`crm.mail_viewer_addresses`, an HMAC of the IP with `APP_SECRET`, noted after each CRM page load at most hourly), the last open was under two minutes ago, or there are already 200. The user agent is reduced to an app or device (`readerAgent`). The mail sync stores the tracking id on messages from the source's own address (`trackingIdIn`), and `listThreads` and `getThread` count and list the opens. `cleanEmailHtml` removes read images, so viewing mail in Orbit never counts as a read.

### Remind me, Send later and Undo send

Undo send lives in the browser: `MailComposer` hands its content to `queueSend` in the compose dock and closes at once; the dock shows "Sent" with Undo and posts `/api/mail/drafts/send` after ten seconds, or straight away with `keepalive` on `pagehide`. The payload waits for any autosave in flight so a draft is never made twice. On the server, `writeDraft` reads the draft, its target and signature in one transaction and skips the Outlook PATCH when `content_hash` (subject, body, signature and recipients) hasn't changed since the last autosave, so a send is usually just Graph's `send`; a draft deleted in Outlook is made again and sent. Attachments load alongside, and the timeline entry and attachment clean-up run in parallel after sending. `mailSourceToken` reads only the one source.

Snooze is the `snooze` mail action: `ensureMicrosoftFolder` finds or makes a top-level Snoozed folder (kept in `mail_sources.snooze_folder_id` and given the `snoozed` role on folder refresh), the conversation's inbox and own-folder messages move there, and a `crm.mail_reminders` row (`kind` `snooze`, owner-only) records when. Send later sets `mail_drafts.send_at` (with attachments, signature and `remind_hours`) through `POST /api/mail/drafts/schedule`; `DELETE` unschedules and `GET /api/mail/scheduled` lists them. Sending with `remindHours` adds a `follow_up` reminder for the thread.

`processDueMail` (`lib/mail/due.ts`) does nothing unless something is due. It claims due drafts (clearing `send_at` with `for update skip locked`) and sends them, recording `send_error` and a notification on failure; claims due reminders, moving snoozed conversations back to the inbox and marking the latest unread, and checking follow-ups for a newer message from anyone but the user's own addresses (done if there is one, otherwise a notification). A surfaced reminder is `due`: `listThreads` sorts by the later of the newest message and `surfaced_at`, includes due follow-up threads in the inbox even when they hold only sent mail, and returns `reminder` and `snoozedUntil`. Archiving or trashing marks the thread's reminders done; unsnoozing ends its snooze. It runs from `/api/cron/mail-due` (`private.mail_due_members()` finds who has work), after each user in `/api/cron/mail`, in `/api/mail/sync` (Mail's minute poll) and after page loads.

### App and notifications

`app/manifest.ts` makes Orbit installable (standalone, `start_url` `/mail`, icons in `public/icons`), and `public/sw.js` shows pushed notifications and sets the app badge. Tapping one posts the link to an open Orbit window (iOS ignores `navigate()` on an existing window), or opens a new one; the worker also keeps the link for a minute so a window that starts up asks for it (`orbit-pending`). `PushRegistrar` opens it, and on Mail selects the conversation in place. `GET` and `POST /api/push/settings` read and save the mail level, meeting reminder minutes and first-read alerts; `POST /api/push/test` saves the device's subscription and sends it a test notification. The proxy lets `/sw.js` and the manifest through without signing in. `components/push/push-client.ts` registers the worker on every CRM page (`PushRegistrar`), subscribes with the VAPID public key from `GET /api/push/key`, and saves the subscription with `POST /api/push/subscribe` (owner-only `crm.push_subscriptions`); Mail sets the badge to the Important unread count.

`lib/push.ts` sends with `web-push`. The VAPID key pair is made on first use and kept in `private.push_keys` (the private key encrypted with `APP_SECRET`) through `private.push_key()`, so there is nothing to configure. Subscriptions the push service reports as gone (404 or 410) are deleted.

New mail: `storePage` returns the ids it inserted (`xmax = 0`), and for a live inbox those become `report.arrived`; after the sync `notifyNewMail` (`lib/mail/notify.ts`) keeps unread mail from others received in the last six hours, works out each one's split, applies the user's `notify_mail` level (`crm.mail_preferences`: important, all or none) and pushes one notification per message, or one summary for more than three. The first sync of a folder never notifies. For speed, each sync keeps a Graph change-notification subscription on the inbox (`created`, about three days, renewed within a day of expiry) pointing at `/api/microsoft/mail-webhook` with a random `clientState`; that public route echoes Graph's validation token, finds the owner through `private.mail_subscription_owner(id, clientState)` and runs a short new-mail sync after responding. Subscriptions need an https `SITE_URL`.

Other alerts go through `sendAlert` (`lib/alerts.ts`), which pushes, optionally adds a bell notification, and records a key in `crm.push_log` (owner-only, unique per user) so each alert goes out once. `calendarAlerts` (`lib/calendar-alerts.ts`) runs every minute from `/api/cron/mail-due` for the people `private.calendar_alert_members()` finds (a device set up and a meeting inside their lead time): one alert per meeting (keyed on iCal UID and start, so the same meeting in two calendars alerts once) whose link is the online meeting URL, which the service worker opens directly. `processDueMail` alerts on a failed scheduled send (always), an unanswered follow-up (with the bell) and a snooze coming back (both off when mail notifications are off). The tracking image route calls `alertFirstRead` after the first recorded open when `notify_reads` is on, using `private.mail_open_owner()`.

### Split inbox

Splits are worked out when listing, not stored, so a new contact or rule changes them at once. `lib/mail/split.ts` builds the SQL: `splitJoin` finds the user's rule for the sender's address or `@domain` in `crm.mail_sender_rules` (owner-only; the address wins), and `splitCase` applies, in order, the rule, a calendar subject or sender, a matching contact (`normalized_email`), a sent message in the same thread, automated sender patterns (news), Outlook's `inferenceClassification` (`mail_messages.focused`, false means other) and finally important. The mirror reads `inferenceClassification` with every message; `classifyFolder` fills it in once for mail already stored, page by page, and sets `mail_folders.classified_at`. `listThreads` takes `{ role: "inbox", split }` (URL `view=inbox:news`) and returns each thread's split; `mailNav` returns totals and unread per source and split, and `mailUnreadCount` (the side menu) counts Important only. `POST /api/mail/sender-split` saves or clears a rule. Bulk actions in the browser move or mark each selected conversation with up to four requests at a time and one toast with Undo.

### Attachments

`lib/mail/attachments.ts` lists a message's attachments from Graph (`/attachments`, inline images left out; `GET /api/mail/attachments?message=`) and streams one through `GET /api/mail/attachment` (`/attachments/{id}/$value`), served with a strict content security policy and `nosniff`; only PDFs, common images and plain text are shown inline, everything else downloads. Nothing is stored in Orbit.

### Other sending addresses

`crm.send_identities` (owner-only) holds an SMTP identity tied to the mail source that receives its mail, with the password encrypted with `APP_SECRET`; `saveIdentity` (`lib/mail/identities.ts`) checks the SMTP login with nodemailer before saving (Neo's servers are preset); `GET`, `POST` and `DELETE /api/mail/identities` list, save and remove them. `composeAccounts` lists each identity as `smtp:<id>` with its source, and the composer sends `identityId` with the source's draft. A draft carries `identity_id`, and the signature and content hash use the identity's address. On send, `sendMailDraft` exports the finished Outlook draft as MIME (`/$value`), rewrites From and Date and drops Bcc, Sender and Exchange headers (`rewriteMime`), sends it over SMTP with every recipient in the envelope, then saves the same MIME to Sent Items (`POST /mailFolders/sentitems/messages`), deletes the draft and appends a copy to the provider's Sent folder over IMAP (imapflow). A send failure is stored as `last_error`. Messages flagged as drafts outside the Drafts folder are treated as sent copies.

### Prepared replies and automatic reminders

`prepareMail` (`lib/mail/prepare.ts`) runs after each user's sync and due mail in `/api/cron/mail` and after a webhook sync that stored anything. It needs `LLM_API_KEY` and reads `mail_preferences.prepare_replies` and `auto_remind_days`. First it takes up to 12 sent messages from the last 48 hours that are the latest in their thread, have no waiting follow-up and haven't been checked, asks the model in one call which expect an answer, and records each in `crm.mail_prepared` (`kind` `follow_up`, `scheduled` or `skipped`, owner-only); a scheduled one adds a `mail_reminders` follow-up with `automatic` set, due after that many working days (`workingDaysLater`). Then, unless the day's 60 drafts are used, it takes up to 6 inbox messages from the last 48 hours in the Important split that are the latest in their thread, from someone else, with no draft, and asks the model whether a reply is needed and for the reply, with the thread, CRM context for the people, recent call and meeting notes, recent sent mail and the last edited drafts (prepared body against what was sent). The result is a `reply` row, `ready` with its body or `skipped`. A follow-up that comes due with no reply calls `prepareNudge`, which writes a `nudge` row for the user's latest message. `getThread` returns the ready draft for the latest message and any waiting follow-up; `listThreads` marks threads with one. `POST /api/mail/prepared` marks a draft `used` or `dismissed`, or cancels a reminder. On send, `notePreparedSent` moves a used draft to `sent` with the sent body (the edits it learns from) and anything else to `dismissed`. Every prompt treats email text as material to read, never as instructions, and nothing is sent automatically.

When the model marks a prepared reply as a meeting request it writes `[[times]]` where times go. `offerTimes` (`lib/mail/scheduling.ts`) takes the booking page rules (or the defaults when there is no page) with at least four hours' notice, reads the user's own busy calendar events through `withActor`, and `pickTimes` chooses up to three slots on different days, preferring 10:00 to 16:00 and moving from morning to afternoon. The body is rendered from the stored `template` and `slots`; `freshPrepared` re-checks them against the calendar when the thread is read and when a draft is used, and re-renders if any is taken or within an hour. `POST /api/mail/ai/event` (`eventFromThread`, `lib/mail/event.ts`) asks the model for a title, date, time, length and note from the thread and returns them with the conversation's other people (matched to contacts) and the invite setup; the reader opens the calendar's `InviteDialog` with that prefill, so sending goes through `createInvite` as usual.

Attachment text: `attachmentNotes` (`lib/mail/attachment-context.ts`) takes the last messages of a thread, and for any with attachments that haven't been read lists them through Graph, downloads up to four readable ones per message (15 MB cap, streamed) and extracts text with `readAttachmentText` (`lib/mail/attachment-text.ts`: unpdf for PDF, fflate plus the XML parts for docx, xlsx and pptx, and plain text and HTML). Each attachment gets a `crm.mail_attachment_texts` row (owner-only; `read`, `unreadable`, `too_large` or `failed`, text capped at 30,000 characters), so it is fetched once. The notes, labelled with file name, sender and date, are shared out within a character budget: 12,000 for prepared replies and Write with AI, 6,000 for summaries. Ask AI also searches read attachments with a full-text index and quotes `ts_headline` fragments.

### Mail AI

`lib/mail/ai.ts` uses `completeJson` with the default model. Thread text comes from the mirror's plain text with quoted history cut (`stripQuoted`), newest messages first up to 16,000 characters. `summariseThread` stores one row per thread in `crm.mail_summaries` (owner-only) with the newest message id, so it is reused until new mail arrives; a single message under 280 characters isn't summarised. `draftWithAi` adds the people's CRM context and up to four of the user's own recent sent emails as examples of their voice, and asks for the body only. `askMail` first turns the question into up to four keyword searches with optional sender and date limits, runs them against the full-text index (falling back to no limits), then answers from the twelve best matches with numbered sources, which become thread links. Em and en dashes are replaced in everything the model writes. Routes: `GET /api/mail/summary`, `POST /api/mail/ai/draft`, `POST /api/mail/ai/ask`, each rate limited per user through `private.consume_rate_limit`. Semantic vector search is left out to keep the database within the Free plan.

## Relationship

`lib/crm/relationship-signals.ts` gathers signals per company or contact in two queries. The first reads email, meeting and call activities up to now, skipping titles that look like automatic replies or bounces and emails whose tone row says `automatic`. It splits them into inbound (`direction = inbound`, or old inbox mail with a `from`), outbound and meetings, with counts, latest dates, the outbound emails since they last replied or met, and engagements in the last 90 days. The second finds the latest tone in the last 120 days from `crm.activity_tones` or a call's `sentiment` (healthy, watch and at risk map to positive, neutral and negative). `scoreRelationship` (`lib/crm/relationship-score.ts`) turns them into a label and a reason. `listCompanies` adds `relationship` when asked with `relationships: true` (the Companies page, `/api/v1/companies`, the assistant and MCP), `getCompanyContext` always does, and the contact page, Quiet and Tasks call `relationshipsFor`.

`crm.activity_tones` holds one row per inbound email activity: `tone`, `automatic`, a short `reason` and the model. Members read and write their workspace's rows; agents only read. `classifyEmailTones` (`lib/crm/email-tone.ts`) runs at the end of `syncMail` when ten seconds or more remain, sending up to 12 unclassified inbound emails from the last 120 days to `completeJson` in one request.

## Boards

A board is a row in `crm.pipelines` with `kind = 'board'` (the default pipeline is `kind = 'sales'`), its own `crm.pipeline_stages`, a `position` for the side menu, and `add_on_won`. Cards are `crm.opportunities` rows on that pipeline: one active card per company per board (checked in `insertOpportunity`), named after the company, with `expected_close_date` used as the due date. Board stages have no won or lost flags and need at least one stage; sales pipelines keep exactly one won and one lost stage. Archiving a board archives its cards.

Lifecycles are free text (1 to 40 characters). `lead`, `prospect`, `customer` and `churned` are built in: `cleanLifecycle` (`lib/companies.ts`) maps their keys and labels to the key, and `matchLifecycle` in `lib/crm/companies.ts` gives any other name the spelling a company in the workspace already uses. `lib/crm/lifecycles.ts` lists them with counts, and renames or deletes custom ones by rewriting each company through `setCompanyLifecycleInDb` (one `company.updated` audit event each; delete moves them to `lead`). Built-in ones can't be renamed or deleted.

When an opportunity on a sales pipeline becomes won (on create or update), `afterWon` sets the company's lifecycle to `customer` with an audit event and adds a card to the first stage of every active board with `add_on_won` that doesn't already hold the company.

Adding is inline. `components/crm/record-combobox.tsx` is a search box with a listbox in a popover anchored to the input; it searches through `searchRecords` in `record-picker.tsx` (contacts scoped to a company with `searchCompanyContactsAction`, or to people with any company when the company is still empty) and offers "Add … as a new company" or "Add … at <company>", which call `addCompanyInlineAction` and `addContactInlineAction`. Enter before results arrive waits for them and picks the exact match, else the first. `opportunity-composer.tsx` uses two of them as a card in a stage (focused without scrolling the page) or as a row under the list, and saves with `addOpportunityInlineAction`; `inline-adders.tsx` holds the Contacts and Companies rows. Opening an existing card or opportunity still uses the sheet.

## Proposals

| Table | What it holds |

| `crm.products` | Name, description, `price_gbp`, `price_usd` (at least one), `billing` (`one_off`, `monthly`, `yearly`), `archived_at`. |
| `crm.document_templates` | `kind` (`proposal`, `nda`), name, `status` (`draft`, `active`, `archived`), `blocks` and `settings` (accent colour, valid days, and `logo`, a PNG data URL of up to 300,000 characters made in the browser) as JSON, checked by the zod schemas in `lib/proposals/model.ts`. |
| `crm.documents` | One proposal or NDA: template, title, `status` (`draft`, `sent`, `viewed`, `client_signed`, `completed`, `declined`, `withdrawn`), company, contact, optional opportunity, owner, currency, `items` and `blocks` copied from the template and products, `valid_until`, `current_version_id`, view counts and the time of each step. |
| `crm.document_versions` | What was sent: `content` (the filled-in blocks, items, totals, both parties and the consent text) and `content_hash`, a SHA-256 of its stable JSON. |
| `crm.document_links` | The client's link for a version: `token_hash` (SHA-256), `token_cipher` (encrypted with `APP_SECRET` so Orbit can show the link again), `revoked_at`. |
| `crm.document_signatures` | One `client` and one `sender` signature per version: name, title, company, typed signature, consent text, method (`email_link` or `orbit_login`), IP address, browser and time. |
| `crm.document_events` | Created, sent, viewed, client signed, countersigned, completed, declined, changed and withdrawn, with who, IP address, browser and data. `occurred_at` defaults to `clock_timestamp()` so events in one transaction keep their order. |
| `crm.document_files` | The `issued` PDF (rendered on send) and the `executed` PDF (rendered on completion), with their SHA-256. |

All of them are shared workspace records with `_member` and `_agent` policies like the rest of the CRM. Drafts can be deleted; sent documents can't. Versions, links, signatures, events and files are insert-only (links may only set `revoked_at`), so what was signed can't be changed after the fact.

`lib/proposals/catalogue.ts` holds products and templates, and `lib/proposals/documents.ts` the rest. `createDocument` checks that the template is active and the contact works at the company, prices the items in the chosen currency, and links the company's only open sales deal. `sendDocument` refuses missing fields and square-bracket placeholders, snapshots the content into a version, renders the PDF (`lib/proposals/pdf.ts`, pdf-lib with the standard fonts and a signing certificate page), creates a 24-byte link, sets the status and emails it through `sendContactEmail`. `reviseDocument` revokes the link and returns to draft. `countersignDocument` needs `client_signed` and the owner, a workspace owner or an admin, then stores the executed PDF and emails the client.

The client page (`app/p/[token]`) and its routes (`/api/p/[token]/sign`, `/decline`, `/pdf`) are public in `proxy.ts`. `private.document_link_owner` (granted only to `crm_app`) turns the hashed token into the document, version and owner; `lib/proposals/public.ts` then acts as the owner through `withActor`, like booking pages. It counts views (not for signed-in members), records `document.viewed` the first time, and alerts the owner in the bell and by push, deduplicated per hour. `clientSign` needs `agree: true`, signs the current version only, and records `document.signed`; signing is limited to 20 attempts per IP address in 10 minutes.

Audit events `document.created`, `.sent`, `.viewed`, `.signed`, `.completed`, `.declined`, `.withdrawn` and `.changed` feed webhooks and the `proposal_event` workflow trigger, whose context adds `proposal` (title, kind, status, total, currency, valid until, decline reason, who signed, Orbit and client links) with the company and contact. `proposalsForDeals` gives Opportunities the latest proposal per deal, by deal or else by the company's unlinked proposal.

## Workflows

`crm.workflows` belongs to its owner (`owner_id`) and stores `definition` (`{version: 2, trigger, triggerPosition, nodes, edges}`, validated by `lib/workflows/definition.ts`: every edge leaves a real output of its source (`out`, or `true`/`false` for If, `each`/`done` for For each item), each output connects to at most one node, and the graph has no cycles), `trigger_type` for matching, `status` (`draft`, `active`, `paused`), `is_template`, and `next_run_at` for schedules. Members read their own workflows and shared templates; owners and admins read all.

Events: `recordAudit` calls `enqueueWorkflowEvent`, which maps the audit event to trigger types (`eventTriggerTypes`) and inserts into `crm.workflow_events` inside the same transaction, carrying the source workflow id and depth from the provenance. `private.dispatch_workflow_events` turns each event into `crm.workflow_runs` for every active workflow with a matching trigger type, skipping the workflow that caused the event and anything three levels deep, snapshotting the definition, then deletes the event. Finer trigger filters (field, stage, board, activity type, "only mine") are checked when the run starts; a run that doesn't match is deleted.

Runs: `private.claim_workflow_runs` claims queued runs, waits that are due, and runs stuck for ten minutes, with `for update skip locked`, only for owners still in the workspace. `executeRun` (`lib/workflows/engine.ts`) builds the context as the owner (`buildContext`: company, contact, deal, activity, call summary and transcript, task, change), then follows the graph from the trigger's `out` edge, storing the current node in `state.at` and a stack of loop frames, and logs each node to `crm.workflow_run_steps`. When a path ends (no edge from the chosen output, or Continue only if is false), the innermost loop moves to its next item or, when done, carries on from its `done` output; with no loop open the run finishes. Older definitions saved as nested step lists are converted to a graph when read (`safeDefinition`), and runs started under the old format are cancelled with a message. Waits store `resume_at`; approvals store the pending step in `state` and notify the owner, and `decideApproval` resumes or cancels the run. Every write a step makes goes through the normal domain functions as the owner, with provenance `source: workflow`. A run stops starting steps eight seconds before its deadline and is re-queued. Test runs execute AI and logic steps and replace actions with a description of what they would do. `private.claim_due_schedules` leases due schedule workflows; the engine queues a run and sets the next time in London time.

Capabilities beyond the basic nodes, all in `lib/workflows/engine.ts` unless named:

- Ask AI can set `webSearch`, which sends `web_search_options` through `completeJson` (`lib/llm.ts`, which also returns the gateway's URL citations) and adds an optional `sources` list output merged with those citations, and `context`, which appends the run's company and contact, their last 10 activities, open and recent deals, and the owner's last 8 emails with the contact (`recordContext`). The system prompt tells the model that emails, pages and records are material, not instructions.
- `find_records` (`lib/workflows/records.ts`) selects up to 100 companies or contacts through `withActor` with lifecycle, tag, owner, open deal, days since the last activity and search filters, ordered by `last_contacted_at` (latest activity), creation or name. `skipDays` leaves out records the same workflow found within that window, using `crm.workflow_record_marks` (owner-only, written only on real runs). Each record item carries `type` and `id`; when For each item reaches one, `applyLoopRecord` loads it as the run's company and contact for that iteration, and the outer company and contact come back when the loop ends.
- `upsert_record` finds a company by domain or normalised name, or a contact by email, and creates it unless `create` is off (companies through `upsertCompany`, which schedules enrichment). `useInRun` makes it the run's record.
- `webhook` posts a rendered body (JSON when it parses, otherwise text), or the run's data as JSON, to an https address, refusing private and local hosts and redirects, with a 10 second timeout.
- Schedules can be monthly (`dayOfMonth` 1 to 28).
- `email_received`: after a mail sync stores new inbox mail, `queueMailWorkflowEvents` (`lib/workflows/mail-events.ts`) checks the owner has an active email workflow, classifies each message (bounce by sender or subject, with the failed address taken from the body; automatic reply by subject; otherwise any, marked as a reply when the user sent earlier in the thread) and inserts a `crm.workflow_events` row with `owner_user_id`. The dispatcher only matches events with an owner to that owner's workflows, and the insert policy only lets a person set themselves as owner. `buildContext` loads the message as the owner and the contact by sender, or by the bounced address. `/api/cron/mail` and the Graph webhook run a workflow tick when events were queued.

`runWorkflowTick` dispatches events, starts schedules and executes claimed runs until its budget runs out. It runs in `after()` on CRM page loads, after `/api/cron/sync`, from `/api/cron/workflows`, and straight after an event is queued.

`crm.notifications` holds in-app notifications per user (approvals, failures, Notify someone steps), readable and updatable only by that user; any member may insert one for another member of the same workspace.

## Linear

`lib/linear.ts` calls Linear's GraphQL API with `LINEAR_API_KEY` (sent raw in `Authorization`), scoped to the team whose key is `LINEAR_TEAM_KEY` (default `CNT`). The team, its workflow states and labels are cached for five minutes. The assistant's create, comment and update tools are write tools, so they need approval.

## Quiet relationships

## Learning

`crm.memories` holds what the assistant has learned: `scope` is `personal` (with `user_id`, readable only by that person), `business` or `market` (shared with the workspace), plus kind, title, body, sources, confidence, pinned, an optional company, origin (`learning`, `assistant` or `manual`) and a generated full-text `search` column. `crm.market_notes` is the inbox Grok Bot writes to through MCP (agents with `market:write` may insert and read in their workspace; a link is unique per workspace), `crm.watchlist` is what it researches, `crm.learning_runs` records each run per unit (workspace and kind, plus user for `personal` and `brief`) and `crm.daily_briefs` holds one brief per person per day. `lib/learning/nightly.ts` gathers material inside `withActor`, calls the model outside the transaction, and applies the returned additions, updates and retirements in another; only notes with origin `learning` that aren't pinned can be changed or retired by it. `private.issue_market_agent` creates or re-keys the Grok Bot agent (scopes exactly `market:write`) for an owner or admin, and `private.market_agent_status` reports when it was connected and last used.
